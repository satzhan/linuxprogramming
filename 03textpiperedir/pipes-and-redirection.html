Pipes and redirection

How seven small dumb programs turn into one useful one, and what the operating system is doing while they do it.

stdin, fd 0 stdout, fd 1 stderr, fd 2

A file too big to look at

Here is a file. Ten lines, each one a timestamp and a word like INFO or ERROR.

2023-09-10 10:15:32 INFO: Application started
2023-09-10 10:16:45 WARNING: Low memory warning
2023-09-10 10:17:30 ERROR: Failed to connect to database
2023-09-10 10:18:22 INFO: User logged in
2023-09-10 10:19:15 DEBUG: Processing item 1
2023-09-10 10:20:05 ERROR: Invalid input received
2023-09-10 10:21:18 WARNING: CPU usage high
2023-09-10 10:22:30 INFO: Task completed successfully
2023-09-10 10:23:45 DEBUG: Closing connection
2023-09-10 10:24:50 INFO: Application shutdown

Two of them are errors. You can count those with your eyes in about four seconds and there is nothing more to say about it.

Now make the file bigger. It has been collecting since March, it has 800,000 lines in it, and somewhere in there the database connection failed a few times. Your eyes are no good now. Opening it in an editor is no good either. The editor will load it, eventually, and then you will scroll for the rest of the afternoon.

So we want to ask the machine instead. Something like: how many lines in this file have the word ERROR in them? The trouble is the machine has no idea what a line is, or a word, or an error. What it has is a pile of small dumb tools, each one doing exactly one thing, and a way to hook them together. Hooking them together is the whole trick, and it is what this page is about.

Let us do it wrong first. Doing it wrong is how you find out what the pieces are for.

Doing it wrong first

Suppose we have two tools. One is grep, which reads lines and prints back only the ones containing some word. The other is wc, which reads lines and prints how many there were. Between them they can answer the question. Neither can answer it alone.

The obvious move is to run the first one, catch what falls out, and hand it to the second one:

$ grep "ERROR" logfile.txt > errors-only.txt
$ wc -l errors-only.txt
2 errors-only.txt
$ rm errors-only.txt

That works. It gives the right answer. And it is a perfectly reasonable thing to do, which is why almost everybody does it the first time. But look at what it costs.

You invented a file. You had to name it, which means you had to think of a name, which means that ten minutes from now there will be a file called errors-only.txt sitting in your directory and you will not remember whether it matters. You had to remember to delete it. If the log had been 40 gigabytes and one line in twenty was an error, you would have needed two gigabytes of free disk just to hold an intermediate answer that nobody wanted. And wc could not start until grep was completely finished, because the file was not complete until then.

Hold on to that last one. It comes back later and it turns out to be the deep difference between the two mechanisms on this page.

What we actually wanted was for the output of grep to become the input of wc without ever touching a disk. That is a pipe, and it is written with one character:

$ grep "ERROR" logfile.txt | wc -l
2

No temporary file. No name to invent. No cleanup. Both programs running at the same moment, one feeding the other.

That is the punchline, and you have now seen it, so the rest of this page is the interesting part: why it works, what the operating system is doing while it happens, and how it is different from the > in the wrong version, which looks similar and is not.

A confession about that command. Even the good version above is doing more work than it needs to. grep can count by itself: grep -c "ERROR" logfile.txt gives the same 2 and starts one program instead of two. We are using the long form because it shows the plumbing. Through this whole page, when a shorter command exists, it gets pointed out. Knowing the short way and the long way is better than knowing either one.

The tools, one at a time

Seven commands. Each one is boring on its own, and that is deliberate. They are boring in a way that makes them combine.

cat — pour a file out

$ cat hello.txt
Hello, World!
Welcome to Linux text manipulation.

cat is short for concatenate, because its real job is gluing several files together end to end: cat a.txt b.txt c.txt gives you one continuous stream of all three. Printing one file is the degenerate case of that, and it is what everyone actually uses it for.

cat -n numbers the lines as they go by. Useful when someone tells you the bug is on line 402.

Where it falls down. cat on a 40-gigabyte log will faithfully throw all 40 gigabytes at your terminal and you will sit there for a long time watching text you cannot read. For big files use head, tail, or less. less shows you one screen at a time and lets you page around; press q to quit. It is not on this page because it is interactive and does not combine with the others, but in real life you will use it constantly.

echo — say something out loud

$ echo "Hello, World!"
Hello, World!
$ NAME="Alice"
$ echo "My name is $NAME"
My name is Alice

echo prints its arguments. That is all it does. It seems almost too simple to be worth a name, and then you find that half of shell programming is echo feeding something else, because it is the cheapest way to manufacture a bit of text out of nothing.

Notice the second one. The shell replaced $NAME with Alice before echo ever ran. echo never saw a variable, it saw the finished words. The shell does a surprising amount of rewriting to your command line before the command starts, and redirection, which we get to shortly, is another piece of that same rewriting.

wc — count what went past

$ wc logfile.txt
 10  70 483 logfile.txt
$ wc -l logfile.txt
10 logfile.txt

Three numbers with no header: lines, words, bytes, in that order. -l for lines, -w for words, -c for bytes, -m for characters.

The -c and -m split is worth a second. In a plain English file they give the same number, because each character is one byte. In a file with accented letters or Japanese or an emoji they do not, because those characters take several bytes each. -c counts storage, -m counts letters.

Where it falls down. wc -l does not really count lines. It counts newline characters. If a file ends without a final newline, the last line is real, visible, and uncounted. This is a genuine and very old source of off-by-one arguments.

sort — put lines in order

$ sort names.txt
Alice
Bob
Charlie
...

Default is alphabetical. -r reverses it, -u drops duplicates, and -n switches to numeric.

You need -n more often than you expect, because without it sort compares text, and as text, 100 comes before 9. That is not a bug. One and nine, and one is smaller. It is only wrong if you meant numbers, and sort has no way to know that you did unless you say -n.

Where it falls down. What counts as alphabetical depends on your language settings. In one locale, punctuation and capital letters are quietly ignored while sorting; in another they are not, so Zebra lands before apple. If you need an answer that is the same on every machine, set the locale to the plain byte ordering for that one command: LC_ALL=C sort names.txt. Scripts that worked on your laptop and broke on the server have died on this.

grep — keep only the lines that match

$ grep "ERROR" logfile.txt
2023-09-10 10:17:30 ERROR: Failed to connect to database
2023-09-10 10:20:05 ERROR: Invalid input received

A sieve. Lines with the pattern fall through, lines without it do not. -i ignores case, -n prefixes each hit with its line number, -v inverts the sieve and keeps everything that did not match, and -c prints the count instead of the lines.

-v is the one people forget they have. "Show me the log with all the DEBUG noise taken out" is grep -v "DEBUG" logfile.txt, and there is no other tool here that does it.

A precision point that matters. grep -c counts lines that contain at least one match, not matches. If a line says ERROR: retrying after ERROR, that is one line and two errors, and -c will say one. If you genuinely want occurrences, grep -o prints each match on its own line, so grep -o "ERROR" logfile.txt | wc -l counts them. The original question we asked at the top of this page, "how many lines have ERROR in them", is the -c question. Be careful which one you are being asked.

head and tail — take an end

$ head -n 3 logfile.txt
(first three lines)
$ tail -n 2 logfile.txt
(last two lines)

Both default to ten lines. head is how you look at a huge file without printing it, and it is the polite thing to run before cat when you do not know how big something is.

tail has one option that is not like the others: tail -f keeps the file open and prints new lines as they are written. That is how you watch a log live while you poke at the thing producing it. It never exits on its own; Ctrl-C stops it.

Alternatives worth knowing. Two more tools show up constantly in real pipelines and are not on this page: cut, which slices columns out of each line, and uniq, which collapses adjacent identical lines and with -c counts them. sort | uniq -c | sort -rn is the standard "count how many of each" idiom and you will meet it everywhere.

Try it first You want the three most common log levels in logfile.txt, with counts. You have cut, sort, uniq -c, and head. What order do they go in? 
$ cut -d" " -f3 logfile.txt | sort | uniq -c | sort -rn | head -n 3
      4 INFO:
      2 WARNING:
      2 ERROR:

The sort before uniq is the part that catches people. uniq only collapses lines that are next to each other, so unsorted input gives nonsense. It is a deliberately dumb tool, and being dumb is why it can handle a file larger than memory.

Redirection

Every one of those commands printed to your screen. None of them mentioned the screen. grep contains no code about terminals, no code about windows, no code about scrollback. It writes its answer into something, and something happens to be the screen, and grep does not know or care which.

Redirection is how you change what that something is.

$ sort names.txt > sorted.txt

Nothing appears on screen. The sorted names went into sorted.txt instead. The important thing is what did not happen: sort was not told to write to a file. sort ran exactly the same code it always runs, writing to the same place it always writes. The shell moved the far end of that place before sort started.

There are four of these to learn and they are all the same idea.

WrittenDoes
> fileSend normal output to file. Wipes it first if it exists, creates it if it does not.
>> fileSend normal output to the end of file, keeping what was there. Creates it if needed.
< fileTake input from file instead of the keyboard.
2> fileSend error messages to file.

The 2 in that last row is not decoration and it is not an option to the command. It is a number that names one of the three streams, and the next section is about where that number comes from.

Two things that will bite you

First, > empties the file before the command runs. Not after, not during. Which makes this an excellent way to destroy your own data:

$ sort names.txt > names.txt
names.txt is now empty. Every name is gone.

The shell opened names.txt for writing, which truncated it to nothing, and only then started sort, which opened an empty file and had nothing to sort. There is no undo. Write to a different name, then rename.

Second, errors do not go where output goes. Run sort on a file that is not there:

$ sort nosuchfile.txt > out.txt
sort: cannot read: nosuchfile.txt: No such file or directory

You redirected the output and the complaint still landed on your screen. That is on purpose, and it is one of the better decisions in the design of this system. If errors travelled with output, then every error message from a three-hour batch job would end up buried in the middle of the output file, and the one thing you want to see immediately is the thing you would be least likely to find. Errors get their own channel so that redirecting the answer never hides the problem.

Try it first You run grep "ERROR" logfile.txt missing.txt > found.txt and missing.txt does not exist. What is on screen, and what is in found.txt?

On screen: one complaint about missing.txt, because that is an error and errors were not redirected. In found.txt: the matching lines from logfile.txt, which grep found perfectly well and wrote to the redirected output.

The command half worked and told you so. This is the normal case, not an unusual one, and it is the reason the two streams are separate.

Three numbers every program is born with

Now the part that makes everything else fall into place.

When the operating system starts a program it hands it a small numbered table. Every open thing the program has, a file, a terminal, a network connection, a pipe, sits in a slot in that table, and the program refers to it by slot number. Those numbers are called file descriptors, and a program does not get to see anything more than the number. It asks the kernel to write to slot 1. What slot 1 is attached to is none of its business.

Three slots are already filled in before your program's first instruction runs:

  • 0, standard input. Where the program reads from. Usually the keyboard.
  • 1, standard output. Where answers go. Usually the screen.
  • 2, standard error. Where complaints go. Also usually the screen, which is why it looks like one place until you redirect and discover it is two.

Redirection, all of it, is one sentence: the shell changes what a slot points at before the program starts.

Read the operators again with that in mind and they stop being four separate facts:

  • > file makes slot 1 point at a file.
  • >> file makes slot 1 point at a file, positioned at the end.
  • < file makes slot 0 point at a file.
  • 2> file makes slot 2 point at a file.

One mechanism, four spellings. And now the mysterious 2 is not mysterious: it was the slot number all along. You can write 1> file if you like, and it means exactly what > file means; the 1 is just the default you are allowed to leave out.

This is a bigger idea than shell syntax, and it is worth saying plainly. Because a program only ever deals in slot numbers, the same program works on a file, a terminal, a pipe, a network socket, a serial port. It was never written for any of them. That is what people mean when they say everything in Unix is a file: not that everything is stored on a disk, but that everything is reached the same way, through a numbered slot, with read and write.

Try it first What does wc -l < logfile.txt print, and how is it different from wc -l logfile.txt? 
$ wc -l logfile.txt
10 logfile.txt
$ wc -l < logfile.txt
10

Same count, no filename. In the first, wc opened the file itself, so it knows the name and prints it. In the second, the shell attached the file to slot 0 and wc read from standard input, where there is nothing to know a name from. wc cannot print what it was never told.

That difference is small here and large later. A command that opens files itself can name them in its error messages. A command reading standard input can only say "something on the input was wrong".

Pipes, and why they are not redirection

Go back to the working command:

$ grep "ERROR" logfile.txt | wc -l
2

Here is what the shell built. It asked the kernel for a pipe, which is a buffer with two ends, a place to put bytes in and a place to take them out. It made slot 1 of grep point at the in end. It made slot 0 of wc point at the out end. Then it started both programs at once and stood back.

So far this sounds like redirection with extra steps, and the syntax encourages the confusion: > and | are both single punctuation marks that sit between things. They are not the same and the difference is worth being precise about.

The difference that matters most

With a temporary file, the second program cannot begin until the first has finished, because until then the file is incomplete and there is no way for wc to know that more is coming.

With a pipe, both programs run at the same time. grep finds a matching line and writes it. wc is already awake, waiting, and counts it. Then grep goes looking for the next one. On a 40-gigabyte log, the answer starts being computed on the first line, and the total amount of disk used by the intermediate result is zero, because there is no intermediate result. There is only a small buffer with data flowing through it.

This is the producer and consumer arrangement, and the reason it works is that neither side has to know how fast the other one is. If grep races ahead and fills the buffer, the kernel puts grep to sleep until wc has taken some out. If wc gets ahead and empties the buffer, the kernel puts wc to sleep until grep writes more. Nobody wrote any code to coordinate this. It falls out of the buffer being a fixed size, and it is the whole reason you can pipe a file larger than your memory through five programs and nothing falls over.

The other differences, briefly

  • A file has a name. A pipe does not. You cannot list it, open it later, or hand it to a program tomorrow. It exists only while the two programs are attached to it and then it is gone.
  • A file can be re-read. A pipe cannot. A program can jump back to the start of a file and read it again. Bytes taken out of a pipe are gone. This is why sort has to read its entire input before printing anything, while grep can print as it goes. sort cannot know the first line of its answer until it has seen the last line of its input.
  • A pipe goes one way. One end writes, the other reads, and there is no arguing with it.
  • A file survives you. A pipe does not. If you want the answer tomorrow, something in the chain has to end in a file.

Which is why the two get used together constantly, and the combination reads exactly as it is built:

$ grep "ERROR" logfile.txt | sort | uniq -c > error-summary.txt

Three programs passing bytes between them with nothing on disk, and then the last one's output landing in a file because that part you want to keep.

Try it first Why does grep "ERROR" huge.log | head -n 3 come back instantly, when grep would need several minutes to read the whole file?

head prints three lines and then, having no further interest in anything, exits. That closes its end of the pipe. The next time grep tries to write, there is nobody at the other end, so the kernel sends it a signal called SIGPIPE, whose default behaviour is to kill the process on the spot.

grep never finishes reading the file. It gets shot in the head, politely, by a mechanism designed for exactly this. It is why you can safely pipe an enormous thing into head and why the same trick with a temporary file would make you wait for the entire run.

What the shell actually does

Everything so far has been a description of results. Now the mechanism, because the mechanism explains several things that otherwise look arbitrary.

When you type sort names.txt > sorted.txt, the shell does not "run sort with redirection". The shell has no power to reach inside another program. What it does instead is stranger and simpler: it makes a copy of itself, rearranges the copy's file descriptor table while the copy is still the shell, and only then tells the copy to turn into sort.

Step through it.

Making one redirection happen

The child's file descriptor table, at each step of sort names.txt > sorted.txt

The thing to take away is step four. dup2 does not move a file into slot 1 and it does not tell sort anything. It overwrites one entry in a table with a copy of another entry, and it quietly closes whatever slot 1 used to hold. After that, slot 1 and slot 3 are two names for the same open file, which is why slot 3 can be thrown away immediately without losing the file.

And step six is the punchline: exec replaces the running program with a completely different one, and the file descriptor table survives that replacement untouched. That is the only reason any of this works. The table belongs to the process, not to the program, so the shell can set the table up and then hand the process over to a program that knows nothing about what was done to it.

A correction to something you may have read. Plenty of explanations, including the notes this page was built from, end the story with "and then the shell restores the original stdout". For an external command like sort that is not what happens, because the shell's own slot 1 was never touched. All the rearranging happened inside a child process that has now become sort and will shortly cease to exist. There is nothing to restore.

The restore version is not invented out of nothing. It is true for commands that the shell runs itself without forking, the builtins, like echo and cd. For those there is no child, so the shell must save its own descriptors and put them back afterwards. Two different mechanisms that produce the same visible result, which is how the two accounts got mixed up. If you learn the fork version, everything you meet later will make sense; if you learn only the restore version, fork and exec will be a shock.

Try it first Given that the table is copied into the child and survives exec: if you redirect in one command, why is the next command back to normal?

Because the rearranged table was the child's copy, and the child is gone. The shell's own table was never modified, so the next command's child inherits a clean copy.

This also explains a thing that surprises people: cd works and persists, because cd is a builtin and the shell really does change its own state. A program that changed directory in a child would have no effect on you at all. That is why cd cannot be an ordinary program.

Inside the pipe

The buffer in the middle of the diagram is a real object with a real size, and knowing its size explains behaviour you will otherwise find mystifying.

On Linux a pipe holds 65,536 bytes, which is 64 kilobytes. When it is full, writers sleep. When it is empty, readers sleep. You can see the number on your own machine:

$ cat /proc/sys/fs/pipe-max-size
1048576

That is the largest a pipe may be enlarged to, not the default. The default of 64 KiB is set in the kernel and a program can request a different size for its own pipes.

About the 4 KB you will see everywhere. Older books and a great many web pages say a pipe buffer is 4 KB. That number is not made up, and it is worth knowing what it is, because you will run into it.

Before Linux 2.6.11, released in 2005, the capacity really was one page, 4096 bytes. Separately, and still true today, there is a constant called PIPE_BUF which is 4096 on Linux and which means something else entirely: it is the largest write that is guaranteed not to be chopped up and interleaved with writes from another program sharing the same pipe. Capacity and atomicity, two different 4096s, and they have been getting confused with each other for twenty years. The capacity is 64 KiB.

What happens at the ends

  • Writer stops, reader keeps reading. The reader drains what is left and then sees end of file, exactly as if it had reached the end of a normal file. This is how wc knows to stop waiting and print its answer.
  • Reader stops, writer keeps writing. The writer gets SIGPIPE and dies, which is the head case from earlier. It looks brutal and it is the right design: continuing to compute an answer nobody will collect is a waste of a machine.
  • Both stop. The pipe is destroyed. It had no name and nothing referred to it, so there is nothing left behind.

That last point is what "anonymous pipe" means. If you want a pipe with a name, one that two unrelated programs started at different times can both open, that exists too and it is called a FIFO: mkfifo mypipe makes one, and it shows up in ls as a real entry in the directory. It is the same buffer mechanism with a doorbell on the front. You will not need it often, but it is worth knowing it exists so that the word "anonymous" means something.

There are two buffers, not one, and only one of them is the kernel's. The kernel has the pipe buffer described above. Separately, most programs keep their own buffer inside themselves and only hand bytes to the kernel when it fills up. Worse, most programs change that behaviour depending on what slot 1 is attached to: when it is a terminal they flush every line so you see output as it happens, and when it is a pipe or a file they save up a few kilobytes first, for speed.

This is the single most confusing thing in this whole area, because it means a command can behave differently when piped than when run alone, and nothing about the pipe caused it. The next section is a demonstration of exactly that, and it looks like a bug until you know this paragraph.

Watching it happen in Python

Shell syntax hides the file descriptors. Python does not, so here is a short program that uses them by number, the way the kernel sees them. Save it as file_descriptor.py.

import os
import sys

# open a file and get back a slot number
fd = os.open("sample.txt", os.O_RDWR | os.O_CREAT)

os.write(fd, b"Hello, File Descriptors!")
os.lseek(fd, 0, os.SEEK_SET)        # jump back to the start
content = os.read(fd, 100)

print(f"Read from file (stdout): {content.decode()}")
print("This is an error message!", file=sys.stderr)

user_input = input("Enter something for stdin demonstration: ")
print(f"You entered (stdout): {user_input}")

os.close(fd)

Three things worth noticing before running it.

The lseek call is the thing a pipe cannot do. The program writes 24 bytes, jumps back to position zero, and reads them again. A file has a position you can move. A pipe has no position at all, and the same program pointed at a pipe would fail on that line. This is the difference from the pipe section, made concrete in one call.

os.read(fd, 100) asks for 100 bytes and gets 24, because that is all there is. Reading fewer bytes than you asked for is normal and correct, and forgetting that is a classic source of bugs in programs that talk to pipes and networks, where a short read means "that is all I have right now", not "that is all there is".

And print goes to slot 1 while print(..., file=sys.stderr) goes to slot 2. Same program, two channels, and from here on you can separate them from outside.

Sending the two channels to different places

$ python3 file_descriptor.py > output.txt 2> error.txt
nothing appears, and the terminal sits there waiting for you to type

Type something, press Enter, and then:

$ cat output.txt
Read from file (stdout): Hello, File Descriptors!
Enter something for stdin demonstration: You entered (stdout): hello
$ cat error.txt
This is an error message!

The two streams went to two files and neither knows about the other. Also, look at the second line of output.txt. The prompt and the answer are on the same line, because input writes its prompt without a newline after it, so the next thing printed lands right behind it. That is not a mistake, it is what a prompt is.

The freeze

Now the interesting one. Redirect only the output:

$ python3 file_descriptor.py > output.txt
This is an error message!
and now nothing. The cursor sits there. It looks hung.

It is not hung. It is waiting for you to type, and it has asked you to, and you cannot see the question, because the question was printed to standard output and standard output is now a file. The error message got through because errors were not redirected.

Press Enter and it completes normally. Nothing was wrong. A program politely asking a question into a file while you stare at a blank screen is the single most common way this trips people up, and once you have seen it once you will recognise it forever.

The pipe version is worse:

$ python3 file_descriptor.py | grep "stdout"
This is an error message!
nothing, again, and this time even after you type

Now the prompt went into the pipe, grep is holding on to it waiting to see whether more is coming, and the program is still reading from your keyboard because only slot 1 was redirected, not slot 0. Type a line, press Enter, and everything appears at once when the program exits.

Try it first In that last command, where does grep get its input, and where does the Python program get its input? They are different. Say which is which before opening this.

grep reads from the pipe. The Python program reads from the terminal, because | only rewires slot 1 of the left-hand command and slot 0 of the right-hand one. Nobody touched slot 0 of the Python program, so it still has the keyboard.

This is why the shell prompt does not come back and why typing seems to do nothing: you are typing into a program whose output you cannot see.

Both channels into one file, and a surprise

Send everything to a single file and read it back:

$ python3 file_descriptor.py > all_output.txt 2>&1 < /dev/null
$ cat all_output.txt
This is an error message!
Read from file (stdout): Hello, File Descriptors!
Enter something for stdin demonstration: Traceback (most recent call last):
...
EOFError: EOF when reading a line

The error message is first. In the program it is printed second. The lines came out in the wrong order.

This is the two-buffer problem from the previous section, caught in the act. Standard error is unbuffered, because an error you never see is useless, so it goes straight out. Standard output, once it is pointed at a file rather than a terminal, is held in the program's own buffer and not handed over until the buffer fills or the program exits. Both are correct. Together they scramble the order, and no amount of staring at the shell command will explain it, because the shell had nothing to do with it.

The < /dev/null on that command is how you tell a program that there is no input and never will be. It reads immediately as end of file, which is why the program crashed with EOFError instead of waiting. The crash is the point: it proves the program got to the input line.

Two honest problems with this script, which are worth seeing because you will write the same ones.

os.open was called without a permission argument. Python's default is 0o777, so after running this, ls -l sample.txt shows -rwxr-xr-x: a text file marked executable. Nothing breaks, and it is still wrong. The habit is to pass the mode you mean, 0o644 for an ordinary file.

There is also no O_TRUNC, so re-running writes over the beginning of the existing file rather than replacing it. Here the text is the same length every time so you never notice. Write something shorter one day and the tail of the old content will still be sitting there.

Joining streams, and throwing them away

2>&1, and why the order is not optional

Sometimes you do want both channels in one place. The spelling is 2>&1, and it reads as: make slot 2 a copy of whatever slot 1 is at this moment.

Those last three words are the whole thing. The shell processes redirections left to right, so these two commands, which look like the same command written in a different order, do different things:

$ sort nosuchfile.txt > f1.txt 2>&1
screen: nothing
f1.txt: sort: cannot read: nosuchfile.txt: No such file or directory

$ sort nosuchfile.txt 2>&1 > f2.txt
sort: cannot read: nosuchfile.txt: No such file or directory
f2.txt: empty

Walk the first one. Slot 1 is pointed at f1.txt. Then slot 2 is made a copy of slot 1, which is now f1.txt. Both end up in the file.

Walk the second. Slot 2 is made a copy of slot 1, which is still the terminal, because nothing has changed it yet. Then slot 1 is pointed at f2.txt. Slot 2 was copied from the old value and does not follow along afterwards. Errors go to the screen, output goes to the file.

The second is not a mistake; it is occasionally exactly what you want. But it is almost never what someone means when they type it, and the reason it catches people is that 2>&1 looks like it declares a permanent relationship between the two slots. It does not. It copies a value, once, at the moment it is read.

Try it first You want both output and errors appended to run.log, keeping what is already in the file. Write it. 
$ ./job.sh >> run.log 2>&1

Slot 1 first, positioned at the end of the file, then slot 2 copied from it. Bash also accepts &>> run.log as a shorthand for the same thing, which is easier to type and does not work in every shell. The long form is worth knowing because it is the one that always works and the one that tells you what is happening.

tee — a fork in the stream

Every pipe so far has moved bytes from one place to exactly one other place. tee is the exception: it reads its input and writes it to a file and passes it along, so you can watch something and record it at the same time.

$ grep "ERROR" logfile.txt | tee errors.txt | wc -l
2
$ cat errors.txt
2023-09-10 10:17:30 ERROR: Failed to connect to database
2023-09-10 10:20:05 ERROR: Invalid input received

The count came out, and the lines that produced it were saved on the way past. This is the tool for the moment when a long pipeline gives you an answer you do not believe and you want to see what went into the middle of it. tee -a appends instead of overwriting.

/dev/null — the bin

/dev/null is a file that discards everything written to it and is instantly empty when read. It is not a special shell feature; it is an ordinary path that behaves that way, which is a nice demonstration of the "everything is reached the same way" idea.

$ find / -name "*.conf" 2>/dev/null

Searching the whole filesystem produces hundreds of permission complaints that bury the results. Throwing slot 2 in the bin leaves the answers.

Use it deliberately. 2>/dev/null does not fix an error, it hides it, and a script that silences its own errors will fail silently at three in the morning and leave you nothing to read. Discard errors when you already know which ones you are discarding and why. Otherwise send them to a log.

Which one do I reach for?

The decision is almost always obvious once the question is phrased right: is the thing on the other end a program, or a place to keep bytes?

Redirection > < 2>Pipe |
Other endA file on diskAnother running program
TimingOne thing at a timeBoth at once, streaming
Leaves behindA file you can read laterNothing
Disk usedAll of the dataNone
Can go back and re-readYesNo
Has a nameYesNo
Good forKeeping results, saving logs, feeding a program a fixed inputComposing tools, filtering huge inputs, anything you do not want on disk

In practice they are not rivals, and almost every real command line uses both: pipes through the middle where the data is still being worked on, and one redirection at the end where the answer stops being traffic and starts being a result.

$ grep -v "DEBUG" logfile.txt | cut -d" " -f3 | sort | uniq -c | sort -rn > summary.txt 2> problems.txt

Five programs, all running at once, nothing touching the disk until the end, and then two files: one with the answer and one with anything that went wrong. You can now read that command left to right and say what each piece does and where each of the three streams of each program is attached. That is the whole subject.

One last one Why can the sort in the middle of that pipeline not print anything until cut has finished, while grep and cut print as they go?

Because sorting requires knowing all the input. The smallest line might be the last one to arrive, so sort has to hold everything until its input hits end of file, and only then can it produce the first line of its answer.

Tools split into these two families and it is worth noticing which is which. grep, cut, tee, head are streaming: one line in, one line out, constant memory, works on a file bigger than your RAM. sort, uniq -c on unsorted data, and wc must see the end before they can speak. Putting a streaming tool early and a blocking tool late is what makes a long pipeline fast.

Incidentally, sort on an input larger than memory does not give up. It writes temporary files to disk and merges them. The pipe saved you a temporary file, and sort quietly made some anyway, because that is the job.

Setting up in Codespaces

Open the repository in a Codespace and you get a full Linux machine in the browser with a terminal at the bottom. Everything on this page runs there unchanged.

To make the sample files, run the generator once:

$ python3 setup_generator.py
Created: hello.txt
Created: names.txt
Created: numbers.txt
Created: logfile.txt
Created: todo.txt

Five files: a two-line greeting, ten names in random order, twenty random numbers, the ten-line log from the top of this page, and a to-do list where some lines start with TODO and some do not. That last one is built for grep and grep -v.

The names file has a surprise in it that is worth doing on purpose:

$ cat names.txt
Frank
Alice
Ivy
Henry
Eva
David
Charlie
Grace
Jack
Bob
$ wc -l names.txt
9 names.txt

Ten names. Nine lines. This is the newline business from earlier, live: the generator joined the names with newlines between them and did not put one after the last, so there are nine newline characters and wc -l counts newline characters.

If you want the honest count, grep -c "" matches every line whether or not it ends in a newline:

$ grep -c "" names.txt
10

Two tools, two answers, both correct, answering slightly different questions. Before you trust a number from a command, it is worth asking which question it actually answered.
