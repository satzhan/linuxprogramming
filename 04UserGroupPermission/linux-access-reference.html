Linux / accounts and access

Who can do what?

A file belongs to a user and a group. Its permissions decide what other accounts can do with it. Most of this topic is learning to read those few pieces of information together.

Alex and Bob share a small Python project. We will use their accounts to explain users, groups, permissions, and administrative access. The separate lab.md walks through creating the setup and trying the commands.

01 / IDENTITYUsers & groupsWhich account is running the command? 02 / ACCESSPermissionsWhat is that account allowed to do? 03 / CREATIONUmaskWhich permissions start switched off? 04 / ADMINISTRATIONSudoMay this command run as another user?

Examples use Ubuntu, Bash, and ordinary Linux permissions. Expected outputs show the relevant fields; your IDs, dates, and error wording may differ. These reference examples are not a setup script—follow the lab for the full sequence.

01 / USERS & GROUPS

Start with the account.

When you type a command, Linux runs a process under an account. That account supplies the identity used for ordinary permission checks. It might be your login, a developer account, or an account used by a background service.

TermMeaningIn this example
User / UIDAn account and its numeric user ID.dev_alex, dev_bob
Group / GIDA named set of accounts and its numeric group ID.dev_team
Primary groupThe account's main group. In the lab, newly created files normally start with this group.Alex's private group: dev_alex
Supplementary groupAn additional membership used in access checks.Alex also belongs to dev_team.
Home directoryThe account's usual personal workspace./home/dev_alex
RootThe administrative account, UID 0, with broad privileges.root

A group is useful when several people need the same access. Give a project file to dev_team, set its group permissions, and manage who belongs to the team. Membership does not grant access to every file on the machine.

Read the identity first

whoami
id
id dev_bob
getent passwd dev_alex
getent group dev_team

whoami prints your effective account name. id shows the identity and groups of the current process. id dev_bob looks up Bob's account information instead. That distinction matters after changing a group.

getent asks the system's configured account databases for an entry. Local accounts are normally recorded in /etc/passwd and /etc/group; a system can also use other account sources.

Create an account, then add membership

Run from an authorized admin account
sudo groupadd dev_team
sudo useradd -m -U -s /bin/bash dev_alex
sudo usermod -aG dev_team dev_alex

-m creates the home directory, -U creates a matching private primary group, and -s selects the login shell. To set a password, use sudo passwd dev_alex.

Keep the -a in -aG. -G supplies a supplementary group list. By itself, it replaces the old list. Adding -a appends memberships and keeps the groups already there.

Switch account without losing your place

sudo -iu dev_alex
whoami
pwd
exit

sudo -iu dev_alex starts a login-style shell as Alex, using your current account's sudo authorization. exit returns to the shell you came from. Alternatively, su - dev_alex normally asks for Alex's password.

New membership, new session. An open Bob shell keeps the groups it started with. After an admin adds Bob to dev_team, leave that shell and start a fresh sudo -iu dev_bob session. Run id inside it to verify.

Reading an account record

A getent passwd dev_alex entry has seven colon-separated fields: username, password placeholder, UID, primary GID, comment, home directory, and login shell. The numbers vary by machine. The group list in /etc/group does not necessarily list users whose primary group it is; use id username to inspect membership.

For a course project: a group can collect the people who maintain a project. A separate service account can identify the program that runs it. People and programs both need an account under which their actions occur.

02 / PERMISSIONS

Read the file's access rules.

A file has one owning user, one owning group, and three sets of ordinary permissions: owner, group, and others. The same structure applies to directories, though the permission letters mean something different there.

ls -l hello.py
stat -c '%A %a %U %G %n' hello.py
Expected stat output for the lab file
-rwxr-x--- 750 dev_alex dev_team hello.py

Linux chooses one set

For these ordinary permission checks, Linux does not combine all three columns. It picks the applicable set, then checks whether that set allows the requested operation.

For example, if Alex owns a file with mode 040, Alex cannot read its contents through an ordinary read operation, even if Alex belongs to its group. The owner set is selected and has no read bit. Alex can still change the mode as the owner.

Files and directories are different

BitOn a regular fileOn a directory
r · readRead the file's contents.List the names stored in the directory.
w · writeChange the file's contents.Add, remove, or rename entries; normally also needs x.
x · execute / searchPermit direct execution as a program.Look up names and pass through the directory.

Think of a directory as a list of names pointing to files. Editing a file changes the file. Deleting it removes a name from that directory. Those are different operations on different objects.

A read-only file can still be deleted. In an ordinary directory, write and search permission on the containing directory can let you remove an entry even when you cannot modify the file's contents. The lab demonstrates this with a disposable copy.

Every directory on the path matters

To read /srv/access-lab/hello.py, Bob must reach the file first. A readable file behind a directory Bob cannot search is still inaccessible.

Use ls -ld /srv/access-lab to inspect the folder itself. Without -d, ls -l normally lists what is inside. A private home directory can block access to a file even after its group has been changed; that is why the lab uses a separate project folder.

Change the bits with chmod

Symbolic permissions name the affected class: u for owner, g for group, o for others, or a for all three. Here u means the file's owner, not whichever user happens to type the command.

chmod g+w hello.py           # add group write
chmod g-w hello.py           # remove group write
chmod u=rwx,g=rx,o= hello.py  # set all three classes
chmod 750 hello.py           # same ordinary bits

Each octal digit represents three switches. Read contributes 4, write 2, and execute 1. Add the enabled values within each class: r-x is 4 + 1 = 5.

Octal lookup · use one digit each for owner, group, and others
DigitPermissionsDigitPermissions
0---4r--
1--x5r-x
2-w-6rw-
3-wx7rwx

640 suits a file the owner may edit and the group may read. 750 suits a program the owner may edit and the group may run. 770 also lets the group edit it. Choose the access needed for the job; 777 gives every account all ordinary permissions.

Change ownership with chown or chgrp

chgrp dev_team hello.py
sudo chown dev_bob hello.py
sudo chown dev_alex:dev_team hello.py

The owner can normally change a file's group to a group they belong to. Transferring the owning user normally requires administrative privilege. chmod changes the permissions; chown and chgrp change who those permissions apply to.

Having write permission is not the same as owning the file. A group member may be able to edit its contents without being allowed to change its mode.

Two ways to run a Python script

The lab's file contains:

#!/usr/bin/env python3
print("Hello, dev_team!")

./hello.py

Linux is asked to execute the script. It needs execute permission and a usable interpreter line. Python also needs to read this script.

python3 hello.py

Linux executes Python. Python reads the script as input. The script needs read permission; its own execute bit is not required.

With mode 640, Alex can use the second form but cannot use the first. Adding x changes direct execution; it does not create a separate barrier against someone who can read and interpret the source.

What these examples leave out

The reference uses ordinary permission bits and ordinary users. Additional access control lists, special mode bits, mount settings, and security policies can affect real systems. Root can bypass many ordinary checks, so testing as root does not tell you what Bob can do. The lab tests with Bob's identity.

For a course project: separate the right to run a program from the right to edit it. Check the project directory as well as the file. A readable configuration file is still private if only the intended account can reach and read it.

03 / UMASK

Choose the starting permissions.

chmod changes a file that already exists. A umask blocks selected permission bits when a process creates something new. Read it as “leave these permissions switched off.”

For a newly created regular file, tools such as touch normally request 666, or rw-rw-rw-. A plain mkdir normally requests 777. The mask removes bits from that request. Programs can request less access; a mask cannot add what they did not request.

umask          # show this shell's current mask
umask 027      # change it in this shell
touch notes.txt
mkdir notes

With fresh names, those last two commands normally produce a 640 file and a 750 directory.

MaskNew fileNew directoryTypical effect
002664775Keep group write; block others' write.
022644755Only owner keeps write.
027640750Group can read; others get no access.
077600700Owner-only starting access.
033644744Remove group/others write and execute.

Do not subtract the numbers. With 033, a new file is 644, not 633. The mask removes named bits; removing a bit that is already off leaves it off.

The number also is not a simple “more private” scale. Mask 003 blocks others' write and execute but leaves their read bit. Mask 004 blocks read but leaves write. Look at which bits each digit represents.

It belongs to the process

Bash's umask command changes the current shell's setting. Programs started by that shell inherit it. Another terminal that is already open keeps its own setting. A new login may load a mask from the system or shell's startup configuration.

Changing the mask does not alter existing files. Running touch on an existing file updates its timestamps; it does not apply the new mask. Use a fresh filename when experimenting, or use chmod to change an old file.

If the shell prints 0027, it means the same mask as 027. The leading zero is octal formatting here; it is not a fourth mask that controls special permissions.

The bitwise version

The rule is requested_mode & ~mask, considering the nine ordinary permission bits. Invert the mask to mark the bits that may remain, then keep only bits present in both that inverted mask and the request.

StepOwnerGroupOthers
Request 666110110110
Mask 027000010111
Inverted mask111101000
AND result 640110100000

The examples assume no inherited default access control list. Default ACLs can change the creation rules; they are outside this lab.

For a course project: a script that creates private configuration files can start with umask 077. That protects ordinary new files from group and other access. It still needs to run under the intended account and use an appropriate directory.

04 / SUDO

Run a command with another identity.

sudo checks policy and, if permitted, runs a command as another account. The usual default target is root. It does not mean “ignore any error,” and it does not permanently change the account in your current shell.

The Ubuntu sudo group

Run from an existing authorized admin account
sudo useradd -m -U -s /bin/bash newuser
sudo passwd newuser
sudo usermod -aG sudo newuser
sudo -l -U newuser

On a standard Ubuntu setup, policy authorizes members of the sudo group. A rule commonly looks like this:

%sudo ALL=(ALL:ALL) ALL

%sudo selects the group. The rule grants its members broad permission to run commands as other users and groups. A group with that name has no special power by itself; the policy grants the power.

Open a fresh Newuser session after adding membership. Run sudo whoami there to check the result. If it asks for a password, standard sudo policy asks for newuser's password, not root's. Some environments use cached authentication or passwordless rules.

CommandWhat it does
sudo -lList what your current account may run.
sudo -l -U newuserAs an authorized administrator, inspect another account's sudo privileges.
sudo -kInvalidate cached authentication for the current session context; the next sudo use follows the policy's authentication requirements.
sudo -u dev_bob commandRun one command as Bob, useful for testing Bob's access.
sudo -iu dev_bobStart a login-style shell as Bob.
sudo visudo -cCheck sudoers configuration syntax without editing it.

For an authorized policy change, use sudo visudo; it checks syntax when saving. The practice lab uses Ubuntu's existing group policy and requires no sudoers edits.

Removing access

sudo gpasswd -d newuser sudo

This removes the membership from the account database. Leave the old Newuser shell, open a new one, and test again. Removing a group does not terminate old shells or commands that are already running, and another sudo rule could still grant access.

Login records and shell history

last -n 5 reads recorded login events. A container may have no login records or may omit the command. Bash's history 10 shows recent entries in the current shell; ~/.bash_history is saved history and can lag behind an active session.

An authorized administrator can often read another user's saved history with a command such as sudo cat /home/dev_alex/.bash_history. Read someone else's history only for an authorized purpose. History can be incomplete, changed, or contain secrets; it is not a complete audit trail.

For a course project: installing system packages or creating accounts may require sudo. Editing a project file that you own usually does not. Run each command under the account whose access you intend to use.

Delete practice accounts only after their shells have exited and their work is no longer needed. userdel without -r normally leaves the home directory; -r removes it and the mail spool, but does not remove every file the account may own elsewhere.

When access fails: check the account, check its active groups, check the file's owner and mode, then check every directory on the path. Change the part that explains the failure.
