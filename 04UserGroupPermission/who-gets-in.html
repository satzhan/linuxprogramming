Who gets in

Users, groups, permissions, umask and sudo on Linux. A reference to read, come back to, and keep open in another tab while you work through the lab.

-a regular file
rwxowner dev_alex: read, write, run
r-xgroup dev_team: read, run
---everyone else: nothing

Those ten characters start every line that ls -l prints, and most of this page is about reading them. Who counts as the owner, who counts as the group, who is left over as everyone else. Then two shorter topics: umask, which decides what the letters look like on a brand-new file, and sudo, which lets a trusted person step past all of it for one command.

A Linux machine is a shared apartment building. Lots of people and programs live there at the same time, every door has a lock, and the building needs a rule for who holds which key. Everything below is that rule, in detail.

1Users and groups

A user is a number wearing a name tag

You see dev_alex. The kernel sees 1001. Every running program carries a user ID, every file records one as its owner, and nearly every "may I?" question on the system gets answered by comparing those numbers. The names are there for humans. The system works more like a coat check: it has no interest in who you are, only in the number on your ticket.

One number is special. root is user 0, and the permission checks mostly wave it through without looking. That's the reason nobody works as root day to day. A typo made as root doesn't get stopped by anything.

Groups, and why everyone gets one of their own

A group is a named list of users. It lets you open a door for a whole team at once instead of person by person, and it's where the middle triplet in -rwxr-x--- gets its meaning.

Every user has exactly one primary group and any number of supplementary ones. On Ubuntu, creating a user quietly creates a primary group with the same name, with that user as the only member. A club with one member sounds pointless until you notice what it protects. New files belong to their creator's primary group, so if that group is just you, nobody picks up group access to your files by accident.

Joining dev_team leaves alex's primary group alone. Files he creates still come out belonging to the group dev_alex, and handing them to the team is a separate step (section 2 shows how).

Where the system writes it down

In two plain text files that anyone can read. Each line of /etc/passwd is one account:

dev_alexname
: 
xpassword lives elsewhere
: 
1001user ID
: 
1003primary group ID
::empty comment field
/home/dev_alexhome directory
: 
/bin/bashlogin shell

That x is a leftover. Passwords, scrambled, used to sit right there. But /etc/passwd has to be readable by everyone (it's how ls -l turns 1001 back into dev_alex), so the scrambled passwords moved to /etc/shadow, which only root can read. The scrambling only goes one way. When you log in, the system scrambles what you typed the same way and compares the results.

/etc/group works the same way, with four fields:

dev_teamgroup name
:x:unused password field
1002group ID
: 
dev_alex,dev_bobsupplementary members

A user's primary group doesn't appear in that member list; it comes from the fourth field of their passwd line. So the line dev_alex:x:1003:, with nothing after the last colon, is not an empty group. alex is in it.

$ getent passwd dev_alex dev_alex:x:1001:1003::/home/dev_alex:/bin/bash $ getent group dev_team dev_team:x:1002:dev_alex,dev_bob

grep dev_team /etc/group would print the same line here. getent asks the system's account lookup instead of reading the file directly, which matters on machines that also pull accounts from a network directory, like many university systems.

Making and changing accounts

$ sudo groupadd dev_team $ sudo useradd -m -s /bin/bash dev_alex $ sudo passwd dev_alex New password: Retype new password: passwd: password updated successfully $ sudo usermod -aG dev_team dev_alex $ id dev_alex uid=1001(dev_alex) gid=1003(dev_alex) groups=1003(dev_alex),1002(dev_team)

On useradd, -m makes the home directory and -s /bin/bash sets the login shell. Leave -s off and Ubuntu gives the account /bin/sh. Everything still works, but there's no tab completion and no arrow-key history, and typing in it feels like typing in oven mitts.

Passwords don't echo. Not a letter, not a dot. That's normal.

Ubuntu and Debian also ship adduser, a friendlier wrapper that asks a few questions and does everything above in one go, bash included. useradd is the one you'll find on every distribution, which is why the lab uses it.

The one-letter difference in usermod

In usermod -aG, the -G names supplementary groups and the -a means append. Drop the -a and -G replaces the whole list with whatever you typed. You meant to add a name to the guest list and instead you tore it up and wrote one name on a fresh sheet.

$ sudo usermod -G scratch dev_alex $ id dev_alex uid=1001(dev_alex) gid=1003(dev_alex) groups=1003(dev_alex),1004(scratch)

dev_team is gone. sudo gpasswd -a dev_alex dev_team does the same job as usermod -aG and has no replace mode to fall into, which is a point in its favour.

Group changes wait for the next login

Your groups are looked up once, when you log in, and every program you start after that inherits the list. Add dev_bob to a group while he's logged in and his current shell carries on without it. It works the other way too, which surprises people more: take him out of a group and the session he already has open keeps the access until he logs out.

Two commands can seem to disagree about this. id dev_bob, with a name, reads the account files and shows the change straight away. Plain id, typed inside bob's old shell, shows the list that shell is actually carrying, and that's the list file access uses.

Becoming someone else

$ su - dev_alex Password: $ whoami dev_alex $ exit logout

su asks for the target user's password, not yours. The dash matters. It gives you a real login as that user, starting in their home directory with their settings. Without the dash you become them but keep standing in your old directory with your old environment, which gets confusing quickly.

Each su opens a new shell on top of the one you were in, and exit closes one. Go from your own account into alex and from alex into bob, and it takes two exits to get home. whoami always tells you where you are, and on most setups the prompt does too (dev_alex@...).

If you have sudo rights, sudo -iu dev_alex gets you the same login without knowing alex's password. It asks for yours instead, if it asks at all.

Removing accounts

$ sudo userdel -r dev_alex userdel: dev_alex mail spool (/var/mail/dev_alex) not found $ sudo groupdel dev_team

-r removes the home directory too. Without it the account disappears and its files stay behind, owned by a number nobody answers to anymore. In ls -l you'd see 1001 where the name used to be.

The mail spool line is harmless: userdel tried to tidy a mailbox that never existed. A message like user dev_alex is currently used by process 586 is different. Something is still running as alex, usually a su session you forgot to exit. And a group can't be deleted while it's still someone's primary group.

2Permissions and ownership

Reading one line of ls -l

Every file and every directory records one owner and one group. ls -l shows both, together with the permission string:

-rwxrwx---type and permissions
1links
dev_alexowner
dev_teamgroup
49size in bytes
Sep 23 16:33last modified
hello.pyname

The first character is the type: - for a regular file, d for a directory, l for a symbolic link. After it come three groups of three. Each slot holds either its letter or a dash, and the order never changes: r, then w, then x. The first three belong to the owner, the next three to members of the file's group, the last three to everyone else.

stat says the same thing at greater length, and shows the permissions both ways at once:

$ stat hello.py File: hello.py Size: 49 Blocks: 8 IO Block: 4096 regular file Device: 254,0 Inode: 573515 Links: 1 Access: (0770/-rwxrwx---) Uid: ( 1001/dev_alex) Gid: ( 1002/dev_team) (a few timestamp lines follow)

Exactly one triplet applies to you

When you try to use a file, Linux picks one of the three triplets and ignores the other two. It asks its questions in a fixed order and stops at the first yes.

No adding up, no best of three. That has a strange consequence. If dev_alex sets his own file to ----rwx---, the group can read it and alex can't, even though he is a member of the group. The check found him as the owner and never looked any further.

$ chmod 070 hello.py $ ls -l hello.py ----rwx--- 1 dev_alex dev_team 49 Sep 23 16:33 hello.py $ cat hello.py cat: hello.py: Permission denied

He isn't locked out for good. The right to change a file's permissions doesn't come from the bits at all; the owner can always chmod their own file, so chmod 770 hello.py puts it back.

root skips the read and write checks entirely. To run a file as a program, though, even root needs at least one x to be set on it somewhere.

What r, w and x mean

On a file the letters mean what you'd guess. On a directory they mean something different, and it helps to stop picturing a directory as a box with files inside. A directory is a list of names, like one page of a phone book, and each entry points at a file stored somewhere else on the disk. With that picture:

on a fileon a directory
rread what's in itread the list of names (ls works)
wchange what's in itchange the list: create, delete and rename entries (needs x as well)
xrun it as a programgo through it: cd into it, reach anything inside by name

Deleting is a change to the directory

Removing a file means erasing its name from the directory's list. That's an edit to the directory, so the directory's w and x decide, and the file's own bits don't get a vote. A read-only file sitting in a folder you can write to is a file you can delete. Here dev_bob, a member of dev_team, is in a folder where dev_team has rwx:

$ ls -l notes.txt -r--r--r-- 1 dev_alex dev_alex 23 Sep 23 16:33 notes.txt $ rm notes.txt rm: remove write-protected regular file 'notes.txt'? y $ ls hello.py

That question is rm being polite, not the system objecting; rm -f skips it. Shared folders deal with this using the sticky bit, the t at the end of drwxrwxrwt on /tmp. In a sticky directory you can only delete files you own (the directory's owner can still delete anything). After sudo chmod +t on the folder, the same attempt gets:

$ rm -f notes.txt rm: cannot remove 'notes.txt': Operation not permitted

Every door along the hallway

Before the file's own bits even come up, you have to reach it. Opening /srv/devteam/hello.py needs x on /, on /srv and on /srv/devteam, in that order, and only then r on the file. One locked door anywhere along the hallway and it doesn't matter how wide open the last room is.

This is why other users can't read anything in your home directory on recent Ubuntu, whatever the files inside say. New home directories are created as drwxr-x---. Everyone else gets no x, so they stop at the front door:

$ ls -ld /home/dev_alex drwxr-x--- 2 dev_alex dev_alex 4096 Sep 23 16:33 /home/dev_alex # meanwhile, logged in as dev_bob: $ ls /home/dev_alex ls: cannot open directory '/home/dev_alex': Permission denied

Older releases made home directories drwxr-xr-x, so check yours rather than assume. Notice the group on that home directory, too: it's dev_alex, not dev_team. Joining the team wouldn't help bob get in. For files a team shares, the usual answer is a folder outside anyone's home, like the lab's /srv/devteam. (/srv is the traditional place for data a machine serves.)

Reading a script is not running it

python3 hello.py doesn't run hello.py. It runs python3, and python3 opens hello.py and reads it like any text file, so it needs r and nothing else. The x bit only matters when you run the file itself, as ./hello.py. For that, the first line of the file has to say which interpreter should handle it:

#!/usr/bin/env python3 print("Hello, dev_team!")
$ chmod 660 hello.py $ python3 hello.py Hello, dev_team! $ ./hello.py -bash: ./hello.py: Permission denied

Changing permissions with chmod

There are two ways to say the same thing. The symbolic way names who (u owner, g group, o others, a all three), then an operation (+ add, - remove, = set exactly), then the letters.

$ chmod u+x hello.py # owner may run it $ chmod g+w hello.py # group may edit it $ chmod o-r hello.py # others may no longer read it $ chmod u=rwx,g=rx,o= hello.py # exactly rwxr-x---

The numeric way gives each letter a value: r is 4, w is 2, x is 1. Add them up for each triplet and write the three sums side by side. It's like paying with coins worth 4, 2 and 1. Every amount from 0 to 7 can be paid in exactly one way, so every digit decodes to exactly one set of letters.

digit01234567
letters-----x-w--wxr--r-xrw-rwx

So 750 reads as 7 for the owner (rwx), 5 for the group (r-x), 0 for everyone else (---). A handful of modes cover most real situations:

modelooks liketypical use
644rw-r--r--ordinary files: you edit, others read
600rw-------private files, SSH keys
640rw-r-----config a team needs to read
755rwxr-xr-xprograms, ordinary directories
750rwxr-x---team can read and run, others can't
770rwxrwx---team can do everything, others nothing
700rwx------private directories

chmod -R applies a change to a directory and everything under it. Handy, and also the classic way to make a thousand text files executable when you only meant the folders. A capital X helps: it means "x, but only on directories and on files that already had an x somewhere," which is usually what you wanted. chmod -R g+rX shared/ lets the group into every folder and read every file, without turning notes into programs.

Changing the owner and the group

$ chgrp dev_team hello.py # group only $ chown :dev_team hello.py # same thing $ sudo chown dev_bob hello.py # new owner $ sudo chown dev_bob:dev_team hello.py # both at once

The rules are lopsided on purpose. Only root can give a file to a different owner; otherwise you could plant a file that looks like someone else wrote it, or fill their disk quota with your junk. The owner can change the file's group, as long as it's a group they belong to. That's why dev_alex can run chgrp dev_team hello.py with no sudo at all.

The occasional s or t

Now and then you'll see an s or t where an x would normally be. These are the special bits. In numeric form they're the extra leading digit in modes like 2770 or 1777.

you seecalledwhat it does
s in the owner triplet of a programsetuidThe program runs as its owner instead of as you. /usr/bin/passwd is -rwsr-xr-x root, which is how you can update the root-only /etc/shadow, but only through that one program.
s in the group triplet of a directorysetgidNew files inside get the directory's group instead of their creator's primary group. Team folders love this: no more chgrp after every new file.
t at the end, on a directorystickyYou can delete only your own files inside. /tmp has it.

A capital S or T means the special bit is set but the x underneath it isn't, which is rarely what anyone intended.

3umask: what new files start with

When a program creates a file, it asks the kernel for a set of permissions. Most programs ask for 666 on files (read and write for everyone) and 777 on directories. Nobody really wants every new file writable by the whole building, so before the request is granted, the kernel strikes out every bit listed in your umask.

The name is literal. It's a mask. Picture painter's tape stuck over some of the nine permission slots: tape keeps paint off, and it can't add any. That also explains why new files never come out executable. The program didn't ask for x, and umask has no way to put one there.

rwxrwxrwx
a new file asks for 110110110 666 rw-rw-rw-
umask 022 tapes over 022
what you get 110100100 644 rw-r--r--

Directories go under the same tape. 777 with 022 masked off becomes 755, which is drwxr-xr-x.

Why subtraction gives the wrong answer (sometimes)

666 minus 022 happens to be 644, so it's tempting to treat umask as subtraction. Try 033. Subtraction predicts 633, which would be rw--wx-wx: a file others can write to but not read. What you actually get is 644.

rwxrwxrwx
a new file asks for 110110110 666 rw-rw-rw-
umask 033 tapes over 033
what you get 110100100 644 rw-r--r--
what 666 − 033 would say 110011011 633 rw--wx-wx

033 says "no w and no x" for the group and for others. There was never an x in the request, so that part of the tape lands on bare wall and does nothing. Subtraction goes wrong because it lets the missing x borrow from the bits next to it, and tape never borrows. Written as a rule: result = request AND NOT umask.

Subtraction gives the right answer exactly when every bit in the mask was requested in the first place. Directories ask for everything (777), so for them it always works, and 777 − 033 really is 744. Files never ask for x, so any mask containing an x can trip it up.

Common values

umasknew filenew directorysuits
022rw-r--r-- 644rwxr-xr-x 755the usual default; others can read
002rw-rw-r-- 664rwxrwxr-x 775people who share work through a group
027rw-r----- 640rwxr-x--- 750group reads, others get nothing
007rw-rw---- 660rwxrwx--- 770group gets everything, others nothing
077rw------- 600rwx------ 700private
033rw-r--r-- 644rwxr--r-- 744nobody; others can list that directory but can't enter it

Reading it and setting it

$ umask 0022 $ umask -S u=rwx,g=rx,o=rx $ umask 027 $ touch report.txt $ ls -l report.txt -rw-r----- 1 dev_alex dev_alex 0 Sep 23 16:33 report.txt

The leading 0 is the slot for the special bits and is almost always 0. umask -S shows the opposite view: which letters are still allowed through, rather than which are taped over.

A umask you type lasts only for that shell and the programs started from it; close the terminal and you're back to the default. It shapes files created afterwards and never touches existing ones (that's chmod's job). To make a value permanent for your account, add a line like umask 027 to the end of ~/.bashrc. New shells will pick it up.

The default comes from /etc/login.defs (UMASK 022 on Ubuntu) and is applied when you log in. Ubuntu can hand some accounts 002 instead, depending on how their private group is set up, so seeing 0022 on one machine and 0002 on another is normal.

4sudo: root's keys, one command at a time

su and sudo both let you act as someone else. They're built on different ideas, though.

su - newuser asks for newuser's password and hands you a whole shell as them. It's like being given someone's house keys. You're in for as long as you like, and nobody asks what you did in there.

sudo command runs one command as root. It asks for your own password, checks your name against the rules in /etc/sudoers, and if you're allowed, runs the command and writes it in a log. Think of a building manager with a clipboard: you show your own ID, the manager finds you on the list, unlocks the one door you asked for, and notes that you went through it.

su - someonesudo command
whose passwordtheirsyours
what you geta whole shell as themone command as root
who decidesanyone who knows the passwordthe rules in /etc/sudoers
what's loggedthat the session startedevery command

That's why sudo won on most systems. Nobody has to share root's password, access can be given to one person and taken back from one person, and the log says who did what.

The line that grants it

%sudowho: % means a group, here "sudo"
ALLon any machine
= 
(ALL:ALL)as any user : any group
ALLany command

Ubuntu ships that line already, so on Ubuntu joining the sudo group is all it takes. Fedora, RHEL and their relatives use a group called wheel for the same job.

$ sudo usermod -aG sudo newuser $ groups newuser newuser : newuser sudo

Other ways to grant or take it: sudo gpasswd -a newuser sudo, sudo gpasswd -d newuser sudo, and on Ubuntu or Debian sudo adduser newuser sudo. Like any group change, it counts from the next login.

What you'll see

Before newuser is on the list:

$ sudo ls -la /root [sudo] password for newuser: newuser is not in the sudoers file.

Older versions of sudo add "This incident will be reported." The wording changed; the answer didn't. After joining the group and logging in again:

$ sudo ls -la /root [sudo] password for newuser: total 24 drwx------ 4 root root 4096 Apr 18 18:13 . drwxr-xr-x 22 root root 4096 Sep 23 16:32 .. -rw-r--r-- 1 root root 3106 Apr 22 2024 .bashrc drwxr-xr-x 4 root root 4096 Apr 18 18:10 .config -rw-r--r-- 1 root root 161 Apr 22 2024 .profile drwx------ 2 root root 4096 Apr 18 18:08 .ssh $ sudo -l Matching Defaults entries for newuser on vm: env_reset, mail_badpass, secure_path=..., use_pty User newuser may run the following commands on vm: (ALL : ALL) ALL

A plain sudo ls /root often prints nothing at all. That's not a failure. Root's home usually holds only hidden files, and ls hides those unless you add -a.

After one correct password, sudo trusts you for a while (15 minutes by default) and doesn't ask again. sudo -k makes it forget right away.

Looking at the rules, and changing them

Read the file with sudo cat /etc/sudoers. To change it, use sudo visudo and nothing else. visudo checks the syntax before it saves. A typo saved straight into /etc/sudoers can break sudo for everyone, you included, and then you need root to repair the file that gives you root.

Most systems also read every file in /etc/sudoers.d/ (the @includedir line near the bottom of sudoers does that), so a rule for one person can live in a small file of its own: sudo visudo -f /etc/sudoers.d/newuser. Easy to add, easy to delete.

commanddoes
sudo -llists what you're allowed to run
sudo -iopens a root shell; use sparingly, it's su with better paperwork
sudo -iu dev_alexa login shell as dev_alex, using your password rather than his
sudo -kforgets the remembered password now

On a full Ubuntu install the log lives in /var/log/auth.log, and journalctl shows the same entries. Containers, including many cloud development environments, often don't keep one.
