Before we start

A server is a program waiting for requests. A client is a program making one. These are jobs: your VM can do either job, or both. HTTP is a set of rules clients and servers use to request and deliver resources, such as files.

Think of an address on an envelope. The IP address identifies the machine. The port identifies the service on that machine. The file path says what you want from that service.

Alice · servesCreates a note and runs the server.

Bob · downloadsGets the note from a different VM.

Mallory · comparesWatches, predicts, then asks for her own copy.

In a pair, Bob also plays Mallory. Take turns at the keyboard and explaining results. Use only your group's machines and made-up notes.

Which terminal? Use your usual SSH connection to open each person's own VM. Run the commands below inside those VM sessions. A terminal on your laptop and a terminal logged into a VM are different places. Refer to the earlier Host/Guest team lab if you need help connecting; this activity creates no new accounts.
Start here · about 8 minutes

Step 0 — Testing cross-VM operation check

We will check the connection by sending the actual note. Success means Bob receives Alice's words on a different VM.

A Alice: make something to share

Alice · inside her own VM
mkdir -p ~/lab00-share
cd ~/lab00-share
echo "Meet our group by the blue door." > note.txt
mkdir -p
Makes a folder, or keeps it if it already exists. ~ means your home folder.
cd
Moves your shell into that folder.
echo … > note.txt
Writes the quoted words into a file. > replaces the file's previous contents. Change the words to a short note your group will recognize.

Keep only practice files in this folder. The next command makes its readable contents available to anyone who can reach the server.

B Alice: find your address and start the server

Alice · same terminal, in ~/lab00-share
hostname -I
python3 -m http.server 8000 --bind 0.0.0.0

hostname -I prints your VM's addresses; the I is uppercase. Share the private IPv4 address on its Azure network, often beginning with 10.. If several addresses appear, ask the instructor which belongs to the lab network.

python3 -m http.server
Runs Python's built-in file-serving module from this folder.
8000
The port where this server waits. We choose 8000; HTTP can use other ports.
--bind 0.0.0.0
Listens on all of this VM's IPv4 interfaces. It does not change Azure or Ubuntu firewall rules. Clients use Alice's actual IP, never 0.0.0.0.

Leave this terminal running. It is busy serving files, so the usual prompt disappears. A second SSH terminal to Alice's VM lets Alice run other commands.

Enter it to fill the commands below, or replace ALICE_IP yourself.
http://protocol · how we ask
ALICE_IPaddress · which machine
:8000port · which service
/note.txtpath · which file

C Bob: collect the note

Bob · inside his own VM
mkdir -p ~/lab00-downloads
cd ~/lab00-downloads
wget http://ALICE_IP:8000/note.txt
cat note.txt

wget requests the file and saves a local copy, normally under its original name. cat prints that local file. Alice should see a request with status 200 in her server terminal: the server answered successfully. If you repeat the download and wget saves note.txt.1, use cat note.txt.1 to read that new copy.

Pause together. Can Bob read Alice's distinctive note? Can Alice see Bob's request? Record who served, who downloaded, and the address used. This is your cross-VM check.
If it does not work

Stop a waiting command with Ctrl + C. Record the exact message before changing anything.

What you seeWhat it suggestsCheck first
Connection refusedThe connection was rejected; often nothing is listening there.Is Alice's server still running on that address and port?
Timeout / keeps waitingNo answer arrived. It does not tell us why.Both VMs running? Correct private IP? Ask the instructor to check network/firewall rules.
404 File not foundAn HTTP server answered, but could not find that path.File spelling and the folder Alice started the server from.

Command not foundThe named tool is missing.Ask the instructor; do not spend the activity installing tools.

127.0.0.1 points back to whichever machine runs the command. On Bob's VM it means Bob, not Alice. Also, the public address used for Azure SSH is a different route; adding :8000 to it does not publish your HTTP server.

Compare · about 4 minutes

1. Same note, different tool

Bob has used wget. Now try curl from the same VM, asking for exactly the same URL.

Bob · same terminal
curl http://ALICE_IP:8000/note.txt
curl -o note-curl.txt http://ALICE_IP:8000/note.txt
cat note-curl.txt

curl normally prints the response body in the terminal. The second command uses lowercase -o to save it in note-curl.txt instead. Neither command changes Alice's file.

Can wget choose the output name too?
Bob · same terminal
wget -O note-wget.txt http://ALICE_IP:8000/note.txt

Yes: uppercase -O chooses the output file. Here it replaces note-wget.txt if that file exists. Without -O, a repeated ordinary download will usually create note.txt.1, then note.txt.2. Check which copy you are reading after Alice edits her note.

Explain it to Alice. Where did each command put the downloaded bytes? Did switching from wget to curl change the machine, the port, or the protocol?

Both tools are HTTP clients in this experiment. Switching tools does not encrypt the transfer; these URLs still begin with http://.

Choose one · about 7 minutes

2. Change one thing

Choose one experiment together. Before running it, each person makes a prediction. Let someone who has typed less run this part. Afterwards, each person explains the difference in their own words.

AChange the addressWhat does “this machine” mean?

Alice keeps the server running. Open a second SSH terminal to Alice's VM, then run:

Alice · second terminal to her VM
curl --max-time 5 http://127.0.0.1:8000/note.txt

Now Bob runs the exact same command on Bob's VM:

Bob · on his VM
curl --max-time 5 http://127.0.0.1:8000/note.txt

127.0.0.1 is the loopback address: it sends the request back into the machine making it. Alice should get her note. Bob is asking Bob's own VM; if he has no server there, the connection should fail. --max-time 5 limits the request to five seconds.

Bob now repeats his request using Alice's private IP:

Bob · on his VM
curl --max-time 5 http://ALICE_IP:8000/note.txt
Explain: Why can the same command succeed on one VM and fail on the other? Why does Alice's successful loopback request tell us nothing about Bob's access?
One extra twist: listen only to yourself

Alice presses Ctrl + C in the server terminal, then restarts it there:

Alice · original server terminal
python3 -m http.server 8000 --bind 127.0.0.1

Repeat Alice's loopback request and Bob's private-IP request. The server now accepts connections only through Alice's loopback interface. Afterwards, stop it and restore the original server:

Alice · original server terminal
python3 -m http.server 8000 --bind 0.0.0.0

What changed: the client's destination, or the addresses the server listens on?

BChange the portSame machine. Different service address.

Alice stops her server with Ctrl + C and restarts it in the same folder on port 8001:

Alice · original server terminal
python3 -m http.server 8001 --bind 0.0.0.0

Bob tries the old port, then the new one:

Bob · on his VM
curl --max-time 5 http://ALICE_IP:8000/note.txt
curl --max-time 5 http://ALICE_IP:8001/note.txt

The file and VM have not moved. The listening port has. The old request should fail if nothing else is listening on 8000. The new request should work if the network permits 8001. A timeout alone is not proof that the server is stopped.

Explain: What did Bob have to change? Does using port 8001 make this transfer encrypted?

Alice stops the server and restores port 8000 before the next part:

Alice · original server terminal
python3 -m http.server 8000 --bind 0.0.0.0
CUse SSH to copy the fileFor teams whose earlier Host/Guest setup is ready.

scp copies files through an encrypted SSH connection. It uses an account on the receiving or serving machine. Use an authorized Guest account from the earlier team lab; no new accounts are needed here.

Alice puts a copy in the earlier lab's shared folder so that the Guest account can read it:

Alice · second terminal to her VM
cp ~/lab00-share/note.txt /srv/team/lab00-note.txt
chmod a+r /srv/team/lab00-note.txt

cp copies the file. chmod a+r adds read permission for all local users to this practice copy. The existing shared-folder permissions must also allow the Guest to enter /srv/team.

On Bob's VM, replace GUEST_USER with Bob's authorized account name on Alice's VM:

Bob · in ~/lab00-downloads on his VM
scp GUEST_USER@ALICE_IP:/srv/team/lab00-note.txt note-scp.txt
cat note-scp.txt

The left side names the remote account, machine, and file. The final name is Bob's local destination. This uses SSH's usual private-network port, 22, independently of the Python server on 8000. A key may authenticate you without a password prompt. Follow the earlier lab's host-key verification step if SSH asks about an unfamiliar machine.

Explain: Which method required an account? Which encrypted the connection? Could scp still work after Alice stopped her Python server? Try stopping it, then repeat the copy.

SSH protects the transfer between its endpoints. Alice's source and Bob's downloaded text file are still readable on their respective machines.

How does the Azure public SSH address fit in?

Your usual Azure connection may use a public host and an assigned SSH port. That port is forwarded to SSH on the chosen VM. To use that route with scp, the port flag is uppercase -P:

Optional · using the public SSH connection details
scp -P AZURE_SSH_PORT GUEST_USER@AZURE_SSH_HOST:/srv/team/lab00-note.txt note-public.txt

Replace all three uppercase placeholders using Alice's actual connection details and your authorized Guest account. This is optional; it can be run from your laptop's terminal using its existing SSH access. Private-IP access from Bob's VM uses a different route. Neither route exposes Python's port 8000 to the public internet.

Restart Alice's HTTP server for the next part if you stopped it:

Alice · original server terminal, in ~/lab00-share
python3 -m http.server 8000 --bind 0.0.0.0
Ask one more person · about 3 minutes

3. Was the note only for Bob?

Alice's server should be back on port 8000. Mallory uses her own VM to ask for the same note. In a pair, Bob makes this second request while playing Mallory.

Mallory · on her VM; Bob in a pair
curl http://ALICE_IP:8000/note.txt

Mallory has not guessed a password or intercepted somebody else's connection. She asked the server for a file. This simple server does not authenticate downloaders, so anyone who can reach it can request its readable files.

Discuss: Alice said “this note is for Bob.” Where, in the commands we used, did she enforce that rule?

Access control decides who may obtain something. Encryption makes the contents unreadable without the right key. Those solve different problems. Adding encryption to a connection would not, by itself, tell a server to refuse Mallory.

This exercise demonstrates an open download, not passive eavesdropping. Successful HTTP delivery alone does not show who else can observe network traffic.

Explain · about 5 minutes

One logbook, everybody's explanation

One person records. Each person explains at least one comparison aloud, and the others ask a question. A few sentences and a useful command or result are enough.

Notes stay in this browser when storage is available. Download your logbook before leaving.

Finish

Alice presses Ctrl + C in the server terminal. Keep your tiny practice files if you want to revisit them; no cleanup script is needed. If you tried SCP, Alice can remove the shared practice copy with rm /srv/team/lab00-note.txt after the group finishes.
