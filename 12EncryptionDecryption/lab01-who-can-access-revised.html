Linux together / Lab 01

Who can read it?

A file is marked private. Someone downloads it anyway. Did Linux forget its own rules? Not quite. We put the lock on one door. The visitor came through another.

~55–70 minutesThree students · three VMsEveryone rotates roles

You will make files, lock them, move them, rename them, and watch which requests get through. Every command has a job. No worksheet, no long report. Just three terminals doing things to one another.

You need three Ubuntu virtual machines that can already reach one another using private IP addresses. Everyone uses their own machine. When we say “on B”, we mean the SSH terminal logged into B’s VM, not somebody’s laptop.

On each student’s computer, if you are not connected to your VM yet
ssh -p SSH_PORT YOUR_USER@AZURE_SSH_HOST

Use the SSH host, port, and username assigned to your VM. If you are already at your VM shell prompt, stay there. Open two SSH terminals per person: one can keep a server running, the other is for typing commands.

Everyone · inside their own VM · working terminal
whoami
hostname -I
mkdir -p "$HOME/lab01/served" "$HOME/lab01/locked" "$HOME/lab01/received"
ls -ld "$HOME/lab01" "$HOME/lab01/served"

The output of whoami tells you whose permissions apply to the server. hostname -I gives the VM’s network addresses; use its reachable private IPv4 address, not the SSH public endpoint. mkdir -p creates the folders and doesn’t complain if they already exist.

Put your three private IP addresses here
The addresses fill in the commands below. Nothing is sent anywhere by this page. You may also replace A_IP, B_IP, and C_IP by hand.
Everyone · second VM terminal · keep this running
python3 -m http.server 8000 --bind 0.0.0.0 --directory "$HOME/lab01/served"

A server is simply a program waiting for requests. 8000 names its port; --bind 0.0.0.0 lets it listen on the VM’s network interfaces; --directory specifies the shelf of files it will serve. Each VM runs a different server even though all three use port 8000.

Already running a server on port 8000? Go to its old server terminal and press Ctrl+C before starting this one. Don’t kill someone else’s process. Keep this server terminal open while working; use your other terminal to create files.
Everyone · working terminal · verify their own server
curl --max-time 5 -I http://127.0.0.1:8000/

127.0.0.1 means “this very machine.” At this point your shelf is probably empty; an HTTP response is what matters. A connection to localhost does not prove that the other VMs can reach you.

Round 1 · A prepares

A file with permission 600

PreparesA
AttemptsB
ChallengesC

Alice wants to share a notice and keep a ledger to herself. Both files sit on the same public shelf. It’s a bad filing arrangement. Good: we can see exactly why.

A · create three files with three different permissions

A · working terminal
printf "Lunch is at noon.\n" > "$HOME/lab01/served/notice-a.txt"
printf "A ledger that only Alice should read.\n" > "$HOME/lab01/served/ledger-a.txt"
printf "Sealed box: even Alice cannot read this yet.\n" > "$HOME/lab01/served/sealed-a.txt"
chmod 644 "$HOME/lab01/served/notice-a.txt"
chmod 600 "$HOME/lab01/served/ledger-a.txt"
chmod 000 "$HOME/lab01/served/sealed-a.txt"
ls -l "$HOME/lab01/served"

printf writes the invented messages. > creates or replaces a file. chmod 644 lets the owner write and everyone read; 600 lets only the owner read/write; 000 denies normal file access to everyone, including the owner. Notice what ls -l prints: those rwx letters are Linux’s permission rules.

B · take the notice, then the ledger

B · working terminal
curl -i --max-time 5 http://A_IP:8000/notice-a.txt
curl --max-time 5 -o "$HOME/lab01/received/ledger-from-a.txt" http://A_IP:8000/ledger-a.txt
cat "$HOME/lab01/received/ledger-from-a.txt"

The first curl -i includes the HTTP status and headers. The second uses lowercase -o to save a local copy with a new name. It succeeds even though Alice used 600. Why? The HTTP server runs as Alice. It reads the file as Alice and hands a copy to B. Linux did not ignore anything.

C · try another client and a genuinely unreadable file

C · working terminal
wget -qO- http://A_IP:8000/ledger-a.txt
curl -i --max-time 5 http://A_IP:8000/sealed-a.txt

wget -qO- means quiet, write the result to standard output (the screen). It does not create a named download here. Expect the ledger to appear. The sealed file cannot be read, and this simple server normally answers 404 even though the file exists. Its error message does not distinguish “missing file” from “unreadable file.”

A changes one lock. C retries; B saves the file another way.

A chooses how to open the lock. Both routes make this file owner-readable, but one states the final permission value; the other changes just a particular permission bit. Run one route, then check the permissions.

Route 1 · numeric permissions
chmod 400 "$HOME/lab01/served/sealed-a.txt"
ls -l "$HOME/lab01/served/sealed-a.txt"
Route 2 · symbolic permissions
chmod u+r "$HOME/lab01/served/sealed-a.txt"
ls -l "$HOME/lab01/served/sealed-a.txt"

400 sets the entire mode to owner-read-only. u+r adds read permission for the owner without changing the other bits. Because this file started at 000, both routes produce the same result. On a file that already had other permission bits, they might differ.

C · working terminal
curl -i --max-time 5 http://A_IP:8000/sealed-a.txt
B · working terminal
wget -O "$HOME/lab01/received/sealed-copy-a.txt" http://A_IP:8000/sealed-a.txt
cat "$HOME/lab01/received/sealed-copy-a.txt"

Now the owner may read. Therefore the server may read. wget -O (uppercase O) chooses the output file, like curl -o. It is not the same as wget -qO-, which prints bytes directly in the terminal. Three forms, one HTTP server, no password check on the visitors.

Watch the two different locks. Linux permissions control which local account can open a file. This small HTTP server has no rule saying “Bob yes, C no.” The server’s account is the one using the Linux lock.
Round 2 · B prepares

The file with a dot in front

PreparesB
AttemptsC
ChallengesA

Bob decides that hiding a filename is surely as good as hiding the file. Computers have a slightly different idea of “hidden.”

B · make a visible notice and a hidden draft

B · working terminal
printf "This one is meant to be public.\n" > "$HOME/lab01/served/status-b.txt"
printf "Draft: please do not read me.\n" > "$HOME/lab01/served/.draft-b.txt"
chmod 644 "$HOME/lab01/served/status-b.txt"
chmod 600 "$HOME/lab01/served/.draft-b.txt"
ls "$HOME/lab01/served"
ls -a "$HOME/lab01/served"
ls -la "$HOME/lab01/served"

ls normally hides names beginning with a dot. ls -a includes them, and ls -la adds permission details. The dot changes how ls displays the name; it does not create a security rule.

C · read the visible file, then browse the shelf

C · working terminal
wget -qO- http://B_IP:8000/status-b.txt
curl --max-time 5 http://B_IP:8000/

With no index.html on the shelf, the server displays a directory listing. The hidden filename may appear there too. It is not a secret just because an ordinary ls omits it.

A · ask directly for the hidden file

A · working terminal
curl -i --max-time 5 http://B_IP:8000/.draft-b.txt
mkdir -p "$HOME/lab01/received"
wget -O "$HOME/lab01/received/draft-from-b.txt" http://B_IP:8000/.draft-b.txt
cat "$HOME/lab01/received/draft-from-b.txt"

A knows the name, so A can request it. A’s download name is ordinary, without a dot. File naming on the receiver does not change what was on B’s VM.

B · put a home page in front of the listing

B · working terminal
printf "<h1>Welcome to B's shelf</h1>\n" > "$HOME/lab01/served/index.html"
ls -la "$HOME/lab01/served"
C · working terminal
curl --max-time 5 http://B_IP:8000/
curl -i --max-time 5 http://B_IP:8000/.draft-b.txt

The browser-friendly index.html replaces the automatic listing at /. It does not block a direct request for /.draft-b.txt. Not showing a filename and refusing access to it are different jobs.

B renames the draft. A tries both addresses.

B chooses how to get a new filename. A will request both names afterward. Keep track of whether you moved the draft or copied it.

Route 1 · move the draft to a new name
mv "$HOME/lab01/served/.draft-b.txt" "$HOME/lab01/served/memo-b.txt"
ls -la "$HOME/lab01/served"
Route 2 · make a second copy instead
cp "$HOME/lab01/served/.draft-b.txt" "$HOME/lab01/served/memo-b.txt"
ls -la "$HOME/lab01/served"

mv gives one file a new name, so the old URL no longer reaches it. cp creates another file, leaving the old one where it was. In either case, any copy A downloaded earlier stays on A’s VM.

A · working terminal
curl -i --max-time 5 http://B_IP:8000/.draft-b.txt
curl --max-time 5 http://B_IP:8000/memo-b.txt

mv moves or renames files. If B used mv, the old URL stops working; if B used cp, both URLs still work. And A’s previously downloaded file is unaffected either way. Renaming the original does not retrieve an earlier copy.

Round 3 · C prepares

Two shelves and one shortcut

PreparesC
AttemptsA
ChallengesB

C tries a better arrangement: put the public files in one folder and the private ones elsewhere. Now we have two shelves, not one. There is a catch involving shortcuts.

C · put the private file outside the served directory

C · working terminal
printf "The public menu from C.\n" > "$HOME/lab01/served/menu-c.txt"
printf "C's private practice file.\n" > "$HOME/lab01/locked/vault-c.txt"
chmod 644 "$HOME/lab01/served/menu-c.txt"
chmod 600 "$HOME/lab01/locked/vault-c.txt"
ls -l "$HOME/lab01/served"
ls -l "$HOME/lab01/locked"

A downloads the menu. B looks for the vault.

A · working terminal
curl --max-time 5 -o "$HOME/lab01/received/menu-from-c.txt" http://C_IP:8000/menu-c.txt
cat "$HOME/lab01/received/menu-from-c.txt"
B · working terminal
curl -i --max-time 5 http://C_IP:8000/vault-c.txt
curl -i --max-time 5 http://C_IP:8000/locked/vault-c.txt

A gets the menu; B should get HTTP 404 for both requests. That means the server does not have a file at those URLs. It does not prove that the file is unreadable to C’s Linux account; the file is simply outside this particular shelf.

C · add a shortcut pointing to the private file

C · working terminal
ln -s "$HOME/lab01/locked/vault-c.txt" "$HOME/lab01/served/vault-window-c.txt"
ls -l "$HOME/lab01/served/vault-window-c.txt"
readlink "$HOME/lab01/served/vault-window-c.txt"

ln -s creates a symbolic link: a name that points at another path. readlink shows where it points. This Python server follows these links. It is easy to expose something outside the served folder without moving the file itself.

B · working terminal
wget -qO- http://C_IP:8000/vault-window-c.txt

C · remove the shortcut, then deny the owner read permission

C · working terminal
rm "$HOME/lab01/served/vault-window-c.txt"
chmod 000 "$HOME/lab01/locked/vault-c.txt"
ln -s "$HOME/lab01/locked/vault-c.txt" "$HOME/lab01/served/closed-window-c.txt"
B · working terminal
curl -i --max-time 5 http://C_IP:8000/vault-window-c.txt
curl -i --max-time 5 http://C_IP:8000/closed-window-c.txt

The first address has lost its link. The second link still exists, but its target is unreadable to the server process. With this Python server, both requests normally return 404. The same HTTP error can hide two different causes. Paths and permissions: both matter. C can now put things back.

C · working terminal
rm "$HOME/lab01/served/closed-window-c.txt"
chmod 600 "$HOME/lab01/locked/vault-c.txt"
ls -l "$HOME/lab01/locked/vault-c.txt"
This is a learning exercise, not a secure production file service. Python’s built-in HTTP server has no user authentication and follows symbolic links. Only serve made-up files in these folders.
Finish

Leave the machines in a sensible state

Stop the running server on each VM with Ctrl+C in the terminal where python3 -m http.server is running. The other terminal stays open.

Everyone · working terminal
ls -la "$HOME/lab01/served"
ls -la "$HOME/lab01/received"
ls -la "$HOME/lab01/locked"

The files are left in ~/lab01 so you can see what you created. To remove only this practice folder, first look at it, then run rm -r "$HOME/lab01". Never paste a broader rm -r command without checking the path.

What happenedWhere to look first
Connection refusedIs the server running? Wrong port? Check the server terminal.
Request times outCheck private IP and Azure networking; don’t assume a file permission caused it.
HTTP 404The Python server could not serve the requested path. The file may be absent, or the server account may lack access.
HTTP 403Some servers use this for forbidden access; Python’s simple file server usually responds 404 instead.
Address already in useThere is already a server on that port on this VM. Stop your previous one with Ctrl+C.
Downloaded name differscurl -o and wget -O set the local output name.
