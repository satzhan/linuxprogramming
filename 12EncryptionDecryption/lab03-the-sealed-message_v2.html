Linux Security · Lab 03

The sealed message

Alice can publish a lock that everyone can use. But can only Alice unlock what arrives? And what happens when the same secret travels in a different envelope?

The ideaPrepare keysA sealed scheduleA readable-looking secretA message for twoWhat did we learn?

Anyone may lock it. Not everyone can unlock it.

You have already tried signatures in Lab 04. There the message was readable; the signature helped you check who signed the bytes. This time the problem is different. Alice wants someone to receive information privately. A stranger may intercept the file, copy it and even keep it forever. That should not reveal the message.

Public key: a lock Alice gives away. Other people use it to encrypt information for Alice.

Private key: the part Alice keeps. It lets her decrypt information encrypted for her public key.

The three assigned identities are Alice, Bob and Mallory. Each has a Linux VM. The story keeps moving: the sender in one scene becomes the recipient or the curious bystander in the next. Follow the role you've been assigned in each scene. You have already used HTTP downloads in an earlier lab; you'll use them again here.

Tools: gpg (OpenPGP encryption), python3 (a tiny HTTP file server), curl, wget, and the ordinary Linux commands you know. We use disposable, passphrase-free keys for this exercise; do not use these keys for anything real. Only publish *.pub.asc files and ciphertext, never the private keyring.

Command explanations are hidden under “Explain these commands.” Open them when something is unclear, then go back to the experiment. No answer is supposed to depend on memorizing a flag.

Before the story

Make the locks and exchange them

Imagine a wall of public mailboxes. Each person publishes a padlock, not a key that opens it. We will use a public folder served over HTTP as that wall.

Give your VM its identity

Use alice, bob, or mallory for ROLE. Put the three real VM addresses into the other variables. Keep this terminal open for the exercises; if you reconnect, restore the variables.

EVERY STUDENT · own VM
ROLE=alice
ALICE_IP=10.0.0.10
BOB_IP=10.0.0.11
MALLORY_IP=10.0.0.12

mkdir -p "$HOME/lab03"/{gpg,public,inbox,notes}
export GNUPGHOME="$HOME/lab03/gpg"
chmod 700 "$GNUPGHOME"
command -v gpg python3 curl wget
hostname -I
Explain these commands
  • ROLE is the name assigned to this VM in the story. The three IP variables point to the actual Azure VMs, not the example addresses shown here.
  • mkdir -p .../{gpg,public,inbox,notes} creates separate spaces for keys, published files, downloads and drafts. Bash expands the braces into four directory names.
  • GNUPGHOME gives this lab its own GPG keyring rather than using the student’s usual one. chmod 700 restricts access to its directory.
  • command -v checks whether the tools exist. hostname -I shows the VM’s IP addresses; use the appropriate address that worked in your cross-VM lab.

If gpg is missing: on Ubuntu, install it with sudo apt update && sudo apt install -y gnupg.

Create an encryption key and publish its public half

The public half is meant to be copied. The secret half stays inside the private gpg directory. Do not publish that directory.

EVERY STUDENT · own VM
gpg --batch --pinentry-mode loopback --passphrase '' --quick-generate-key "$ROLE Lab03 <$ROLE@lab03.invalid>" default default never
gpg --list-keys "$ROLE@lab03.invalid"
gpg --list-secret-keys "$ROLE@lab03.invalid"
gpg --armor --export "$ROLE@lab03.invalid" > "$HOME/lab03/public/$ROLE.pub.asc"
gpg --fingerprint "$ROLE@lab03.invalid"
ls -lh "$HOME/lab03/public"
Explain these commands
  • --quick-generate-key makes a new OpenPGP key for this lab. --batch and the empty passphrase make the example reproducible without a password prompt. They are for disposable classroom keys, not personal security.
  • --list-keys displays public keys; --list-secret-keys shows which private keys this VM can use.
  • --export outputs only the public portion. --armor encodes that public data as printable ASCII text; > saves it to a file.
  • --fingerprint identifies the cryptographic key. An email label is not proof that the key belongs to that person.

Repeat-run note: if you already generated this lab key, do not create another by accident. Use gpg --list-keys and continue with the existing one.

Make the public shelf reachable

The HTTP server exposes only the public folder. Everything placed there can be downloaded by classmates. The server runs in the background so the shell remains usable.

EVERY STUDENT · own VM
python3 -m http.server 8000 --bind 0.0.0.0 --directory "$HOME/lab03/public" > "$HOME/lab03/server.log" 2>&1 &
echo $! > "$HOME/lab03/server.pid"
curl -fsS "http://127.0.0.1:8000/$ROLE.pub.asc" | head -n 2
Explain these commands
  • python3 -m http.server serves files from public over HTTP. --bind 0.0.0.0 makes it listen on the VM’s network interfaces, not just localhost.
  • > server.log 2>&1 records normal output and errors in a log file; the final & runs the server in the background.
  • $! is the process ID of the most recent background process. We save it for cleanup.
  • curl -fsS ... | head -n 2 requests your public key from your own server and displays its first two lines. This verifies a local download, not the cross-VM connection.

If a different service already uses port 8000, look at server.log. Cross-VM access also depends on Azure network rules; use the working connectivity arrangement from Lab 00.

Collect the published keys

You can use either downloader. Do both here, then inspect what you received. Each student obtains the same three public-key files.

EVERY STUDENT · own VM
curl -fS -o "$HOME/lab03/inbox/alice.pub.asc" "http://$ALICE_IP:8000/alice.pub.asc"
wget -qO "$HOME/lab03/inbox/bob.pub.asc" "http://$BOB_IP:8000/bob.pub.asc"
curl -fS -o "$HOME/lab03/inbox/mallory.pub.asc" "http://$MALLORY_IP:8000/mallory.pub.asc"

gpg --show-keys --fingerprint "$HOME/lab03/inbox/"*.pub.asc
gpg --import "$HOME/lab03/inbox/"*.pub.asc
gpg --list-keys
Explain these commands
  • curl -o FILE URL and wget -O FILE URL both download a resource to a specified filename. -fS makes curl report HTTP failures; -q makes wget quiet.
  • gpg --show-keys inspects keys from files without requiring you to import them first. --fingerprint displays key fingerprints.
  • gpg --import adds those public keys to the local keyring. Importing does not establish that Alice really owns a file labelled Alice.
  • Check with the actual person: compare a fingerprint directly with what the supposed owner sees on their VM. Reading a fingerprint from the same untrusted download does not establish identity.

Try this: compare the two downloaders using ls -lh and sha256sum. Does the choice of curl or wget change the key?

What matters: every person should now have one private key on their own VM and public keys for all three people. If a download fails, resolve the network connection before starting the messages. A successful download by itself is not proof of key ownership.
Dispatch 01 · The quiet timetable

The museum schedule must stay secret

Alice writes and seals the scheduleBob opens itMallory finds a copy

Alice manages a small exhibition. She wants Bob to know when the doors will open and which temporary access phrase to use. The file travels through an ordinary web server. Mallory can see the transfer and download exactly the same ciphertext. That is acceptable—provided the ciphertext does not disclose the secret.

Before running commands: who should be able to open the message? Who should be able to download the encrypted file? Those are different questions.

Alice seals a note for Bob

Alice writes an ordinary text file, then encrypts it using Bob’s public key. Alice never needs Bob’s private key.

ALICE · create and encrypt
printf 'Museum opening: 16:30
Temporary access phrase: LANTERN-42
' > "$HOME/lab03/notes/01-schedule.txt"
cat "$HOME/lab03/notes/01-schedule.txt"
gpg --batch --yes --trust-model always --encrypt --recipient bob@lab03.invalid --output "$HOME/lab03/public/01-schedule.gpg" "$HOME/lab03/notes/01-schedule.txt"
file "$HOME/lab03/public/01-schedule.gpg"
wc -c "$HOME/lab03/notes/01-schedule.txt" "$HOME/lab03/public/01-schedule.gpg"
Explain these commands
  • printf writes a two-line plaintext. It is not secret until encryption happens.
  • --encrypt --recipient bob@lab03.invalid tells GPG which public key should protect the message. --output names the encrypted file.
  • --trust-model always bypasses GPG’s usual owner-trust question for this classroom exercise. It does not verify Bob’s identity. You need to compare fingerprints independently.
  • file guesses the data format, while wc -c counts bytes. The ciphertext does not have to be the same size as the plaintext.

Bob retrieves and opens the sealed file

Bob downloads the ciphertext like any other HTTP file. Only afterward does his private key come into play.

BOB · download and decrypt
curl -fS -o "$HOME/lab03/inbox/01-schedule.gpg" "http://$ALICE_IP:8000/01-schedule.gpg"
gpg --batch --yes --output "$HOME/lab03/inbox/01-opened.txt" --decrypt "$HOME/lab03/inbox/01-schedule.gpg"
cat "$HOME/lab03/inbox/01-opened.txt"
Explain these commands
  • curl downloads the ciphertext; the server does not decrypt anything for Bob.
  • gpg --decrypt finds a matching private key inside Bob’s keyring and uses it to recover the plaintext. --output saves the recovered file.
  • cat proves the decrypted output is readable. Ask Alice whether it matches the note she wrote.

Mallory obtains exactly the same sealed file

Mallory does not need to break into anyone’s machine. The file is already public. Try to decrypt it anyway.

MALLORY · download and inspect
wget -qO "$HOME/lab03/inbox/01-schedule.gpg" "http://$ALICE_IP:8000/01-schedule.gpg"
file "$HOME/lab03/inbox/01-schedule.gpg"
gpg --batch --yes --output "$HOME/lab03/inbox/01-mallory-opened.txt" --decrypt "$HOME/lab03/inbox/01-schedule.gpg"
ls -lh "$HOME/lab03/inbox/01-"*
Explain these commands
  • wget -qO obtains the same encrypted bytes that Bob downloaded, though the local filename can be whatever you choose.
  • gpg --decrypt should report that no secret key is available. That failure is the expected observation—not a networking problem.
  • ls lets you check what files exist after the attempt. A failed decryption is not evidence that a readable output file was created.
Explain: Bob and Mallory downloaded the same encrypted bytes. Why is Bob’s outcome different? What is public here, and what must remain private?
Dispatch 02 · The late correction

The note looks readable. It still isn't.

Bob reports a correctionMallory receives itAlice sees the transmission

After the exhibition opens, Bob notices a mistake in the equipment inventory. Mallory is handling the overnight delivery, so Bob sends the correction to Mallory. This time the encrypted file is printable text that begins with a familiar-looking header. Alice intercepts it and wonders whether that means it is no longer encrypted.

Bob sends the correction in a different envelope

This time GPG adds ASCII armor. The file will look like text, but readable characters do not necessarily mean readable information.

BOB · ASCII-armored encryption
printf 'Inventory correction: 8 crates, not 6.
New arrival time: 07:15.
' > "$HOME/lab03/notes/02-inventory.txt"
gpg --batch --yes --trust-model always --armor --encrypt --recipient mallory@lab03.invalid --output "$HOME/lab03/public/02-inventory.asc" "$HOME/lab03/notes/02-inventory.txt"
head -n 5 "$HOME/lab03/public/02-inventory.asc"
wc -c "$HOME/lab03/notes/02-inventory.txt" "$HOME/lab03/public/02-inventory.asc"
Explain these commands
  • --armor represents encrypted binary data with printable characters. It does not replace encryption; it only changes how encrypted data is packaged.
  • head -n 5 shows the armored header and the beginning of the encoded data.
  • wc -c makes the overhead of the text representation visible. A printable file may be longer than the binary form.

Mallory receives the inventory correction

Mallory expects a secret destined for her. She should not need to know which encryption format Bob chose.

MALLORY · decrypt the ASCII file
wget -qO "$HOME/lab03/inbox/02-inventory.asc" "http://$BOB_IP:8000/02-inventory.asc"
gpg --batch --yes --output "$HOME/lab03/inbox/02-opened.txt" --decrypt "$HOME/lab03/inbox/02-inventory.asc"
cat "$HOME/lab03/inbox/02-opened.txt"
Explain these commands
  • wget -qO downloads the file; this time the file contains printable armor rather than raw binary ciphertext.
  • gpg --decrypt understands both armored and binary OpenPGP messages. Mallory’s private key opens the encrypted message.
  • cat reveals the recovered plain text, not the original armor.

Alice examines the suspicious-looking text

Alice can see an OpenPGP header and inspect some packet information. But can she read the inventory correction?

ALICE · inspect without permission to decrypt
curl -fS -o "$HOME/lab03/inbox/02-inventory.asc" "http://$BOB_IP:8000/02-inventory.asc"
head -n 5 "$HOME/lab03/inbox/02-inventory.asc"
gpg --list-packets "$HOME/lab03/inbox/02-inventory.asc"
gpg --batch --yes --output "$HOME/lab03/inbox/02-alice-opened.txt" --decrypt "$HOME/lab03/inbox/02-inventory.asc"
Explain these commands
  • head reveals the armor header. It does not expose the decrypted inventory information.
  • --list-packets inspects the OpenPGP packaging and may reveal metadata such as recipient key identifiers. Encryption does not necessarily hide all metadata.
  • --decrypt should fail because Alice lacks Mallory’s private key. A readable-looking encrypted file is not a plaintext file.
Explain: in Dispatch 01 Alice produced a binary .gpg file; in Dispatch 02 Bob produced a printable .asc file. What changed? What did not change?
Dispatch 03 · The emergency notice

One message, more than one recipient

Mallory reports an urgent changeAlice opens itBob discovers the message

The opening schedule changes again. Mallory must tell Alice immediately, but she also wants to keep an encrypted copy that she can open herself later. Bob finds the published file. He has a private key too—just not one of the keys named as a recipient.

Make a prediction: does naming two recipients produce two plaintext files? Or can one encrypted file be opened by either of two private keys?

Mallory seals one notice for Alice and herself

No need to produce and publish two ciphertext files. GPG can mark multiple recipients in one encryption operation.

MALLORY · two recipients
printf 'Urgent update: the delivery is now at the north entrance.
Confirmation phrase: BLUE-ORCHID.
' > "$HOME/lab03/notes/03-urgent.txt"
gpg --batch --yes --trust-model always --encrypt --recipient alice@lab03.invalid --recipient mallory@lab03.invalid --output "$HOME/lab03/public/03-urgent.gpg" "$HOME/lab03/notes/03-urgent.txt"
gpg --list-packets "$HOME/lab03/public/03-urgent.gpg"
gpg --batch --yes --output "$HOME/lab03/notes/03-my-copy.txt" --decrypt "$HOME/lab03/public/03-urgent.gpg"
cat "$HOME/lab03/notes/03-my-copy.txt"
Explain these commands
  • --recipient can be repeated. Each specified public key is authorized to open the same encrypted content with the matching private key.
  • --list-packets can show multiple public-key-encrypted session-key packets. There is still one message payload.
  • Mallory also decrypts the published file. Unlike a single-recipient message sent only to Alice, this copy was deliberately encrypted for Mallory too.

Alice opens the urgent notice

Alice is one of the recipients and should be able to recover the secret with her own private key.

ALICE · decrypt
curl -fS -o "$HOME/lab03/inbox/03-urgent.gpg" "http://$MALLORY_IP:8000/03-urgent.gpg"
gpg --batch --yes --output "$HOME/lab03/inbox/03-opened.txt" --decrypt "$HOME/lab03/inbox/03-urgent.gpg"
cat "$HOME/lab03/inbox/03-opened.txt"
Explain these commands
  • curl brings the encrypted file to Alice’s machine. Anyone with network access to the file could have downloaded those bytes.
  • gpg --decrypt succeeds because Alice was included as a recipient. This does not imply that Alice acquired Mallory’s private key.

Bob tries the same file

Bob has a legitimate key pair. The presence of a private key is not enough; it must match an intended recipient.

BOB · examine and attempt
wget -qO "$HOME/lab03/inbox/03-urgent.gpg" "http://$MALLORY_IP:8000/03-urgent.gpg"
gpg --list-packets "$HOME/lab03/inbox/03-urgent.gpg"
gpg --batch --yes --output "$HOME/lab03/inbox/03-bob-opened.txt" --decrypt "$HOME/lab03/inbox/03-urgent.gpg"
gpg --list-secret-keys
Explain these commands
  • --list-packets can reveal that the package contains more than one recipient entry without revealing the message itself.
  • --decrypt should fail because Bob’s secret key matches neither recipient.
  • --list-secret-keys confirms Bob owns a key pair. That fact alone does not grant access to every encrypted message.
Explain: both Alice and Mallory can open the notice. Bob cannot. How is that possible with only one encrypted file? Does the encrypted file prove who wrote it?
A connection to Lab 04: encryption protects confidentiality but does not by itself authenticate the sender. Anybody with Alice’s public key could have encrypted a file for Alice. A signature is a separate way to check who signed content, provided the verifying public key is trustworthy.
Debrief

What have you actually tested?

Across the three dispatches every student has published a public key, obtained other keys, encrypted and sent a message, opened a message intended for them, and tried to open one that was not. What changes is the situation, the recipient, the packaging, and finally the number of recipients.

Submit evidence, not a command transcript

Show that your key existed and your public key was published; that your assigned message was encrypted and downloadable; that you successfully decrypted a message addressed to you; that decryption failed for a message not addressed to you; and that you compared what happened across the three dispatches. Use as many or as few screenshots as needed to demonstrate those outcomes.

In a short explanation, answer: (1) Why can someone download your ciphertext without being able to read it? (2) What is the difference between .gpg and armored .asc? (3) Why could two recipients decrypt Dispatch 03? (4) Does encryption alone tell you who sent the file? (5) Why must you verify that a public key really belongs to its claimed owner?

Close the temporary file server

When your work is finished, stop the server on your own VM. The created files remain for inspection.

EVERY STUDENT · cleanup
kill "$(cat "$HOME/lab03/server.pid")"
cat "$HOME/lab03/server.log" | tail -n 8
Explain these commands
  • kill sends a termination signal to the server process whose ID was saved earlier.
  • tail -n 8 shows recent HTTP requests. The log is one more way to see which public resources were requested.

Where Lab 05 starts: You have used public-key encryption without caring how GPG makes the large message efficient. In fact, GPG usually uses a fresh symmetric session key for the message and public-key cryptography to protect that session key. Lab 05 can take this mechanism apart: fast symmetric encryption for the data, asymmetric encryption for exchanging its key.
