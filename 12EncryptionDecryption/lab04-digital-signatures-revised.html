Lab 04: Digital signatures

What are we checking?

Alice sends Bob a notice through Mallory. Mallory may change what gets delivered, but Mallory does not have Alice's private key. Bob wants to tell whether Alice's key signed the message he received.

A signature is not a secret message. Anyone can read the text. The key pair has two different jobs:

Sign(private key, message, purpose) → signature

Verify(public key, message, signature, purpose) → yes / no

Verification never requires an original copy of the message. It does require knowing which public key should count as Alice's. If Bob accepts a replacement public key from the same untrusted messenger, he may verify a message that Alice never signed.

One more limitation: even a genuinely signed message may be old. We'll test that near the end.

AliceWrites and signs notices on VM A.
MalloryRuns a separate forwarding server on VM C. Never changes Alice's VM.
BobDownloads what Mallory forwards and decides what to trust on VM B.

Use only your assigned Azure VMs. These are disposable lab keys with no passphrases. Never serve the private key, and don't use your actual SSH login keys. You'll need Bash, OpenSSH with ssh-keygen -Y, Python 3, curl, and wget.

Set up your VMs

Everybody runs the first three steps on their own VM. Use one terminal for the HTTP server and another terminal for commands. Keep the server running while the group works.

1. Prepare a clean workspace

This lab has separate places for keys, published files, downloads, and trusted identities.

Every VM · working terminal
command -v ssh-keygen
command -v python3
command -v curl
command -v wget
ssh -V
hostname -I
mkdir -p "$HOME/lab04"/{keys,outbox,inbox,trust}
chmod 700 "$HOME/lab04/keys" "$HOME/lab04/trust"
ls -ld "$HOME/lab04"/{keys,outbox,inbox,trust}
Explain these commands
  • command -v asks Bash where a program can be found; it does not start it. Run the four lines separately so you can tell which tool, if any, is missing.
  • ssh -V prints the OpenSSH version; ssh-keygen -Y sign and -Y verify need an OpenSSH version that supports SSH signatures.
  • hostname -I prints addresses assigned to this VM. Pick the private IP your teammates can actually reach; it may print several.
  • $HOME is the current user's home directory. {keys,outbox,inbox,trust} is Bash brace expansion: the shell produces four paths.
  • mkdir -p creates missing directories and does not complain if they already exist.
  • chmod 700 gives the directory owner read, write and traversal permission; ordinary other users get none. It does not prevent administrators from accessing the files.
  • ls -ld shows permissions on directories themselves, not their contents.

Check: You have four folders. Only the outbox will be served over HTTP.

2. Generate an Ed25519 key pair

Each VM makes its own lab key. Everyone uses the same filename, but the generated keys are different.

Every VM · working terminal
if [ ! -f "$HOME/lab04/keys/dispatch" ]; then
  ssh-keygen -q -t ed25519 -N "" -f "$HOME/lab04/keys/dispatch" -C "lab04-disposable"
fi
cp "$HOME/lab04/keys/dispatch.pub" "$HOME/lab04/outbox/dispatch.pub"
ssh-keygen -lf "$HOME/lab04/outbox/dispatch.pub" -E sha256
ls -l "$HOME/lab04/keys" "$HOME/lab04/outbox"
Explain these commands
  • if [ ! -f FILE ]; then ... fi means “generate the key only if the private-key file does not already exist.” -f inside [ ] tests for a regular file; ! reverses the result.
  • ssh-keygen -t ed25519 generates a public/private key pair. -q reduces output; -N "" sets an empty passphrase for a disposable practice key; -f specifies its location; -C adds an optional comment.
  • dispatch is the private key. dispatch.pub is the public key. The public key is safe to distribute; the private key must stay in keys/.
  • cp copies only the public key into outbox. The lab server will be able to serve this file.
  • ssh-keygen -lf ... -E sha256 displays the public key's SHA-256 fingerprint. This identifies the key material, not the human who owns it.
  • ls -l displays file information so you can check that dispatch is NOT in the published outbox.

3. Serve public files

In your server terminal, start Python’s small HTTP server. It will stay occupied until you stop it with Ctrl+C.

Every VM · server terminal · leave running
python3 -m http.server 8000 --bind 0.0.0.0 --directory "$HOME/lab04/outbox"
Explain these commands
  • python3 -m http.server runs Python's built-in HTTP file server. -m tells Python to run a module.
  • 8000 is the listening port. Another VM can request http://YOUR_IP:8000/dispatch.pub.
  • --bind 0.0.0.0 listens on all IPv4 interfaces, not just 127.0.0.1. Network security rules must still allow the connection.
  • --directory .../outbox serves only that directory tree. Because your private key is outside it, it should not be downloadable through this server.
  • The HTTP connection is not encrypted and has no sender authentication. That is deliberate for this experiment.

4. Test the server locally, then from a second VM

First confirm your server works. Then have a teammate replace PARTNER_IP with your VM’s reachable private IP.

Every VM · working terminal; cross-VM test on partner VM
curl -fS --max-time 8 http://127.0.0.1:8000/dispatch.pub | head -c 80
printf '\n'
# On a DIFFERENT VM, replace PARTNER_IP with the server VM's real IP:
curl -fS --max-time 8 http://PARTNER_IP:8000/dispatch.pub | head -c 80
printf '\n'
Explain these commands
  • 127.0.0.1 always means the VM you are currently on. It does not test communication between machines.
  • curl URL downloads the HTTP response; without -o it prints to the terminal. -f treats HTTP error responses as failures; -S shows errors; --max-time 8 limits the whole transfer to eight seconds.
  • | sends output from the first program into the second. head -c 80 keeps only the first 80 bytes so your terminal is not filled with key text.
  • printf '\n' adds a newline. Lines beginning with # are Bash comments; they explain what to do but are not commands.
  • A timeout usually points to a wrong address, firewall restriction, or missing server. A 404 response means the HTTP connection worked but the requested file is absent.

Check: You can fetch a public key using the other VM’s IP, not only 127.0.0.1.

Bob establishes Alice’s key

Do this before Mallory delivers any notice. Bob needs an authentic reference for Alice’s public key. The public key itself is not secret, but its ownership matters.

5. Alice reads her fingerprint; Bob checks it

Alice runs the first command on Alice’s VM. Bob downloads Alice’s public key using the address known for Alice’s VM. Bob then compares fingerprints with Alice in person (for example, by looking at Alice’s terminal).

Alice · working terminal; show to Bob
ssh-keygen -lf "$HOME/lab04/keys/dispatch.pub" -E sha256
Explain these commands
  • ssh-keygen -lf prints a fingerprint derived from the public key. -E sha256 selects SHA-256.
  • The fingerprint is not a secret. The important part is how Bob establishes that the fingerprint really came from Alice instead of Mallory.
Bob · working terminal
curl -fS --max-time 8 -o "$HOME/lab04/inbox/alice-trusted.pub" http://ALICE_IP:8000/dispatch.pub
ssh-keygen -lf "$HOME/lab04/inbox/alice-trusted.pub" -E sha256
Explain these commands
  • curl -o PATH saves the downloaded public key under the filename Bob chooses. Replace ALICE_IP with the actual private address of Alice’s VM.
  • Bob compares the downloaded key fingerprint with Alice’s directly confirmed fingerprint, character for character. If the fingerprints differ, STOP. Do not create a trusted entry.
  • If the two fingerprints agree, Bob has evidence that this downloaded key matches the key Alice showed him independently. HTTP alone did not establish that.

Do not substitute a public key from a link Mallory supplies here. The whole point is to establish one reference that the intermediary cannot choose.

6. Bob records which key is allowed to represent Alice

OpenSSH uses an allowed signers file. Bob makes one line connecting an identity label to the public key he just checked.

Bob · working terminal
awk '{print "alice@lab04", $1, $2}' "$HOME/lab04/inbox/alice-trusted.pub" > "$HOME/lab04/trust/alice_allowed"
cat "$HOME/lab04/trust/alice_allowed"
Explain these commands
  • awk splits the public-key line into fields. In a normal OpenSSH public-key file, $1 is the key type and $2 is the encoded public key. The optional comment is not needed.
  • "alice@lab04" is a local identity label chosen for this exercise. It is not proof that a real email account or person was contacted.
  • print writes the label, key type and key bytes into one line. This is the OpenSSH allowed_signers format.
  • > redirects standard output into the named file, replacing its previous contents. cat displays the resulting line.
  • This file is Bob’s trust policy. It records which key Bob will accept for the identity alice@lab04; the signature operation itself does not make that decision.

Check: The file begins alice@lab04 ssh-ed25519 .... Keep this file unchanged during the attacks.

1. Change the message, keep the signature

Bob will receive only the copy hosted by Mallory. He will not see Alice’s original message during verification. The question is whether he can reject a change anyway.

7. Alice signs a notice

Alice publishes a notice saying the delivery is at 14:00. A signature file appears next to it.

Alice · working terminal
printf 'FROM: Alice\nDelivery hour: 14:00\n' > "$HOME/lab04/outbox/notice.txt"
ssh-keygen -Y sign -f "$HOME/lab04/keys/dispatch" -n lab04-notice "$HOME/lab04/outbox/notice.txt"
ls -l "$HOME/lab04/outbox/notice.txt"*
Explain these commands
  • printf writes predictable text. Each \n represents a newline. > saves it to notice.txt.
  • ssh-keygen -Y sign signs the exact bytes of the message with Alice’s private key. It does NOT encrypt the text.
  • -f supplies Alice’s private key; -n lab04-notice specifies the signature namespace (the purpose for which it is signed).
  • notice.txt at the end names the input file. The command creates notice.txt.sig alongside it.
  • ls -l ...* uses * as a filename pattern, showing both the text file and its signature.

Check: Alice has notice.txt and notice.txt.sig in outbox.

8. Mallory forwards an edited copy

Mallory downloads those two files, changes only the time, and publishes the copy from Mallory’s own server. Mallory does NOT have access to Alice’s VM or private key.

Mallory · working terminal
curl -fS --max-time 8 -o "$HOME/lab04/outbox/notice.txt" http://ALICE_IP:8000/notice.txt
wget -q -O "$HOME/lab04/outbox/notice.txt.sig" http://ALICE_IP:8000/notice.txt.sig
sed -i 's/14:00/17:00/' "$HOME/lab04/outbox/notice.txt"
grep 'Delivery hour' "$HOME/lab04/outbox/notice.txt"
Explain these commands
  • curl -o and wget -O both download into a chosen local filename. This is deliberately a comparison of two transfer tools; either one can retrieve a file.
  • wget -q suppresses progress messages. The signature is downloaded intact, before the message is modified.
  • sed -i edits a file in place. s/14:00/17:00/ means substitute the first matching time on each line.
  • grep displays the matching line, letting Mallory check that the change happened.
  • The new message is in Mallory’s outbox. Alice’s original is untouched. The old signature remains a signature of the 14:00 version.

Check: The published copy says 17:00, while notice.txt.sig is still the signature Alice made.

9. Bob verifies the delivered copy

Bob downloads the message and signature from Mallory only. No diff or original-message download.

Bob · working terminal
curl -fS --max-time 8 -o "$HOME/lab04/inbox/delivery.txt" http://MALLORY_IP:8000/notice.txt
wget -q -O "$HOME/lab04/inbox/delivery.sig" http://MALLORY_IP:8000/notice.txt.sig
cat "$HOME/lab04/inbox/delivery.txt"
ssh-keygen -Y verify -f "$HOME/lab04/trust/alice_allowed" -I alice@lab04 -n lab04-notice -s "$HOME/lab04/inbox/delivery.sig" < "$HOME/lab04/inbox/delivery.txt"
Explain these commands
  • curl and wget save the two files Mallory serves. cat lets Bob read what Mallory delivered, not what Alice originally wrote.
  • ssh-keygen -Y verify checks the signature using the message supplied on standard input.
  • -f supplies Bob’s previously trusted list of signer names and public keys. -I alice@lab04 chooses the expected identity.
  • -n lab04-notice requires the same signing context Alice used. -s names the received signature file.
  • < supplies the received message as standard input. There is no original file in this command, because verification does not need one.
  • The command should report a verification failure (nonzero exit status). This does not say exactly who changed what; it says the received message/signature pair is not valid under the trusted key and context.

Check: Verification fails. Bob cannot deduce the original delivery time from the failed signature alone.

Before continuing: Bob has never downloaded the original notice. Why was he nevertheless able to reject the received one? Would diff have been possible without a second copy?

2. Replace the message, signature, and public key

Mallory notices the problem: the old signature belongs to Alice. So Mallory creates a new signature with Mallory’s own private key and labels Mallory’s public key as though it belonged to Alice. Bob will try this key first without checking its ownership. Then he will try his earlier trusted key.

10. Mallory signs the altered notice

Move the original signature out of the public folder so a second signing command does not have to overwrite it. Then publish a look-alike public key file.

Mallory · working terminal
mv "$HOME/lab04/outbox/notice.txt.sig" "$HOME/lab04/inbox/alice-old.sig"
ssh-keygen -Y sign -f "$HOME/lab04/keys/dispatch" -n lab04-notice "$HOME/lab04/outbox/notice.txt"
cp "$HOME/lab04/keys/dispatch.pub" "$HOME/lab04/outbox/alice.pub"
ssh-keygen -lf "$HOME/lab04/outbox/alice.pub" -E sha256
Explain these commands
  • mv moves the original Alice signature out of the published folder. It remains on Mallory’s VM but will no longer be served under notice.txt.sig.
  • ssh-keygen -Y sign creates a new signature for the modified 17:00 message, this time using Mallory’s own private key. The resulting notice.txt.sig matches Mallory’s key.
  • cp ...dispatch.pub ...alice.pub gives Mallory’s public key a misleading filename. A filename does not change which private key it matches.
  • ssh-keygen -lf ... -E sha256 shows the fingerprint of the key Mallory is claiming is Alice’s. It should differ from Alice’s actual fingerprint.

Check: Mallory’s server now offers a self-consistent altered message, matching new signature, and a file named alice.pub containing Mallory’s key.

11. Bob checks the files using the supplied key

For this one test, Bob deliberately makes the mistake of trusting the key that arrived with Mallory’s message. Store the bad trust policy in a separate disposable file.

Bob · working terminal · deliberately unsafe check
curl -fS --max-time 8 -o "$HOME/lab04/inbox/offer.txt" http://MALLORY_IP:8000/notice.txt
curl -fS --max-time 8 -o "$HOME/lab04/inbox/offer.sig" http://MALLORY_IP:8000/notice.txt.sig
curl -fS --max-time 8 -o "$HOME/lab04/inbox/claimed-alice.pub" http://MALLORY_IP:8000/alice.pub
awk '{print "alice@lab04", $1, $2}' "$HOME/lab04/inbox/claimed-alice.pub" > "$HOME/lab04/trust/unchecked_allowed"
ssh-keygen -Y verify -f "$HOME/lab04/trust/unchecked_allowed" -I alice@lab04 -n lab04-notice -s "$HOME/lab04/inbox/offer.sig" < "$HOME/lab04/inbox/offer.txt"
Explain these commands
  • The three curl -o commands save the modified message, Mallory’s new signature, and a public key all from the same intermediary. That is the mistake Bob will examine.
  • awk builds a signer list with the label alice@lab04, but the key bytes actually come from Mallory’s file.
  • unchecked_allowed does not replace alice_allowed. It is a deliberately incorrect trust list for this controlled experiment.
  • ssh-keygen -Y verify should succeed: the message matches Mallory’s signature, and Bob’s incorrect list authorizes Mallory’s key under Alice’s name.
  • Success here means “this signature is valid under the key allowed by unchecked_allowed.” It does not establish that Alice signed the notice.

Check: Verification succeeds, even though Alice never signed the 17:00 message.

12. Bob checks the key against what Alice confirmed earlier

Nothing has changed in the message or signature. Bob only changes which public key he accepts.

Bob · working terminal · correct trust check
ssh-keygen -lf "$HOME/lab04/inbox/alice-trusted.pub" -E sha256
ssh-keygen -lf "$HOME/lab04/inbox/claimed-alice.pub" -E sha256
cmp -s "$HOME/lab04/inbox/alice-trusted.pub" "$HOME/lab04/inbox/claimed-alice.pub" && echo 'Same key file' || echo 'Different key files'
ssh-keygen -Y verify -f "$HOME/lab04/trust/alice_allowed" -I alice@lab04 -n lab04-notice -s "$HOME/lab04/inbox/offer.sig" < "$HOME/lab04/inbox/offer.txt"
Explain these commands
  • The two ssh-keygen -lf calls print the public-key fingerprints. The fingerprint Bob confirmed with Alice earlier is the reference, not the filename alice.pub.
  • cmp -s silently compares exact file bytes. && executes the next command on success and || executes the alternative on failure. Even when two public-key files have different comments, the key fingerprint may remain the same; fingerprints focus on key material.
  • Now -f points to alice_allowed, Bob’s authentic key association. The same modified message and Mallory signature should FAIL under Alice’s key.
  • This is the security improvement: after Bob has established Alice’s public key, the intermediary can distribute later messages but cannot silently replace Alice’s signing identity.

Check: The fingerprints differ; verification with the earlier trusted key fails.

Question: Which command changed between the successful and failed verification attempts? The message and signature were identical. What did Bob stop trusting?

3. A valid message can still be old

This is a different failure. Mallory will not change the message or the signature at all. Instead, Mallory forwards an older notice after Alice has published a newer one.

13. Alice publishes two signed versions

Alice writes an initial instruction, then writes a newer one. Both are genuine messages signed with Alice’s private key.

Alice · working terminal
printf 'REVISION: 1\nDelivery hour: 14:00\n' > "$HOME/lab04/outbox/rev1.txt"
ssh-keygen -Y sign -f "$HOME/lab04/keys/dispatch" -n lab04-notice "$HOME/lab04/outbox/rev1.txt"
printf 'REVISION: 2\nDelivery hour: 17:00\n' > "$HOME/lab04/outbox/rev2.txt"
ssh-keygen -Y sign -f "$HOME/lab04/keys/dispatch" -n lab04-notice "$HOME/lab04/outbox/rev2.txt"
Explain these commands
  • printf creates two different messages. The revision numbers are ordinary message contents, not a feature of OpenSSH itself.
  • ssh-keygen -Y sign signs each file independently using Alice’s key and the same namespace.
  • rev1.txt.sig remains cryptographically valid even after rev2.txt.sig exists. Digital signatures do not automatically expire when a newer message appears.

14. Mallory forwards only revision 1

This time Mallory copies everything intact. Don’t edit any bytes, and don’t re-sign the file.

Mallory · working terminal
curl -fS --max-time 8 -o "$HOME/lab04/outbox/current.txt" http://ALICE_IP:8000/rev1.txt
curl -fS --max-time 8 -o "$HOME/lab04/outbox/current.txt.sig" http://ALICE_IP:8000/rev1.txt.sig
cat "$HOME/lab04/outbox/current.txt"
Explain these commands
  • curl -o saves Alice’s first revision under the name current.txt. That filename is only a claim.
  • Both the message and its signature are authentic, unchanged Alice files. Mallory’s attack is withholding the newer notice, not forging a signature.
  • cat displays what Bob will receive. The content says REVISION: 1, but Bob cannot know from this file alone whether revision 2 exists.

15. Bob verifies the old notice

Bob uses the already confirmed Alice key. No fake keys and no modified bytes this time.

Bob · working terminal
curl -fS --max-time 8 -o "$HOME/lab04/inbox/current.txt" http://MALLORY_IP:8000/current.txt
wget -q -O "$HOME/lab04/inbox/current.sig" http://MALLORY_IP:8000/current.txt.sig
ssh-keygen -Y verify -f "$HOME/lab04/trust/alice_allowed" -I alice@lab04 -n lab04-notice -s "$HOME/lab04/inbox/current.sig" < "$HOME/lab04/inbox/current.txt"
cat "$HOME/lab04/inbox/current.txt"
Explain these commands
  • curl and wget download the two intact older files from Mallory.
  • ssh-keygen -Y verify correctly returns success because Alice genuinely signed the exact bytes Bob received.
  • cat shows REVISION: 1. The word current in the filename provides no freshness guarantee.
  • A signature does not automatically tell Bob whether newer signed instructions exist. An application can add trusted timestamps, expiry rules, or monotonically increasing revision tracking, but must check them separately.

Check: Verification succeeds, even though Alice has published revision 2.

16. Only afterward, inspect Alice’s latest version

Alice now tells Bob that revision 2 exists. Bob fetches and verifies it separately, then compares what the notices say.

Bob · working terminal
curl -fS --max-time 8 -o "$HOME/lab04/inbox/rev2.txt" http://ALICE_IP:8000/rev2.txt
curl -fS --max-time 8 -o "$HOME/lab04/inbox/rev2.sig" http://ALICE_IP:8000/rev2.txt.sig
ssh-keygen -Y verify -f "$HOME/lab04/trust/alice_allowed" -I alice@lab04 -n lab04-notice -s "$HOME/lab04/inbox/rev2.sig" < "$HOME/lab04/inbox/rev2.txt"
diff -u "$HOME/lab04/inbox/current.txt" "$HOME/lab04/inbox/rev2.txt" || true
Explain these commands
  • The two curl calls fetch Alice’s later message and its signature. This is extra information obtained after the old notice passed verification.
  • ssh-keygen -Y verify should succeed for this newer pair too. A valid signature on revision 2 does not invalidate the old signature on revision 1.
  • diff -u shows the changed lines. || true allows the sequence to continue when diff returns a nonzero status because the files differ.
  • Unlike the first attack, diff here serves investigation after the fact. It is NOT the cryptographic verifier, and it needs both files.

Check: Both revisions have valid Alice signatures. The signature mechanism alone never chose which one was current.

Discuss these with your group:

  1. Can Bob detect Mallory’s first modification without seeing Alice’s original message? What does he not learn?
  2. How did Mallory make verification succeed in the second attack? What did Bob need to establish independently?
  3. Why is Alice’s public key safe to share, while her private key is not?
  4. Could the final old-but-valid notice be rejected automatically? What extra rule or information would Bob need?

For each, write one sentence explaining what Bob actually proved. Do not submit private key files.

When finished, return to the server terminals and press Ctrl+C. Then run this local check:

Each VM · working terminal · after Ctrl+C
curl -fS --max-time 3 -I http://127.0.0.1:8000/ || echo 'The test server is not responding'
Explain these commands
  • Ctrl+C sends an interrupt to the Python server and normally stops it.
  • curl -I requests HTTP response headers instead of the full body. 127.0.0.1 tests the same VM.
  • || echo ... prints a short note when the request fails. If the request succeeds, another server may still be listening on port 8000.

These signature commands use OpenSSH. See the ssh-keygen manual for -Y sign, -Y verify, and the allowed-signers format.
