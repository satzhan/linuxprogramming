Two locks, one delivery

A public lock for a small secret. A symmetric lock for the whole message. And one more test to catch an altered parcel.

The central problem

Why carry two locks?

In Lab 03, GPG encrypted messages without showing its internal mechanism. This lab opens the machine: encrypt a big file with AES, protect the small AES key with RSA, and check that the encrypted file was not changed.

Large message → AES-256-CTRA fresh, secret symmetric key turns the document into ciphertext.
Small keys → RSA-OAEPThe recipient’s public key protects the AES key and the HMAC key for delivery.

One more piece: an HMAC tag lets the recipient detect changes to the ciphertext before opening it. Think of a locked chest and a sealed record of what was packed. A lock hides the contents; the seal helps reveal alterations.

Classroom construction. We are manually assembling AES-CTR, RSA-OAEP and HMAC-SHA256 so you can see what each piece does. For real secrets, use a maintained encryption tool or protocol with authenticated encryption. These training keys are disposable; do not put real secrets in these files.

Create a public/private RSA key pair

Generate the private key

Generate the private key

Dispatch 01 · The archive

The report that will not fit

Alice needs to get a long incident report to Bob. She has Bob’s public key. Why not encrypt the entire report using RSA?

That sounds reasonable until the first command fails. The failure reveals why public-key encryption and symmetric encryption have different jobs.

Alice · the failed idea

Try the obvious solution first

Alice runs this experiment. Bob can watch the report size and predict whether RSA will accept it.

Write a long report

A Bash loop creates 300 short lines. This is intentionally much larger than one RSA encryption block.

Write a long report
for i in {1..300}; do echo "Inspection $i: all doors checked."; done > "$ROOT/work/01-report.txt"

This is a single Bash for command. > writes its output to a file.

Measure the input

Check how many bytes are in the report.

Measure the input
wc -c "$ROOT/work/01-report.txt"
Try direct RSA encryption

Ask OpenSSL to encrypt the entire report with Bob’s public key. An error is the expected observation.

Try direct RSA encryption
openssl pkeyutl -encrypt -pubin -inkey "$ROOT/inbox/bob.pub.pem" -in "$ROOT/work/01-report.txt" -out "$ROOT/work/01-direct.rsa" -pkeyopt rsa_padding_mode:oaep -pkeyopt rsa_oaep_md:sha256 -pkeyopt rsa_mgf1_md:sha256

For 3072-bit RSA with OAEP/SHA-256, the maximum message is 318 bytes, far smaller than this report. Direct RSA is not a large-file cipher.

Why this works / what the options mean
-pubin says the input is a public key; OAEP with SHA-256 pads the small message safely for RSA encryption. -pkeyopt rsa_mgf1_md:sha256 keeps the mask-generation hash consistent.
What failed? The report is not corrupted. RSA is not broken. We asked it to encrypt more bytes than its operation permits. Keep the large file; use RSA for a small secret instead.
Alice · now build a proper envelope

Generate the keys, encrypt the report, and publish the parcel

Each short command does one job. Look at the new file it creates before continuing.

Make an encryption key

Generate a fresh 32-byte random AES key. Save it locally as hexadecimal text.

Make an encryption key
openssl rand -hex 32 > "$ROOT/work/01-enc.hex"

The file is secret. Do not put it in the public HTTP directory.

Make an integrity key

Generate a different random key for HMAC.

Make an integrity key
openssl rand -hex 32 > "$ROOT/work/01-mac.hex"

A distinct HMAC key prevents the encryption and integrity checks from sharing the same key material.

Make an IV

Generate a 16-byte starting value for AES-CTR.

Make an IV
openssl rand -hex 16 > "$ROOT/work/01.iv"

This is not a password or private key. It will travel with the ciphertext.

Load the values

These are Bash assignments. They read the three small files into variables that subsequent commands use.

Load the values
ENC_KEY=$(cat "$ROOT/work/01-enc.hex")
MAC_KEY=$(cat "$ROOT/work/01-mac.hex")
IV=$(cat "$ROOT/work/01.iv")

No new files are created by these assignments. The variables remain in this terminal session.

Prepare the small key packet

The two secret keys are placed in a tiny two-line file. RSA will protect this file, not the large document.

Prepare the small key packet
printf '%s\n%s\n' "$ENC_KEY" "$MAC_KEY" > "$ROOT/work/01.keys"

Line 1 is the AES key; line 2 is the HMAC key. This plaintext packet is strictly local.

Encrypt the actual message

The large file becomes ciphertext. It does not need to fit inside an RSA operation.

Encrypt the actual message
openssl enc -aes-256-ctr -e -K "$ENC_KEY" -iv "$IV" -in "$ROOT/work/01-report.txt" -out "$ROOT/work/01.enc"

The output file is unreadable without the AES key. Its size will be close to the plaintext size.

Why this works / what the options mean
AES-256-CTR encrypts the data using a 32-byte key and a 16-byte counter starting value (IV). The IV need not be secret, but should be fresh for each use of the key.
Create the integrity tag

Calculate HMAC over the IV followed by the ciphertext. The recipient will calculate this same value before decrypting.

Create the integrity tag
{ cat "$ROOT/work/01.iv"; cat "$ROOT/work/01.enc"; } | openssl dgst -sha256 -mac HMAC -macopt "hexkey:$MAC_KEY" -binary > "$ROOT/work/01.tag"

The tag can be public; the secret HMAC key cannot. Changing the ciphertext or IV will change the expected tag.

Why this works / what the options mean
The braces stream both inputs in order. -binary saves raw 32-byte HMAC output. The hexkey: option tells OpenSSL to interpret the 64 hex characters as 32 key bytes.
Wrap the keys for Bob

Use Bob’s public RSA key to encrypt the small two-line key packet.

Wrap the keys for Bob
openssl pkeyutl -encrypt -pubin -inkey "$ROOT/inbox/bob.pub.pem" -in "$ROOT/work/01.keys" -out "$ROOT/work/01.bob.rsa" -pkeyopt rsa_padding_mode:oaep -pkeyopt rsa_oaep_md:sha256 -pkeyopt rsa_mgf1_md:sha256

Only the matching private key can unwrap 01.bob.rsa. The sender never needs the recipient’s private key.

Why this works / what the options mean
-pubin says the input is a public key; OAEP with SHA-256 pads the small message safely for RSA encryption. -pkeyopt rsa_mgf1_md:sha256 keeps the mask-generation hash consistent.

Recover the small secret packet

Load the recovered keys

Read the AES key and HMAC key separately from the two-line packet. Read the public IV too.

The first two assignments read secrets; avoid showing their values on screen or in screenshots.

Calculate a fresh HMAC

Run the same HMAC operation on the received IV and ciphertext.

Calculate a fresh HMAC
{ cat "$ROOT/received/01/01.iv"; cat "$ROOT/received/01/01.enc"; } | openssl dgst -sha256 -mac HMAC -macopt "hexkey:$MAC_KEY" -binary > "$ROOT/received/01/check.tag"

Your result is check.tag. Compare it with the tag included in the package.

Verify, then decrypt

This one shell decision decrypts only when the tags match.

Verify, then decrypt
if cmp -s "$ROOT/received/01/01.tag" "$ROOT/received/01/check.tag"; then
  openssl enc -aes-256-ctr -d -K "$ENC_KEY" -iv "$IV" -in "$ROOT/received/01/01.enc" -out "$ROOT/received/01/01-opened.txt"
  echo "Verified and decrypted."
else
  echo "HMAC mismatch: do not decrypt."
fi

If a comparison fails, no decryption command runs. AES-CTR by itself would not recognize a modified ciphertext.

Read the recovered report

The file now contains the original 300 lines again.

Read the recovered report
head -n 4 "$ROOT/received/01/01-opened.txt"
Compare against Alice’s original

Alice can run the same hash command on the original report. Compare only the hash values, not the secret keys.

Compare against Alice’s original
sha256sum "$ROOT/received/01/01-opened.txt"

Bob’s recovered plaintext should hash to the same value as Alice’s original file.

Alice’s comparison hash

Run this on Alice’s VM.

Alice’s comparison hash

First discovery: AES can process the big file. RSA transports the small secret keys. A public archive is safe to distribute only because the necessary secret keys were not included in plaintext.

Change exactly one bit

Python changes one byte in the ciphertext. The original HMAC tag is intentionally untouched.

Change exactly one bit

The operation ^=1 flips one bit. Because we are changing ciphertext rather than plaintext, the edit is invisible to someone merely reading its contents.

Dispatch 03 · The shared notice

One ciphertext, two readers

A closure notice is meant for Alice and Bob. Instead of encrypting the large document twice, one person can encrypt it once and wrap the same small keys separately for each reader.

Alice prepares the notice for herself and Bob. She is allowed to be a recipient of a package she creates; it shows that recipient access depends on which public keys were included.

Mallory prepares a shared notice for Alice and Bob. They use different private RSA keys but recover the same AES key and therefore the same plaintext.

Prepare the small key packet

The two secret keys are placed in a tiny two-line file. RSA will protect this file, not the large document.

Prepare the small key packet

Line 1 is the AES key; line 2 is the HMAC key. This plaintext packet is strictly local.

Encrypt the actual message

The large file becomes ciphertext. It does not need to fit inside an RSA operation.

Encrypt the actual message
openssl enc -aes-256-ctr -e -K "$ENC_KEY" -iv "$IV" -in "$ROOT/work/03-notice.txt" -out "$ROOT/work/03.enc"

The output file is unreadable without the AES key. Its size will be close to the plaintext size.

Why this works / what the options mean
AES-256-CTR encrypts the data using a 32-byte key and a 16-byte counter starting value (IV). The IV need not be secret, but should be fresh for each use of the key.
Create the integrity tag

Calculate HMAC over the IV followed by the ciphertext. The recipient will calculate this same value before decrypting.

Create the integrity tag
{ cat "$ROOT/work/03.iv"; cat "$ROOT/work/03.enc"; } | openssl dgst -sha256 -mac HMAC -macopt "hexkey:$MAC_KEY" -binary > "$ROOT/work/03.tag"

The tag can be public; the secret HMAC key cannot. Changing the ciphertext or IV will change the expected tag.

Why this works / what the options mean
The braces stream both inputs in order. -binary saves raw 32-byte HMAC output. The hexkey: option tells OpenSSL to interpret the 64 hex characters as 32 key bytes.
Wrap the keys for Alice

Use Alice’s public RSA key to encrypt the small two-line key packet.

Wrap the keys for Alice
openssl pkeyutl -encrypt -pubin -inkey "$ROOT/inbox/alice.pub.pem" -in "$ROOT/work/03.keys" -out "$ROOT/work/03.alice.rsa" -pkeyopt rsa_padding_mode:oaep -pkeyopt rsa_oaep_md:sha256 -pkeyopt rsa_mgf1_md:sha256

Only the matching private key can unwrap 03.alice.rsa. The sender never needs the recipient’s private key.

Why this works / what the options mean
-pubin says the input is a public key; OAEP with SHA-256 pads the small message safely for RSA encryption. -pkeyopt rsa_mgf1_md:sha256 keeps the mask-generation hash consistent.

Before you finish

Which lock solved which problem?

What worked in Lab 03 now has a visible mechanism. These tools solve different problems, so we need to keep their guarantees separate.

QuestionMechanism demonstrated
How do we encrypt many bytes?AES-256-CTR encrypts the document using a fresh symmetric key.
How does a recipient obtain that key?RSA-OAEP wraps the short AES and HMAC keys using the recipient’s public key.
How do we detect a changed ciphertext?HMAC-SHA256 checks IV + ciphertext before decryption.
How do we include two recipients?Wrap the same secret-key packet separately for each reader.
Who sent this package?Our construction does not establish sender identity. Lab 04’s digital signatures address that separate question when the verification key is trusted.
A subtle point. An attacker who can change the *entire* delivery can make a fresh AES key, fresh ciphertext, fresh HMAC, and a new RSA packet for your public key. The HMAC will match, yet this does not prove who sent it. Confidentiality, integrity, and sender authentication are different properties.
