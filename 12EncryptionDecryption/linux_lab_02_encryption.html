Linux together / Lab 02

The locked envelope

Anyone can take a copy. That does not mean everyone should be able to read it. So we send a locked envelope instead of a loose sheet of paper. Then we do something foolish with the key.

~60–75 minutesThree students · three VMsAES encryption using GPG

Three rounds. Each person takes a turn preparing a message, opening one, and trying a way around the protection. You will use gpg, curl, wget, file, cmp, and sha256sum. There is nothing to submit or write about during the exercise.

Prepare the three machines

Lab 02 starts from scratch. If you did Lab 01, fine. If not, also fine. All three need Ubuntu VMs that can reach each other on their private IP addresses. You need two SSH terminals per person: a working terminal and one for the file server.

On each student’s laptop if not already connected
ssh -p SSH_PORT YOUR_USER@AZURE_SSH_HOST
Everyone · VM working terminal
whoami
hostname -I
command -v python3
command -v curl
command -v wget
command -v gpg
mkdir -p "$HOME/lab02/served" "$HOME/lab02/private" "$HOME/lab02/received"
export GPG_TTY=$(tty)

The command -v lines tell you whether each program exists. gpg is the encryption program. GPG_TTY helps GPG know which SSH terminal should display its password prompts. If gpg is missing, and your lab VM permits installations, use the command below; otherwise ask the instructor to install gnupg on the VM, not on your laptop.

Only if gpg is missing, and you have sudo on your lab VM
sudo apt-get update
sudo apt-get install -y gnupg
Enter the three private IPv4 addresses
The commands fill in automatically, in this browser only. Replace A_IP, B_IP, C_IP manually if you prefer.
Everyone · second SSH terminal · keep this server running
python3 -m http.server 8000 --bind 0.0.0.0 --directory "$HOME/lab02/served"

Each VM serves files from ~/lab02/served. Keep the private folder out of that shelf. If an old server is already running on port 8000, stop your own previous server with Ctrl+C first.

Everyone · working terminal · check local connection
curl -I --max-time 5 http://127.0.0.1:8000/
Only invented data and practice passwords. In this lab someone will deliberately leak a practice password to show what happens. Never use a real login, school, or personal password. Do not type secrets into command-line arguments: they can end up in shell history or process listings.

When GPG asks for a passphrase, type it at the terminal prompt. You may not see any characters while typing. Press Enter. For encryption it may ask you to repeat the passphrase. If the terminal cannot open a passphrase prompt, try export GPG_TTY=$(tty) again in the working terminal.

Round 1 · A prepares

Everyone can download it

PreparesA
AttemptsB
ChallengesC

Alice has two messages: one anyone can read, one meant for Bob. She will publish both—but the second one goes into a locked envelope first. The envelope is not hidden. Everyone can take a copy.

A · create a private note and a public postcard

A · working terminal
printf "Weather is excellent.\n" > "$HOME/lab02/served/postcard-a.txt"
printf "A private fictional note meant for B.\n" > "$HOME/lab02/private/letter-a.txt"
chmod 600 "$HOME/lab02/private/letter-a.txt"
ls -l "$HOME/lab02/private/letter-a.txt"

A · encrypt the private note

A · working terminal
gpg --pinentry-mode loopback --no-symkey-cache --symmetric --cipher-algo AES256 -o "$HOME/lab02/served/letter-a.gpg" "$HOME/lab02/private/letter-a.txt"
ls -l "$HOME/lab02/served"
file "$HOME/lab02/served/letter-a.gpg"

--symmetric encrypts using a passphrase you choose. --cipher-algo AES256 explicitly selects AES-256. -o chooses the ciphertext filename. --no-symkey-cache prevents GPG from remembering this symmetric secret for subsequent commands. Choose a new practice passphrase and give it only to B in person, out of C’s hearing. Do not put it in the shared HTTP folder.

B · download both objects, but only one needs unlocking

B · working terminal
curl --max-time 5 http://A_IP:8000/postcard-a.txt
curl --max-time 5 -o "$HOME/lab02/received/letter-from-a.gpg" http://A_IP:8000/letter-a.gpg
file "$HOME/lab02/received/letter-from-a.gpg"
wc -c "$HOME/lab02/received/letter-from-a.gpg"

The postcard appears directly. The encrypted file is saved using curl -o. file tries to recognize its format. wc -c counts bytes. Encryption changes how the bytes are represented; it does not stop B from downloading them.

B · working terminal · enter A’s passphrase when prompted
gpg --pinentry-mode loopback --no-symkey-cache --output "$HOME/lab02/received/opened-letter-a.txt" --decrypt "$HOME/lab02/received/letter-from-a.gpg"
cat "$HOME/lab02/received/opened-letter-a.txt"

--decrypt opens the ciphertext using the passphrase. Notice that we gave the output file a different name from the encrypted input file.

C · take the same envelope without the password

C · working terminal
wget -O "$HOME/lab02/received/unknown-letter-a.gpg" http://A_IP:8000/letter-a.gpg
file "$HOME/lab02/received/unknown-letter-a.gpg"
od -An -tx1 -N 32 "$HOME/lab02/received/unknown-letter-a.gpg"

wget -O downloads to a chosen filename. od prints the first 32 bytes in hexadecimal. These bytes are data, not a readable letter. C can also try gpg --decrypt with a deliberately wrong practice passphrase. It should fail; a short easily guessed passphrase would be another story.

C · working terminal · deliberately enter an incorrect passphrase
gpg --pinentry-mode loopback --no-symkey-cache --output "$HOME/lab02/received/not-opened-a.txt" --decrypt "$HOME/lab02/received/unknown-letter-a.gpg"
A private file was delivered over an open server. The encryption protected its contents, not its availability. Anyone with the correct passphrase can read it—including C, if C learns that passphrase. The file was not authenticated as coming from Alice, either.
Round 2 · B prepares

Two wrappers, then a damaged one

PreparesB
AttemptsC
ChallengesA

This time Bob prepares one message in two kinds of encrypted wrapper. Same idea, different appearance. After C opens both, A will damage a copy in transit—not by spying on traffic, just by sending C an altered file.

B · make a new secret and two ciphertext formats

B · working terminal
printf "Route B: depot 4, arrival 09:30.\n" > "$HOME/lab02/private/route-b.txt"
gpg --pinentry-mode loopback --no-symkey-cache --symmetric --cipher-algo AES256 -o "$HOME/lab02/served/route-b.gpg" "$HOME/lab02/private/route-b.txt"
gpg --pinentry-mode loopback --no-symkey-cache --armor --symmetric --cipher-algo AES256 -o "$HOME/lab02/served/route-b.asc" "$HOME/lab02/private/route-b.txt"
ls -lh "$HOME/lab02/served/route-b."*

Use the same new practice passphrase for both encryptions, and give it only to C. --armor stores encrypted data as printable text, hence the .asc name; without it, .gpg holds a binary representation. Both are encrypted. ASCII-looking does not mean readable plaintext.

C · receive and open both versions

C · working terminal
wget -qO- http://B_IP:8000/route-b.asc | head -n 5
wget -O "$HOME/lab02/received/route-binary.gpg" http://B_IP:8000/route-b.gpg
curl --max-time 5 -o "$HOME/lab02/received/route-armored.asc" http://B_IP:8000/route-b.asc

The first command pipes a portion of an ASCII-armored ciphertext to head; you can read the format header but not the message. The second and third commands save the two different files locally.

C · working terminal · enter the passphrase B gave you
gpg --pinentry-mode loopback --no-symkey-cache -o "$HOME/lab02/received/route-from-binary.txt" --decrypt "$HOME/lab02/received/route-binary.gpg"
gpg --pinentry-mode loopback --no-symkey-cache -o "$HOME/lab02/received/route-from-armor.txt" --decrypt "$HOME/lab02/received/route-armored.asc"
cmp "$HOME/lab02/received/route-from-binary.txt" "$HOME/lab02/received/route-from-armor.txt"
cat "$HOME/lab02/received/route-from-armor.txt"

cmp compares two files byte by byte; no output means the two decrypted messages match. The encryption format changed, not the message.

A · damage the binary copy, then publish the damaged file

A · working terminal
curl --max-time 5 -o "$HOME/lab02/received/original-route-b.gpg" http://B_IP:8000/route-b.gpg
head -c -16 "$HOME/lab02/received/original-route-b.gpg" > "$HOME/lab02/served/damaged-route-b.gpg"
sha256sum "$HOME/lab02/received/original-route-b.gpg" "$HOME/lab02/served/damaged-route-b.gpg"

Here head -c -16 keeps every byte except the last 16. The damaged file is shorter. sha256sum produces fingerprints of byte contents; different hashes confirm these copies are not the same. We have not cracked encryption. We have broken the envelope.

C · receive the damaged file and try to open it

C · working terminal
curl --max-time 5 -o "$HOME/lab02/received/damaged-route-b.gpg" http://A_IP:8000/damaged-route-b.gpg
gpg --pinentry-mode loopback --no-symkey-cache -o "$HOME/lab02/received/damaged-output.txt" --decrypt "$HOME/lab02/received/damaged-route-b.gpg"
rm -f "$HOME/lab02/received/damaged-output.txt"

GPG should report a failure because the encrypted data is truncated. It may nevertheless write some plaintext before reporting the error. Never use an output from an operation that failed integrity verification. The final rm -f discards any partial output.

Different problem, different test. A hash detects that two copies differ if you already trust the expected hash. Decryption with modern GPG can also detect altered ciphertext. Neither fact, by itself, proves who wrote the original message.
Round 3 · C prepares

The file is safe. The password is not.

PreparesC
AttemptsA
ChallengesB

C finishes with a perfectly encrypted file—and then makes the mistake people make all the time. The password travels by the same open route as the protected file.

C · encrypt the last fictional document

C · working terminal
printf "C's practice secret: red bicycle at the library.\n" > "$HOME/lab02/private/last-note-c.txt"
chmod 600 "$HOME/lab02/private/last-note-c.txt"
gpg --pinentry-mode loopback --no-symkey-cache --symmetric --cipher-algo AES256 -o "$HOME/lab02/served/sealed-note-c.gpg" "$HOME/lab02/private/last-note-c.txt"
ls -l "$HOME/lab02/served/sealed-note-c.gpg"

Choose a new practice passphrase, not the one from earlier rounds. Let only A know it, using an out-of-band conversation. Do not use a real account password.

A · download and decrypt; B · download but cannot yet decrypt

A · working terminal
curl --max-time 5 -o "$HOME/lab02/received/sealed-from-c.gpg" http://C_IP:8000/sealed-note-c.gpg
gpg --pinentry-mode loopback --no-symkey-cache -o "$HOME/lab02/received/opened-from-c.txt" --decrypt "$HOME/lab02/received/sealed-from-c.gpg"
cat "$HOME/lab02/received/opened-from-c.txt"
B · working terminal
wget -O "$HOME/lab02/received/locked-from-c.gpg" http://C_IP:8000/sealed-note-c.gpg
file "$HOME/lab02/received/locked-from-c.gpg"

So far, C has shared only the encrypted document. B has it, but without the secret, B cannot simply read it.

C · now publish the practice password beside the encrypted file

C · working terminal · re-enter the same Round 3 passphrase
read -r -s -p "Type your ROUND 3 PRACTICE passphrase: " LEAK
printf "\n"
printf "%s\n" "$LEAK" > "$HOME/lab02/served/round3-password.txt"
unset LEAK
ls -l "$HOME/lab02/served"

The read -s command hides keystrokes while you enter the password, but then printf places the password in a publicly served text file. unset clears the shell variable; it does not remove the published file. Anyone able to reach the server can request it.

B · get the password and open the same encrypted file

B · working terminal
curl --max-time 5 -o "$HOME/lab02/received/password-from-c.txt" http://C_IP:8000/round3-password.txt
cat "$HOME/lab02/received/password-from-c.txt"
gpg --pinentry-mode loopback --no-symkey-cache -o "$HOME/lab02/received/now-open-c.txt" --decrypt "$HOME/lab02/received/locked-from-c.gpg"
cat "$HOME/lab02/received/now-open-c.txt"

When GPG prompts, B types the practice passphrase copied from the public file. No brute-force guessing was needed. The cryptography did its job. The password handling undid it.

C removes the published password. B still has a copy.

C · working terminal
rm "$HOME/lab02/served/round3-password.txt"
ls -l "$HOME/lab02/served"
B · working terminal
cat "$HOME/lab02/received/password-from-c.txt"
curl -i --max-time 5 http://C_IP:8000/round3-password.txt

The server now responds 404 for the old password URL. B’s previously downloaded password remains. Removing the original does not recall existing copies. And neither symmetric encryption nor this little HTTP server decides who should receive the secret.

The limit of this lab: symmetric encryption requires the sender and recipient to share the same secret. Getting that secret to the right person is a separate problem. A future lab can solve it differently with public and private keys.
Finish

Close the servers and clear the practice files

Stop the HTTP servers with Ctrl+C on each VM. These were practice passwords, but the last round deliberately put one in a downloadable file. Remove the practice files when you finish.

Everyone · working terminal · inspect, then clean only this lab folder
ls -la "$HOME/lab02/served"
ls -la "$HOME/lab02/received"
ls -la "$HOME/lab02/private"
rm -r "$HOME/lab02"

We did not store passphrases as shell command arguments or files except for C’s deliberately exposed practice password. GPG may maintain other ordinary local configuration inside your user account; this exercise does not erase your general GPG configuration.
