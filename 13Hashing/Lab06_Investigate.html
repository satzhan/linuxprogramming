Lab 06 · Did the file change?

Someone sends you a file. How do you know whether it is the same file they sent before?

Work on two different Linux VMs. One person uses VM A, another uses VM B. With three students, the third can check the results independently on a third VM, then compare findings. Do not use two terminals on one VM as a substitute for two machines.

Most of the commands are yours to write. The examples show how a command is built, usually with a different filename. Choose the names and values the problem calls for. Open a hint when you need it.

Follow one task at a time. On VM A, you may need a second terminal for editing while the web server runs in the first.

VM A

Put your work in one folder.

We will turn this folder into a tiny download site. Keep it separate from your other files.

Command to run
mkdir -p ~/lab06-share
Need a little help?

This is setup, so the command is supplied. -p also avoids an error if the folder already exists.

What should I notice?

A folder named lab06-share now exists in your home directory.

VM A

Enter that folder.

The server will publish files from whichever folder it is started in.

Command to run
cd ~/lab06-share
Need a little help?

cd changes the current folder. You can confirm it using pwd.

What should I notice?

Running pwd should end with /lab06-share.

VM A

Write a file worth checking.

Create release.txt with two lines: a version number and a short announcement written by your group. Your teammate should not know exactly what you wrote yet.

Example or command shape
Example for another file: printf 'Status: ready\n' > sample.txt
Or edit with nano sample.txt.
Need a little help?

Replace sample.txt with your filename. > saves the output in a file; \n adds a newline. With nano, save using Ctrl+O, Enter, then Ctrl+X.

What should I notice?

Use cat release.txt. Is it actually two lines? That is more important than how you wrote it.

VM A

Make a record of the file as it exists now.

Run SHA-256 on release.txt, but put the result in a separate file named release.sha256. You will send both files to VM B.

Example or command shape
Example: sha256sum sample.txt > sample.sha256
Need a little help?

The first name is the file being read. The name after > is where the result gets saved. sha256sum prints a digest followed by the original filename.

What should I notice?

Open release.sha256 with cat. It should contain a long digest and the name release.txt.

VM A

Make the file available over the network.

Start a web server here. Leave this terminal running. Use a second terminal on VM A for changes later. If port 8000 did not work in your earlier cross-VM exercises, use the port that did.

Command to run
python3 -m http.server 8000 --bind 0.0.0.0
Need a little help?

8000 is the port. 0.0.0.0 means the server listens on the VM's network interfaces; it is not the address to give your teammate. This simple server shares the current folder, so never start it in a folder containing private files.

What should I notice?

The terminal stays occupied, waiting for requests. This is normal. VM B must contact the VM's real address.

VM A

Tell VM B where your server lives.

In the second terminal on VM A, find the IPv4 address and tell your teammate which one belongs to this VM.

Command to run
hostname -I
Need a little help?

There may be more than one address. Use the one that worked in your previous VM-to-VM lab, or test which is reachable. The address and the port are two different pieces of information.

What should I notice?

VM B should have a real IPv4 address such as 10.x.x.x and the port number, not 0.0.0.0 and not localhost.

VM B

Choose where your downloads will go.

Make a receiver folder on your own VM and change into it. You know the two Linux commands for this; use the examples from VM A but choose the folder ~/lab06-received.

Example or command shape
Useful shapes: mkdir -p FOLDER   cd FOLDER
Need a little help?

The ~ symbol means your home directory. VM A and VM B have different filesystems even if the folder names are similar.

What should I notice?

Use pwd. You should be inside lab06-received on VM B, not on VM A.

VM B

Download the announcement.

Use wget to fetch release.txt from VM A. Save it locally as release.txt. You must supply VM A's address and port yourself.

Example or command shape
Command shape: wget -O LOCAL_NAME "http://ADDRESS:PORT/REMOTE_NAME"
Need a little help?

-O (capital letter O) chooses the name of the saved file. ADDRESS is VM A's IP. REMOTE_NAME is the file on VM A. This must be a genuine cross-VM request.

What should I notice?

Check the contents with cat. VM A's server terminal should also show a GET request.

VM B

Fetch the evidence separately.

Download release.sha256 from VM A as a second request. Change your previous wget command, rather than looking for a new one.

Example or command shape
Reuse the wget -O ... shape from the previous step.
Need a little help?

You are downloading a different file from the same server. Both the URL path and the local output name need to change.

What should I notice?

You should now have two files on VM B. Try ls to see them.

VM B

Ask Linux whether they agree.

The checksum file says what digest to expect. Use the check option of sha256sum against the checksum file. Do this before VM A changes anything.

Example or command shape
Example: sha256sum -c sample.sha256
Need a little help?

-c reads the digest and filename from the checksum file. It then hashes the named file on VM B and compares the two results.

What should I notice?

Expected: release.txt: OK. That means the received file matches this checksum; it does not establish that the publisher is trustworthy.

VM B

Keep something that will not change.

Save a copy of release.txt as first-release.txt. Save the current checksum as baseline.sha256. You will need both later. Make two separate cp commands.

Example or command shape
Example: cp draft.txt saved-draft.txt
Need a little help?

The first filename is the source, the second is the new copy. Notice that baseline.sha256 still contains the text release.txt, so it will check the current file with that name.

What should I notice?

Use ls. You should have four files: two current files and two saved references.

VM A

Change the announcement without changing the checksum.

Use the second terminal on VM A. Edit only release.txt: change the version number and at least one word. Do not touch release.sha256. Do not tell VM B what changed.

Example or command shape
Use the same editing method as earlier: nano FILE or printf ... > FILE.
Need a little help?

The server reads from disk for each new request. You do not need to restart it after editing a file.

What should I notice?

Have VM B fetch the file again before revealing what you changed.

VM B

Fetch the same filename again.

Download release.txt again, overwriting the local copy. Before you check it, predict: will it still match baseline.sha256?

Example or command shape
Reuse your earlier wget command for the announcement.
Need a little help?

With wget -O, the specified local file is replaced. The old copy is safe under first-release.txt.

What should I notice?

You should see a new request on VM A. The filename is the same, but the bytes may not be.

VM B

Check against what you kept.

Use sha256sum to check the newly downloaded release.txt against baseline.sha256. Do not download a new checksum yet.

Example or command shape
Command shape: sha256sum -c CHECKSUM_FILE
Need a little help?

If your command returns FAILED, that is the expected finding, not a command error. The old reference describes different file contents.

What should I notice?

Explain to the teammate on VM A what you know and what you do not know. Can the hash tell you which word changed?

VM B

Find out what changed.

Now use the saved text and the new text. Try diff -u to find the changed lines, then cmp to find where the first differing byte occurs.

Example or command shape
Shapes: diff -u OLD_FILE NEW_FILE and cmp OLD_FILE NEW_FILE
Need a little help?

diff is useful for readable text: - marks an old line and + a new one. cmp stops at the first differing byte. A SHA-256 digest cannot tell you which word was changed.

What should I notice?

Ask the sender what they changed. Did your diff output agree?

VM A

Update the checksum to describe the new version.

The announcement has already changed. Now replace release.sha256 with a SHA-256 record of the current release.txt.

Example or command shape
Reuse the sha256sum FILE > CHECKSUM_FILE pattern.
Need a little help?

This makes the new checksum consistent with the edited file. It does not prove the change was approved by anyone.

What should I notice?

Tell VM B only that the checksum was updated, not that the change is trustworthy.

VM B

Can both checks be right?

Download only release.sha256 again. Check the current announcement once against the updated checksum and once against the saved baseline.sha256.

Example or command shape
Reuse wget -O ..., then run sha256sum -c CHECKSUM_FILE twice with different checksum filenames.
Need a little help?

If the current file matches the new checksum, it will say OK. It should still fail against the saved baseline. These results are not contradictory: the expected references differ.

What should I notice?

Ask your group: if somebody replaced both the file and its checksum, would the new pair also say OK? How could you know which checksum to trust?

What did the checks prove?

Explain to one another why the same downloaded file can fail against the first checksum and pass against the new one. A checksum tells you whether a file matches a particular record. It does not tell you who was allowed to change that record.

Submit enough evidence to show three things: the first successful check, the failed check after the file changed, and the two different results when you compared against the old and new checksums. Include one short explanation in your own words and say what each person tested. You decide how many screenshots to use.

If the download does not work

First ask: is VM A's server still running? Did VM B use VM A's address rather than localhost? Are both using the same port? Check the server terminal for a request. If there is no request, the network route or port may be blocked. Use the cross-VM connection method and port you verified in Lab 00. A timeout is different from a 404 response: 404 means the server answered but cannot find the file in its shared folder.

Finish on VM A

In the server terminal, press Ctrl+C to stop sharing the practice folder.
