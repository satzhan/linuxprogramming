Lab 06 · Did the file change?

One Linux machine sends a file. Another receives it. How can the receiver tell whether it has the same information the sender originally published?

Use two different Azure Linux VMs, not two windows into the same VM. Work with a teammate: one operates VM A; the other operates VM B. With three people, VM C can repeat the receiver’s checks independently. Change who types as you go.

You will send a real file with wget, change the file on VM A, and see what Linux can—and cannot—tell you from a checksum.

→
VM Bdownloads; checks the file
Keep this page open on each computer. Reveal and run one command at a time. Commands marked VM A run only on the sender’s VM; commands marked VM B run only on the receiver’s VM.
01

1. Put a real file on VM A

Linux can send files across a network without a graphical interface. Here VM A will run a small web server. VM B will ask that server for a file, just as a browser asks a website for a page.

A hash is a short result calculated from a file’s contents. SHA-256 gives us a 64-character hexadecimal result. Equal contents give equal SHA-256 hashes, regardless of filename. A different hash means the contents differ.

VM AMake a folder to hold only the files you intend to share.
mkdir -p ~/lab06-share
Why this command?

The web server will serve files from the folder where you start it. Keeping the practice files in one folder avoids sharing unrelated files.

VM AEnter that folder.
cd ~/lab06-share
Why this command?

cd changes the directory used by the following commands.

VM AWrite a short note.
printf 'Meeting: Friday 10:00\n' > note.txt
Why this command?

printf produces the text. \n adds a newline. > saves the output in a file, replacing older contents.

VM ASave the SHA-256 hash of the note.
sha256sum note.txt > note.sha256
Why this command?

sha256sum reads the bytes of note.txt. The > stores its result in note.sha256. This second file contains the expected hash and the filename to check.

VM ALook at the saved hash.
cat note.sha256
Why this command?

The long sequence is the hash; note.txt at the end is the filename the check command will later read. The hash is not the original text and is not encrypted text.

VM AFind VM A’s private IP address.
hostname -I
Why this command?

You may see more than one address. Use the IPv4 address reachable by the other Azure VM, often beginning with 10.. It is the address for VM B to contact, not 127.0.0.1.

VM AStart a server and leave this terminal running.
python3 -m http.server 8000 --bind 0.0.0.0
Why this command?

8000 is the listening port. 0.0.0.0 tells the server to accept connections on its network interfaces. Other students connect using VM A’s actual IP address, not 0.0.0.0. This is an unencrypted practice server; share no secrets.

VM A is now serving a real file. Do not close the server terminal. When VM B downloads the note, this terminal should print a request such as GET /note.txt.

Later you will edit the file on VM A. Open a second terminal to the same VM A for those edits; you can use the same account. Keep the server running in the first terminal.

02

2. Download it on VM B

Move to a different Linux VM. It must not be another terminal on VM A. A local copy would not tell us whether we can really transfer anything between two computers.

wget makes a network request and writes the response to a file. Then Linux can compare the downloaded file with the hash supplied by VM A.

VM BMake a receiving folder.
mkdir -p ~/lab06-received
Why this command?

This folder is on VM B, not VM A. Each VM has its own files.

VM BWork inside that folder.
cd ~/lab06-received
Why this command?

Subsequent downloads and checks happen here.

VM BEnter the IPv4 address your teammate found on VM A.
read -r -p 'VM A IPv4 address: ' SERVER_IP
Why this command?

Type the address and press Enter. The shell stores it in SERVER_IP. Keep using this terminal so the variable remains set.

VM BDownload the actual note over the network.
wget -O note.txt "http://$SERVER_IP:8000/note.txt"
Why this command?

wget contacts VM A. -O note.txt chooses the local filename and overwrites it if it exists. Watch the server terminal on VM A: it should log the request.

VM BDownload the saved hash as a separate file.
wget -O note.sha256 "http://$SERVER_IP:8000/note.sha256"
Why this command?

Now VM B has both a downloaded file and the hash file supplied by the server. They are two separate network transfers.

VM BRead the received note.
cat note.txt
Why this command?

You should see the meeting time. Notice that reading the file and checking its hash answer different questions.

VM BAsk Linux whether the downloaded note matches the downloaded hash.
sha256sum -c note.sha256
Why this command?

-c means check. Linux reads the hash stored in note.sha256, recalculates the hash of note.txt, and compares them. Expect note.txt: OK.

VM BKeep the first hash as a record of the original download.
cp note.sha256 baseline.sha256
Why this command?

We need a reference that does not change when VM A publishes a new hash. The name is different, but the checksum file still tells Linux to check note.txt.

VM BKeep the first note so you can later see the exact difference.
cp note.txt original.txt
Why this command?

This is an ordinary copy. The filename differs but the contents match for now.

What does OK mean? It means these particular file bytes match this particular saved hash. Both came from VM A. The check does not yet tell us whether VM A is trustworthy, whether the note is true, or whether it was changed before you downloaded it.

03

3. Change the file; test the check again

Imagine the meeting time changes. The person on VM A edits the note, but forgets to update the published checksum. VM B downloads the new version. Can Linux spot that it no longer agrees with the old record?

VM AIn a second VM A terminal, return to the shared folder.
cd ~/lab06-share
Why this command?

Leave the first terminal running the server. This terminal is only for editing the shared file.

VM AChange the meeting time.
printf 'Meeting: Friday 11:00\n' > note.txt
Why this command?

This changes the actual file being served. We have not edited note.sha256, so it still describes the 10:00 version.

VM BDownload the note again from VM A.
wget -O note.txt "http://$SERVER_IP:8000/note.txt"
Why this command?

Because -O overwrites note.txt, VM B now has the 11:00 version. original.txt still contains the 10:00 version.

VM BCheck against the original saved hash.
sha256sum -c baseline.sha256
Why this command?

Expect FAILED. The same name now refers to bytes that differ from the version you first saved. The command’s nonzero exit status is normal here.

VM BSee what changed, instead of only knowing that something changed.
diff -u original.txt note.txt
Why this command?

The line beginning with - came from the original file; the line beginning with + came from the new one. A difference is expected.

VM BCompare the same two files byte by byte.
cmp original.txt note.txt
Why this command?

cmp usually reports the location of the first differing byte. It prints nothing if two files are identical.

VM BTry MD5 hashes for the same files.
md5sum original.txt note.txt
Why this command?

MD5 also notices this ordinary edit. But MD5 has known collision attacks: someone can deliberately construct different inputs with the same MD5 hash. Use SHA-256 for integrity checks against deliberate manipulation.

VM ANow update the published checksum to match the changed note.
sha256sum note.txt > note.sha256
Why this command?

The note is still the 11:00 version. The checksum file on VM A now describes the new version.

VM BDownload the new checksum.
wget -O note.sha256 "http://$SERVER_IP:8000/note.sha256"
Why this command?

This replaces VM B’s current checksum with the one VM A just published. Your older baseline.sha256 is still unchanged.

VM BCheck with the new checksum.
sha256sum -c note.sha256
Why this command?

Expect OK. The updated note matches the updated checksum.

VM BCheck the very same note against the first checksum.
sha256sum -c baseline.sha256
Why this command?

Expect FAILED. Both results are correct: the new checksum describes the new note, while the old checksum describes the old note.

The important distinction: A hash checks agreement with a reference. It does not tell you why a file changed. A new meeting time could be a legitimate edit or a dishonest replacement.

If someone can replace both a file and the published checksum, a fresh download of both may still produce OK. To know who authorized the file, you need a reference you trust—for example, an authenticated digital signature, as in the earlier security lab.

If VM B cannot download the file

First confirm both students are on different VMs. On VM A, is the Python server still running? Does hostname -I show the address entered on VM B? Is the server started from ~/lab06-share?

If the connection is refused or times out, check on VM A with ss -ltn | grep :8000. If it is listening but VM B still cannot reach it, Azure networking or a VM firewall may block the connection. Ask the instructor to check the allowed VM-to-VM route/port; do not replace the transfer with a local cp. A 404 response usually means the requested file is not in the server’s folder.

This is ordinary, unencrypted HTTP on the lab network: do not serve passwords or private documents. When finished, return to VM A’s server terminal and press Ctrl+C to stop sharing.
