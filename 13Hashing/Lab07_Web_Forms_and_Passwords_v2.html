Lab 07 · A website on your Linux VM

Our browser is on one computer. Our website runs on another. First make the connection work. Then see what a password form actually sends, and what the server does with it.

Use different Azure Linux VMs. One student operates VM A (the server) and opens its page in a browser on that student’s own laptop through SSH. A second student uses VM B for curl; with three students, the third uses VM C for independent requests. Do not share SSH passwords. If you switch which VM hosts the server, its owner creates the new browser tunnel.

Work through the actions one at a time. The command examples are often shapes for you to complete, not a full transcript to paste. Open the explanations when you need them. Only use made-up passwords here.

VM A · terminal 1

Make one small page

On the VM that will serve the website, put a harmless page in a new folder. It will give us something recognizable to open before we deal with Flask.

Run these setup commands.
mkdir -p ~/lab07
cd ~/lab07
printf 'Hello from our Linux VM\n' > index.html
Why this works

The > symbol puts the output into a file. Here index.html contains a single line; no special HTML knowledge is needed yet.

VM A · terminal 1

Start sharing that folder

Run a tiny HTTP server. Leave this terminal open. It should look as though it is waiting, because it is.

Run this command.
python3 -m http.server 8000 --bind 0.0.0.0
Why this works

8000 is the port. 0.0.0.0 means the server listens on the VM’s IPv4 interfaces. This is a listening setting, not the address another student types. Only the practice folder should be shared.

VM A · terminal 2

Find the address of VM A

Open a second terminal on VM A. Find its private IPv4 address and share it with the other students. Leave the server running in terminal 1.

Use the IP that worked in the earlier cross-VM lab.
hostname -I
Why this works

You may see more than one address. A typical private address starts with 10.. VM B needs VM A’s address, not its own.

VM B · terminal

Read the website without a browser

From a different Linux VM, ask for the page using curl. Substitute VM A’s IP address. Then try requesting just the response headers.

These are command shapes: replace VM_A_IP. Try both.
curl http://VM_A_IP:8000/
curl -I http://VM_A_IP:8000/
Why this works

curl prints the response body. curl -I requests headers, where a successful HTTP response normally says 200 OK. VM A should log the requests.

If it doesn’t work

If you get Connection refused, check that the server is running. If it times out, ask whether the VMs can communicate on this port; use the network arrangement already verified in Lab 00. Do not substitute localhost for VM A.

VM A owner · laptop terminal

Open a tunnel to the server

The student who owns VM A uses their own laptop, not a teammate’s SSH credentials. In Azure Lab Services choose Connect via SSH for VM A and look at the SSH command it gives you. Keep its username, public hostname, and SSH port; insert the forwarding options shown below. Run this on the laptop (Terminal or PowerShell), not inside a VM.

Replace SSH_PORT, USER, and AZURE_HOST using the actual Azure SSH command. Leave this terminal open.
ssh -N -p SSH_PORT -L 127.0.0.1:8765:127.0.0.1:8000 USER@AZURE_HOST
Why this works

The laptop listens on 127.0.0.1:8765, sends requests through SSH, and reaches port 8000 on VM A. -N means no remote shell will open. This is not X forwarding.

If it doesn’t work

If your normal SSH command already has a port such as -p 5037, keep that value. If forwarding is not permitted, the lab VM or SSH server may need a settings change; use the working cross-VM curl test while resolving it.

VM A owner · laptop browser

Open the Linux page in a local browser

In Chrome, Edge, or Firefox on your laptop, visit the address below. Then have the student on VM A change the greeting in index.html and save it. Refresh the browser. This shows whose files the browser is actually displaying.

This is a browser address, not a terminal command.
http://127.0.0.1:8765/
Why this works

Here 127.0.0.1 means the laptop, where the SSH tunnel is listening. Through the tunnel it reaches VM A. You should see the changed greeting after refreshing.

If it doesn’t work

If it does not open, check that both the HTTP server and the SSH tunnel are still running, then check whether the local port 8765 is already being used.

VM A · terminal 1

Replace the tiny server with Flask

Stop the current server with Ctrl+C in VM A terminal 1. Stay in that same terminal for the commands below: its virtual environment will be needed when we run Flask. We will reuse port 8000, so the browser tunnel can stay open.

Run these setup commands one line at a time on VM A, not on VM B.
cd ~/lab07
python3 -m venv .venv
source .venv/bin/activate
python -m pip install Flask
Why this works

A virtual environment keeps this project’s Python packages separate from the system’s packages. When activated, python and pip refer to that environment.

If it doesn’t work

If the venv command fails because the module is missing on Ubuntu, install python3-venv with sudo apt install python3-venv and try again. Package installation needs internet access unless Flask is already available.

Starter: app.py

Make app.py in ~/lab07.

from flask import Flask, jsonify, render_template, request
from werkzeug.security import check_password_hash, generate_password_hash

app = Flask(__name__)
app.config["TEMPLATES_AUTO_RELOAD"] = True  # See HTML edits without debug mode.
accounts = {}  # Practice accounts disappear when the server stops.

@app.get("/")
def home():
    return render_template("index.html")

@app.post("/receive")
def receive():
    return jsonify(
        username=request.form.get("username", ""),
        received=request.form.get("password", ""),
    )

@app.post("/register")
def register():
    username = request.form.get("username", "")
    password = request.form.get("password", "")
    if not username or not password:
        return jsonify(error="Both fields are needed"), 400
    accounts[username] = generate_password_hash(password)
    return jsonify(username=username, stored=accounts[username])

@app.post("/login")
def login():
    username = request.form.get("username", "")
    password = request.form.get("password", "")
    saved = accounts.get(username)
    return jsonify(username=username,
                   accepted=bool(saved and check_password_hash(saved, password)))

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=8000, debug=False)

VM A · terminal 1

Run the Flask website

Back in VM A terminal 1, where you activated the virtual environment, start the application. Leave it running. The SSH tunnel from the earlier test should still work.

Start the app first. In another terminal, inspect the port using ss.
python app.py
# In another VM A terminal:
ss -ltnp | grep ':8000'
Why this works

Flask is just a Python process that listens on a port and responds to requests. ss -ltnp lists listening TCP sockets and, when permitted, their processes. We set debug=False deliberately.

If it doesn’t work

If you see “Address already in use,” the earlier http.server may still be running. Stop it before restarting Flask.

VM A owner · laptop browser

Send a made-up password

Reload http://127.0.0.1:8765/. Under Send a value, submit a made-up username and password, such as river7. The server returns JSON showing exactly what it received.

Open browser Developer Tools → Network. Submit again. Open the receive request and find Payload (or Form Data). You should see the form fields there.
Why this works

An input field with type="password" hides characters while someone types. It does not hash them or encrypt the HTTP request. We use fictional values because this endpoint deliberately echoes them.

If it doesn’t work

If the page is blank or stale, refresh the browser. If it says “Connection refused,” the Flask process may have stopped.

VM C (or VM B) · terminal

Send the same kind of request without a browser

A third student has a separate client to operate and test. The browser isn’t needed: submit a made-up username and password to /receive using curl. Change the values and repeat.

Replace VM_A_IP with the real address. Choose your own made-up values for both fields.
curl -X POST -d 'username=team3' -d 'password=river7' \
  http://VM_A_IP:8000/receive
Why this works

-X POST chooses the HTTP method; -d sends form fields in the request body. Flask reads them through request.form. This is the same route the browser form uses.

If it doesn’t work

Try removing the password field or changing it to secret. The Python code looks for a field named password, so different names produce different results.

VM A · editor, then laptop browser

Add a second form that hashes before sending

Open templates/index.html. Copy the first “Send a value” form and give the new form the ID hashed. Put a heading above it such as “Hash before sending.” Add the JavaScript shown in the hint to the bottom of the page, just before </body>. Save and refresh the laptop browser.

The new form should still submit to /receive. Its name="username" and name="password" attributes must remain unchanged.
nano templates/index.html
Show a working form and script

Add these pieces to templates/index.html before the closing </body>. The form should appear only once.

<h2>Hash before sending</h2>
<form id="hashed" action="/receive" method="post">
  <label>Username <input name="username" required></label>
  <label>Password <input name="password" type="password" required></label>
  <button type="submit">Send hash</button>
</form>

<script>
const hashedForm = document.getElementById("hashed");
hashedForm.addEventListener("submit", async (event) => {
  event.preventDefault();
  const field = hashedForm.querySelector('input[name="password"]');
  const bytes = new TextEncoder().encode(field.value);
  const digest = await crypto.subtle.digest("SHA-256", bytes);
  field.value = Array.from(new Uint8Array(digest))
    .map(byte => byte.toString(16).padStart(2, "0")).join("");
  hashedForm.submit();
});
</script>
Why this works

Before the browser sends this form, JavaScript converts the entered password into a SHA-256 hexadecimal digest. The server’s /receive route has not changed.

If it doesn’t work

The JavaScript hashing function requires a trusted browser context. Our browser is visiting 127.0.0.1 through SSH forwarding, which browsers treat as a local trustworthy origin. An ordinary direct http://VM_A_IP:8000 page may not have access to crypto.subtle.

VM A owner · laptop browser

Compare the two requests

Try the same made-up password in the original form and then the new hashed form. Open Network → receive → Payload after each submission. You should get readable text in one request and 64 hexadecimal characters in the other.

For a clean test, return to the home page before each submission. On the hashed form, the server response should also show the 64-character digest.
Why this works

The browser-side SHA-256 operation changed the submitted value. It did not encrypt the connection or make the hash an identity proof. The same digest for the same password can be sent by anybody.

VM C (or VM B) · terminal

Send a digest yourself

The browser shows the digest that was submitted. Copy that made-up digest (not a real password) and submit it directly from the other VM using curl. You will receive the same digest back because the server simply echoes the submitted form field.

Replace the digest and VM A address. This demonstrates that a submitted digest can be repeated.
curl -X POST -d 'username=from-vm-c' \
  --data-urlencode 'password=PASTE_THE_64_CHARACTER_DIGEST' \
  http://VM_A_IP:8000/receive
Why this works

This /receive endpoint is not a login system, so repeating the digest does not demonstrate a login bypass. It shows why a server that treated the incoming digest itself as a reusable password would still be vulnerable to reuse.

VM A owner · laptop browser

Now let the server handle password storage

Under Create a practice account, register a new made-up username and password. Notice that the response shows a long stored hash, not the original password. Then return to the page and use Try to log in once with the correct password and once with a wrong one.

Use the same username on registration and login. Expect "accepted": true for the correct password and false for the wrong one. Try a second username too.
Why this works

The server calls generate_password_hash() when registering and check_password_hash() when logging in. Unlike a quick SHA-256 digest, these functions use password-specific hashing designed to make guessing more costly. The salt is included in the stored result.

If it doesn’t work

Accounts live only in the Python program’s memory. Restarting Flask erases them. The server returns the stored hash solely so students can inspect it; a real application should not expose that value.

VM C (or VM B) · terminal

Test the same login route from Linux

With Flask still running on VM A, create your own practice account from VM C using the /register route (same POST format as below). Then send one correct and one incorrect login request to /login. Work out which values to change between them.

Do not reuse the placeholders. To create the account from VM C, use the same command shape but send it to /register first; then try /login with the same and a different password.
curl -X POST -d 'username=YOUR_TEST_USER' \
  -d 'password=YOUR_TEST_PASSWORD' \
  http://VM_A_IP:8000/login
Why this works

Both browser and curl can send form data to the same route. The server compares the supplied password against its stored hash. A stored hash protects against plaintext disclosure from storage; it does not protect an HTTP password traveling between VMs.

What this lab did not secure

The first form is intentionally unsafe, and the /receive route echoes values so you can inspect them. Browser-side SHA-256 does not replace HTTPS. Even server-side password hashing does not encrypt HTTP traffic between the VMs. The SSH tunnel protects the laptop-to-VM path, but direct HTTP between VMs is not encrypted by that tunnel. This is a practice app, not a template for a real login service.

Quick checks when something fails

Connection refused: the service may not be listening. 404: the service answered, but the path was not found. 405: the path exists, but your HTTP method was wrong. 500: the Flask app raised an error; read VM A’s server terminal. A timeout between VMs often means an address, firewall, or network rule problem, not a hashing problem.
