WEB SECURITY · AZURE LINUX

Cookies, sessions, and a Linux server

A website checks your password once. What happens on the next request? You will run one Flask server on Azure VM A and open it in three different laptop browsers. Then you will see what makes a login persist, what invalidates it, and what disappears when Linux stops the process.

Use the same Azure setup as Lab 07

Student A owns VM A, which runs Flask on port 8000. Students B and C own VMs B and C. Each student tunnels through their own VM and opens 127.0.0.1:8765 on their own laptop. Do not share SSH credentials.

You should have

Three Azure Linux VMs in one working lab network, three laptops with a browser and SSH, Python 3, and a terminal. This page itself works without internet access. Installing Flask with pip may need network access.

VM A: serverVM B: clientVM C: client

Use invented passwords only. This is a teaching application, not a secure service for real accounts. Because B/C forward through their own VM to VM A over plain HTTP, the hop between Azure VMs is not protected by their SSH tunnel. Do not submit real secrets or share complete session cookies.

PART 01

One website, three browsers

Only VM A runs Flask. Everyone views it in a real browser, through their own Azure VM.

How the connection path works

There is only one website process in this lab: Flask on VM A. All three laptops reach that same server, but they do it through SSH forwarding.

Student A laptopBrowser opens 127.0.0.1:8765
→
SSH tunnel to VM A-L 127.0.0.1:8765:127.0.0.1:8000
→
Flask on VM AListens on port 8000
Students B/C laptopsBrowser also opens 127.0.0.1:8765
→
SSH tunnel to own VM-L 127.0.0.1:8765:VM_A_IP:8000
→
Flask on VM AReached across the Azure VM network

The browser address stays the same on every laptop. Students B and C change only the forwarding destination, not the address typed into the browser.

How the login stays alive

The password matters at login time. After login, the browser proves itself in a different way.

1. Browser sends passwordPOST /login
→
2. Flask checks itLooks up user and verifies password hash
→
3. Server creates sessionStores a record in SESSIONS
4. Browser receives cookieSet-Cookie: lab08_session=...
→
5. Later requests send cookieGET /dashboard with Cookie
→
6. Server looks up tokenIf found, the dashboard is allowed

Keep three things separate in your mind: the browser cookie, the server’s SESSIONS dictionary, and the SSH tunnel carrying traffic between machines.

def current_session():
    token = request.cookies.get(COOKIE)
    return token, SESSIONS.get(token) if token else None


def show_page(record=None, token=None, error=None, status=200):
    label = sha256(token.encode()).hexdigest()[:8] if record and token else ""
    return render_template_string(
        PAGE,
        user=record["user"] if record else None,
        visits=record["visits"] if record else 0,
        label=label,
        created=record["created"] if record else "",
        last=record["last"] if record else "",
        active=len(SESSIONS),
        error=error,
    ), status


def redirect_home(clear_cookie=False):
    response = make_response(redirect("/", code=303))
    if clear_cookie:
        response.delete_cookie(COOKIE, path="/")
    return response


@app.after_request
def prevent_caching(response):
    response.headers["Cache-Control"] = "no-store"
    return response


@app.get("/")
def index():
    token, record = current_session()
    if record:
        return redirect("/dashboard", code=303)
    return show_page()


@app.post("/login")
def login():
    username = request.form.get("username", "").strip().lower()
    password = request.form.get("password", "")
    stored = PASSWORDS.get(username)
    if stored is None or not check_password_hash(stored, password):
        return show_page(error="Those credentials do not match.", status=401)
    token = secrets.token_urlsafe(24)
    now = datetime.now().strftime("%H:%M:%S")
    SESSIONS[token] = {"user": username, "visits": 0, "created": now, "last": "—"}
    response = make_response(redirect("/dashboard", code=303))
    response.set_cookie(COOKIE, token, httponly=True, samesite="Lax", path="/")
    return response


@app.get("/dashboard")
def dashboard():
    token, record = current_session()
    if not record:
        return redirect_home(clear_cookie=bool(token))
    record["visits"] += 1
    record["last"] = datetime.now().strftime("%H:%M:%S")
    return show_page(record, token)


@app.post("/logout")
def logout():
    token, _ = current_session()
    if token:
        SESSIONS.pop(token, None)
    return redirect_home(clear_cookie=True)


@app.post("/logout-all")
def logout_all():
    token, record = current_session()
    if record:
        for other_token, other_record in list(SESSIONS.items()):
            if other_record["user"] == record["user"]:
                del SESSIONS[other_token]
    return redirect_home(clear_cookie=True)


@app.get("/status")
def status():
    _, record = current_session()
    return jsonify({
        "logged_in": record is not None,
        "user": record["user"] if record else None,
        "your_dashboard_visits": record["visits"] if record else 0,
        "active_sessions_on_server": len(SESSIONS),
    })


if __name__ == "__main__":
    app.run(host="0.0.0.0", port=8000, debug=False, use_reloader=False)

Why is the session dictionary in Python?

The server uses SESSIONS, a dictionary held in one Python process. The browser gets a random session ID cookie, not a username/password. Each request looks up that ID in the dictionary. Flask also has a different, signed-cookie session system; this lab deliberately uses a server-side store so that logout and restart can be observed.

If python3 -m venv .venv fails on the VM

The usual cause here is a stale local APT package index. The VM asks Ubuntu Focal for an older patch package such as 20.04.11 / 5ubuntu1.10, but the Azure mirror now has a newer replacement. Also, a failed venv command can leave behind a half-built .venv folder, which must be removed before trying again.

  1. Refresh the local APT package index.

    Verification: the command ends with Reading package lists... Done and does not show 404 or Failed to fetch.

    Verification: installation finishes with Setting up python3.8-venv ... and exits cleanly without network errors.
  3. Delete the broken environment and rebuild it cleanly.

    Verification: the prompt returns with no error output. Check that pip exists with ls ~/lab08/.venv/bin/pip.

PART 03

Who keeps the memory?

Not the tab. Not the Azure IP address. The browser stores a cookie; the Linux process stores a record.

3.1Each student · browser

Are tabs separate sessions?

Ordinary tabs in one browser profile generally share cookies for the same site. The cookie belongs to the browser’s cookie store, not to the tab itself. The server therefore finds the same record.

3.3Each student · browser

Why is the cookie missing from document.cookie?

HttpOnly tells the browser not to expose that cookie to ordinary page JavaScript. The browser still sends the cookie with matching HTTP requests. It does not stop a stolen cookie from being replayed. Never show or share the full cookie value.

Why does curl say guest?

The server does not recognize a person simply because a request came from a particular VM or IP. It recognizes this classroom session by the presence of a known lab08_session cookie. Without that cookie, the request is unauthenticated.

PART 04

A terminal can be a browser

curl does not need a graphical interface, but it can send the same requests and cookies.

4.1Each student · own Azure VM

Log in with curl instead of a browser

A terminal client can log in too. On VM B/C, replace VM_A_IP; on VM A you may use 127.0.0.1. This command sends form fields, prints response headers, and saves the returned cookie into alice.cookies. Work in a clean folder on your own VM.

Azure VM · terminal
mkdir -p ~/lab08-client
cd ~/lab08-client

curl -i -c alice.cookies   -d 'username=alice' -d 'password=apple7'   http://VM_A_IP:8000/login
What do -i, -c and -d mean?

-i includes response headers; -c alice.cookies saves cookies received from the server; each -d supplies a form field, making this a POST request. You should see 303 See Other, Location: /dashboard, and Set-Cookie. The cookie file is sensitive within this demo—do not publish it.

4.2Each student · Azure VM

Try the same URL with and without a cookie

Run both requests. The first has no saved cookie and redirects to login. The second sends the cookie saved earlier and receives the dashboard. Compare the HTTP status and returned page.

Azure VM · terminal
curl -i http://VM_A_IP:8000/dashboard
curl -i -b alice.cookies http://VM_A_IP:8000/dashboard
What does -b do?

-b alice.cookies loads cookies from that file and sends any matching ones. The two requests can come from exactly the same VM and have the same IP. Their different result is due to the cookie.

4.3Each student · Azure VM

Follow the redirect automatically

The previous login used -i and stopped at the redirect. Try a fresh login with -L so curl follows the redirect to the dashboard. Keep both -b and -c: one reads existing cookies and the other saves updated ones.

Azure VM · terminal
touch bob.cookies
curl -i -L -b bob.cookies -c bob.cookies   -d 'username=bob' -d 'password=river9'   http://VM_A_IP:8000/login
Why does -L matter?

-L follows the server’s Location redirect. After the 303, curl requests the dashboard using GET. With both -b and -c, cookies received during the chain can be used and saved. Without -L, curl shows the redirect but does not load the destination page.

4.4Each student · Azure VM

Make a second copy of the same ticket

Copy Alice’s cookie jar to another file. Both now hold the same session token. Use both to visit the dashboard, then inspect only the cookie name in the jar, not its value.

Azure VM · terminal
cp alice.cookies alice-copy.cookies
curl -s -b alice.cookies http://VM_A_IP:8000/status
curl -s -b alice-copy.cookies http://VM_A_IP:8000/status

grep 'lab08_session' alice.cookies | cut -f6
Are these two login sessions?

No. The files contain copies of the same session token, so both act as the same already-authenticated session. That is why a session cookie must be treated like a password while it is valid. You should not send the full token to another student.

Before moving on

PART 05

A cookie is a bearer ticket

Anyone holding a valid session token may be recognized as that session. Logout must invalidate it.

5.1Each student · browser

Log out only one browser

Sign into the same account in an ordinary window and a private window. The two session labels should differ. In the private window, click Log out this session. Refresh the ordinary window. It should still work.

What did logout delete?

The server deletes only the current token from the SESSIONS dictionary, and the response instructs this browser to delete its cookie. Other sessions belonging to the same username keep working.

5.2Each student · Azure VM

Invalidate the copied curl session

Use the original cookie jar to log out, then try the copied jar. The copied file still contains the old token, but the server no longer recognizes it. The server’s decision, not just deleting the browser’s cookie, is what makes logout effective.

Azure VM · terminal
curl -i -b alice.cookies -c alice.cookies   -X POST http://VM_A_IP:8000/logout

curl -i -b alice-copy.cookies http://VM_A_IP:8000/dashboard
Why does the copy stop working?

SESSIONS.pop(token) removes the server-side record. Both jars carried the same token. Once that record is gone, neither can authenticate. The second command should redirect to /, even though the file still exists.

5.3Whole group · own browsers

Log out all sessions for one user

Have all three students sign in as Alice, each on their own laptop browser. Notice that their session labels differ. Student A clicks Log out all my sessions. Students B and C refresh: both should return to the sign-in page. Then Student B signs in as Bob, and Student C repeats the Alice logout-all action from a new session. Bob should remain logged in.

What did the all-sessions button do?

The application removes every in-memory token whose user is alice. It does not remove Bob’s session. Each browser still makes an ordinary HTTP request; the invalidation is a decision made by the server.

5.4Student A edits; everyone investigates

Change one small security setting, then restore it

Find the line that sets the cookie in app.py. It has httponly=True. Stop the server with Ctrl+C, change that argument to httponly=False, restart, and log in again. Repeat document.cookie in the browser Console. Then restore httponly=True and restart once more.

VM A · edit while server stopped
grep -n 'set_cookie' app.py
nano app.py
python3 app.py
What changed, and what did not?

With HttpOnly=False, page JavaScript can read the cookie. With HttpOnly=True, it cannot. In both cases a browser can still send the cookie in HTTP requests. Changing this setting and restarting will also erase the lab’s in-memory sessions because the process was restarted.

Before moving on

Confirm the server source has httponly=True again before moving on.

Is a stopped server a logged-out user?

No. While the server is down there is no program to answer requests at all. A missing service and an invalid session are different failures. When Flask runs again, it can return a response—but its old in-memory records will be gone.

Restart the process

Restart Flask from the same folder with the virtual environment active. Do not replace the SSH tunnels. Everyone refreshes the website: the connection works again, but the old sessions are no longer recognized. Sign in again and notice the new session labels and a new visit count.

VM A · Flask terminal

Why did the login disappear?

Our SESSIONS dictionary lived in the old Python process’s RAM. Stopping that process destroyed the data. A new process starts with an empty dictionary. A production service might use a database or shared session store, so a restart need not log everybody out.

The three kinds of state

The laptop browser remembers cookies. The Linux server remembers its SESSIONS dictionary. The SSH tunnel carries bytes between machines. Losing or replacing one does not automatically erase or repair the others.

References and one important limitation

This lab implements a simple server-side session dictionary on purpose. Flask’s built-in session uses signed cookies instead, so restart behavior differs. Also, this demonstration omits HTTPS, CSRF defenses, persistent session storage, and production deployment controls. The lessons about cookies still apply, but do not deploy this code as a real login system.
