Day Zero: Your First Push

It is your first day on a small team that ships its tools as Docker containers. Before anyone hands you a real project, there is day zero. Your lead's welcome message is short:

"Welcome aboard! Before you get a real project, let's get your desk ready. Install Docker, and get GitHub to trust your machine. Then ship one tiny thing: a name tag. It's a little container that prints a card with your name on it. Put it on GitHub, get two teammates to build it and run it, and let each of them ask you one question. Answer them in code. If all of that works, you're ready for real work."

That is this lab. None of it is hard, on purpose. Setting up GitHub for the first time comes with a handful of confusing moments: a key that is not accepted, a branch that cannot be found, a push that seems to go nowhere. It is much better to meet them today, on a three-line text file, than in the middle of a real project. Everything you set up here keeps working for every project after it.

Everything happens on your own Azure Lab VM (Ubuntu 20.04) and on github.com.

The finish line

You are done when all of these are true:

  • Docker runs on your VM without sudo
  • GitHub trusts your VM: ssh -T git@github.com greets you by name
  • Your nametag repository is on GitHub, and anyone can build it with one command
  • You built and ran the name tags of at least 2 classmates
  • You asked each of them one question in an Issue, and saw the answer show up in their name tag
  • You answered every question on your own repository with a commit that closed its Issue
  • Your log has an entry for every step marked LOG
  • You cleaned up your VM

No teams are needed. Trade with the people around you.

How this works

The steps

Each step tells you what you are trying to do and why it matters, but not the exact command. Try it on your own first. When you get stuck, open Hint for a nudge. When you are still stuck, open Show me for the command. Using Show me is completely fine. What counts is that you can say what the command did and why.

Boxes labeled Why this way? explain why the lab does something the way it does, and what else people do in the real world. Boxes labeled Think about it are questions worth a minute of your time. Neither one needs an answer handed in.

The log

Every step marked LOG gets an entry in your log. Each entry has four parts:

  1. Plan. Before you type anything: what are you about to do, and why? One or two sentences in your own words.
  2. Command. The exact command or commands you ran.
  3. What I see. What came back, and what it means. Did it match your plan? If it surprised you, say what surprised you.
  4. Screenshot. The command and its output on your screen.

Steps without the LOG mark are setup. Do them, but they need no entry.

Text like <your-username> means "put your own value here, without the angle brackets".

Part 0: git, meet GitHub

You already know git. Every commit you have made so far lives in exactly one place: the hidden .git folder inside your project. That folder is the history. Nobody else can see it, and if your VM disappears, the history disappears with it.

GitHub is a computer on the internet that keeps a copy of a repository where other people can reach it. That is most of the idea. Git does not treat GitHub as anything special. To git, GitHub is simply another copy of the same repository, sitting at some address. A saved address like that is called a remote, and the one you cloned from is called origin by convention.

Three commands move commits between the copies:

  • git clone makes a complete copy of a repository, with all of its history, and remembers where it came from as origin.
  • git push sends your new commits to the remote.
  • git pull brings the remote's new commits to you. You will not need it today, because nobody but you writes to your repository.

The consequence worth remembering: a commit you make on your VM exists only on your VM until you push it. Think of git as your own notebook and GitHub as a shelf in the library where you leave a copy for others to read. Writing in your notebook changes nothing on the shelf. git push does. And git status is the friend who tells you when the two have drifted apart.

GitHub also adds things that git does not have at all: a web page for every repository, and Issues, a public list of questions and to-dos attached to a repository, where anyone can add one. Today you use both.

Why this way? GitHub is the most common place to keep a repository, but it is not the only one. GitLab, Bitbucket and Codeberg do the same job, and many companies run their own server. Git works the same way with all of them, because git only needs an address. What you learn today carries over.

Part 1: Set up your workbench

Nothing here needs a log entry. It is setup, and it only has to work. If you already did some of it in an earlier lab, check that it still works and move on.

1.1 Make sure Docker is installed, and say hello

Docker may already be on your VM from an earlier lab. Ask Docker for its version to find out. If the command is not found, install the Docker package that Ubuntu provides (its name is docker.io). Either way, finish by running the official test image hello-world with sudo, and read what it prints. It describes, in four short steps, what just happened, including the moment it downloaded something.

Show me
docker --version

Only if that says command not found:

sudo apt update
sudo apt install -y docker.io

Then:

sudo docker run hello-world

1.2 Make Docker work without sudo

Now try docker run hello-world without sudo. If it works, you did this step before, so move on. If it fails, the error mentions a file called docker.sock. That file is the doorway between the docker command you type and the Docker service that does the real work. Look at who owns it and what its permissions are, the same way you would look at any file.

You will see that the doorway belongs to the group docker. So join that group. Group changes only count for new logins, so log out and back in (or start a new shell that has the group). Then docker run hello-world should work without sudo.

Hint

usermod changes a user's settings. You want to append one more Group to your own user. Be careful: without the "append" part, you would be removed from every other group, including the one that lets you use sudo.

Show me
docker run hello-world
ls -l /var/run/docker.sock
sudo usermod -aG docker $USER
exit

Reconnect to your VM, then:

groups
docker run hello-world

If you would rather not reconnect, newgrp docker opens a new shell that already has the group.

Do not skip this step. The rest of this lab assumes it. And in bigger projects, files that Docker creates for you while you use sudo docker belong to root, which causes Permission denied errors later.

Think about it Anyone in the docker group can start a container that reads or changes any file on the machine. So being in that group is almost the same as being root. That is fine on your own lab VM. Would you add a coworker to it on a shared company server?

1.3 Introduce yourself to git and GitHub

Tell git your name and email, so every commit you make says who made it. If you do not have a GitHub account yet, create one at github.com. Write your GitHub username somewhere handy. You will type it a lot.

Show me
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global --list

Use the same email as your GitHub account.

Every commit carries this email, and on GitHub anyone can read it. If you would rather keep your real address private, GitHub gives you a private no-reply address under Settings → Emails. Use that one here instead.

1.4 Give GitHub a key instead of a password

GitHub will not accept your password from the command line. Instead, your VM proves who it is with a key pair, the same public-key idea that RSA is built on. You keep the private key on the VM and never show it to anyone. You give GitHub the public key. When you connect, GitHub sends a challenge that only the matching private key can answer.

First look in ~/.ssh. If a file named id_ed25519 is already there, you made a key before: do not make a new one, just make sure its .pub half is on GitHub and test the connection. Otherwise, create an ed25519 key pair, find the two files it made, and paste the public one into GitHub under Settings → SSH and GPG keys → New SSH key. Then test the connection.

Show me
ls -l ~/.ssh

Only if there is no id_ed25519 yet:

ssh-keygen -t ed25519 -C "you@example.com"

Press Enter at every question to accept the defaults. Then show the public key:

ls -l ~/.ssh
cat ~/.ssh/id_ed25519.pub

Copy the whole line that cat prints into GitHub. Then:

ssh -T git@github.com

Type yes if it asks about a fingerprint. Success looks like Hi <your-username>! You've successfully authenticated.

It says Permission denied, or it hangs

Permission denied (publickey) means GitHub does not have your public key yet, or you pasted the wrong file. Paste the content of id_ed25519.pub, the one ending in .pub.

If it hangs instead, the normal SSH port may be blocked. GitHub also listens on port 443. Create ~/.ssh/config with this content and try again:

Host github.com
    Hostname ssh.github.com
    Port 443
    User git

Why this way? The other common option is HTTPS with a personal access token, a long random string you paste instead of a password. It works too. Keys win on a machine you use every day, because nothing secret ever travels over the network: the private key only answers a challenge, it never leaves your VM.

Part 2: Your first repository

2.1 Create a repository on GitHub and clone it LOG

On github.com, create a new public repository named nametag. This time, switch Add README on. With a README, GitHub makes the first commit for you, on a branch named main, so the repository is ready to clone right away.

On the new repository's page, the green Code button shows its addresses. Pick the SSH tab and copy the address that starts with git@github.com:. Clone the repository into your home folder. Then look around: list everything in it, including hidden files, show its history, and show where origin points.

For your log: where does origin point? How many commits are there already, and whose name is on them? You never ran git commit, so where did they come from?

Show me
cd ~
git clone git@github.com:<your-username>/nametag.git
cd nametag
ls -la
git log
git remote -v

Permission denied (publickey) sends you back to 1.4. Repository not found usually means a typo in the username or the repository name.

Why this way? There are two other ways to start. One: create an empty repository on GitHub, run git init in a local folder, connect the two with git remote add origin, and push. On this VM that route has a trap. Its git is older (version 2.25) and names the first branch master, while GitHub expects main, so you would also need git branch -M main to rename it. GitHub's own instructions for an empty repository include that exact line for this reason. Two: take a clone of someone else's project and point it at a new empty repository with git remote set-url. That is how you take over someone else's project and make it your own. Starting with a README skips both traps, which is why it comes first.

2.2 Make the name tag LOG

Your name tag is three small files:

  • card.txt: the words on the card. This is the one you will edit.
  • tag.py: a tiny Python program that prints every line of card.txt inside a frame.
  • Dockerfile: the recipe that packs both into an image, on top of a ready-made image that already has Python in it.

Inside ~/nametag, create the three files exactly as shown. Each block below is one command: cat > file <<'EOF' writes every line up to EOF into file, which is a quick way to make a file without opening an editor.

cat > card.txt <<'EOF'
Hi! I'm <your first name>
GitHub: <your-username>
Ask me one question in an Issue.
EOF

cat > tag.py <<'EOF'
# tag.py: prints every line of card.txt inside a frame
lines = open("card.txt").read().splitlines()
width = max((len(line) for line in lines), default=0)
print("+" + "-" * (width + 2) + "+")
for line in lines:
    print("| " + line.ljust(width) + " |")
print("+" + "-" * (width + 2) + "+")
EOF

cat > Dockerfile <<'EOF'
# Name tag: a tiny box that prints card.txt inside a frame
FROM python:3.12-slim
WORKDIR /tag
COPY tag.py .
COPY card.txt .
CMD ["python3", "tag.py"]
EOF

The Dockerfile reads top to bottom, like a recipe:

  • FROM starts from an image that already has Python 3.12. Docker downloads it the first time you need it.
  • WORKDIR /tag makes a folder /tag inside the image and works from there.
  • The two COPY lines copy your files from ~/nametag into /tag. They are on separate lines on purpose. Step 4.4 shows why.
  • CMD is the command a container runs when it starts.

Now open card.txt in nano and replace the two placeholders with your first name and your GitHub username. Then build an image named nametag from this folder, and run it.

For your log: the build prints one numbered step for each instruction in the Dockerfile. Which step took the longest, and why? What did the container print?

Show me
nano card.txt

Save with Ctrl+O and Enter, leave with Ctrl+X. Then:

docker build -t nametag .
docker run --rm nametag

The dot at the end of docker build means "the Dockerfile and the files are in this folder". --rm deletes the container as soon as it finishes, so stopped containers do not pile up. If the build starts with a DEPRECATED warning about the legacy builder, ignore it: your VM's Docker uses its older build engine, which works fine here.

Success looks like this, with your own name:

+----------------------------------+
| Hi! I'm Sam                      |
| GitHub: sam-lopez                |
| Ask me one question in an Issue. |
+----------------------------------+

2.3 Look, commit, push LOG

Right now your three files exist on your VM and nowhere else. Ask git what it thinks with git status. Add the three files, commit them with a clear message, and run git status again. Read its second line carefully: it compares your copy with the last thing it knew about origin. Then push, run git status a third time, and refresh your repository's page on GitHub.

For your log: what did git status say after the commit, and after the push? Explain "ahead of 'origin/main' by 1 commit" in your own words.

Show me
git status
git add card.txt tag.py Dockerfile
git commit -m "Add my name tag"
git status
git push
git status

Because you cloned this repository, git already knows where to push and which branch to use, so a plain git push is enough.

Think about it Right after git commit, and before git push, your commit existed in exactly one place in the world. Where? What would have happened to it if your VM had been wiped at that moment?

Part 3: Run it like a stranger

3.1 Build straight from GitHub LOG

Your classmates will never see your ~/nametag folder. All they will have is your GitHub address. Luckily, Docker can build from an address: it downloads the repository and follows its Dockerfile. Build your own name tag from your GitHub URL, with the name test-mine, and run it. If that works for you, it works for anyone.

One catch: the Docker on your VM assumes a repository's main branch is called master, the old default. GitHub calls it main. Add #main to the end of the URL to name the branch.

For your log: this build probably finishes almost instantly, even though Docker had to download your repository. Read the build output. What does Docker say for each step, and why could it skip the work?

Show me
docker build -t test-mine https://github.com/<your-username>/nametag.git#main
docker run --rm test-mine

couldn't find remote ref master means the #main is missing. Image names must be all lowercase. If Docker cannot find your repository at all, check that it is public and that your push went through.

Think about it You cloned with a git@github.com: address, and GitHub checked your key. Docker used an https:// address with no key at all, and GitHub let it in anyway. What does that tell you about what your key is actually for?

Why this way? The usual way to share an image is a registry such as Docker Hub or the GitHub Container Registry: you build once, push the finished image, and everyone else downloads it ready-made. That needs accounts, tokens and an extra push step. Building from the GitHub URL needs none of that, and everyone builds from a recipe they can read. The cost is that every person builds it themselves.

Part 4: Trade name tags

Now the name tags travel. Find at least two classmates and swap GitHub usernames. Trade both ways: everyone whose name tag you take gets yours. Then each of you asks the other one question, and the answer shows up inside the name tag.

4.1 Build their name tags LOG

Build each classmate's name tag straight from their GitHub URL, as tag-<their-username> in lowercase, and run it. Then list every image on your VM.

For your log: compare this build with your very first build in 2.2. What did Docker not have to download again, and why?

Show me
docker build -t tag-<their-username> https://github.com/<their-username>/nametag.git#main
docker run --rm tag-<their-username>
docker images

If Docker says the repository does not exist, your classmate has not pushed yet, made the repository private, or you have a typo.

4.2 Ask each of them one question

On each classmate's repository page, open the Issues tab and create a new Issue:

  • Title: Question from <your-username>
  • Body: one question they can answer in one short line. For example: What is your favorite Linux command? Which lab so far was the most fun? What would you build with a free week?

Issues are public, so keep it friendly and do not ask for anything personal. GitHub numbers every Issue, like #1, right after its title. Your classmate needs that number in the next step, so make sure they know it.

No Issues tab? The owner can turn it on under Settings → General → Features.

4.3 Answer the questions on your repository LOG

When an Issue shows up on your repository, read it and note its number. Add one line to card.txt that answers it and says who asked. Before you commit, ask git to show you exactly what changed. Then commit with a message that ends in fixes #<number>, using that Issue's number, and push. Open the Issue on GitHub again.

Here is what just happened. GitHub reads every commit message that lands on main. When it finds a closing keyword (fixes, closes or resolves) followed by # and a number, it closes that Issue and adds a link to the commit. The Issue is now a public record of what was asked and which commit answered it. Answer each question in its own commit, so each Issue points at its own answer.

For your log: what did git diff show? What happened to the Issue after the push, and what appeared on its page?

Show me
nano card.txt

Then:

git diff
git add card.txt
git commit -m "Answer <their-username>'s question, fixes #1"
git push

Use the number of the Issue on your repository. The second question is probably #2. A new line in card.txt might look like this:

Favorite command: grep (asked by maria-r)

Why this way? On a real team, a change like this usually arrives as a pull request: you push your work to a separate branch, a teammate reviews it, and merging it into main closes the Issue. The same keywords work in a pull request's description. Here the repository is yours and the change is one line of text, so pushing straight to main is fine.

4.4 Rebuild their name tag and find your answer LOG

Once a classmate tells you they answered your question, run their name tag again using the image you already have. Do not rebuild yet. Look at the card. Then rebuild it with the same command as in 4.1, and run it again. This time, read the build output closely: some steps say Using cache (or CACHED), and some actually run.

Docker reuses a layer only when everything underneath it is the same and the step's own input is the same. In your classmate's repository the only file that changed is card.txt. So FROM, WORKDIR and COPY tag.py come straight out of the cache, while COPY card.txt and every layer above it are built again. That is why the Dockerfile copies the two files on separate lines, with the file that changes most often last.

Finally, leave a short comment on the closed Issue saying you see the answer.

For your log: why did the first run still show the old card? In the rebuild, which steps came from the cache, and which ran again?

Show me
docker run --rm tag-<their-username>
docker build -t tag-<their-username> https://github.com/<their-username>/nametag.git#main
docker run --rm tag-<their-username>

Think about it Suppose the Dockerfile had copied card.txt before tag.py. Which steps would run again after every answer? Now picture a real project where one step installs a hundred packages and takes five minutes. Where in the Dockerfile would you want that step, and where would you put the files you edit every day?

Part 5: Clean up

5.1 Clear out Docker

List all containers, including stopped ones. You will find leftovers from hello-world, which you ran without --rm. Ask Docker to remove everything it no longer uses, and read its list before you answer y. Then remove the name tag images (yours, test-mine and your classmates') and hello-world.

Keep python:3.12-slim. Any later image that starts from it skips the download.

Show me
docker ps -a
docker system prune

Answer y once you have read the list. Then:

docker images
docker rmi nametag test-mine tag-<their-username> tag-<their-username> hello-world
docker images

Images with the name <none> are old versions that a rebuild replaced. docker system prune removes them.

5.2 Delete your project, then get it back LOG

Here is the real reason GitHub matters to you. Delete your ~/nametag folder completely, history and all. Then clone it again and check. Are all your commits there? Is card.txt still answering your classmates' questions?

For your log: what came back with the clone, and was anything missing? What would you have lost if you had never pushed?

Show me
cd ~
rm -rf ~/nametag
git clone git@github.com:<your-username>/nametag.git
cd nametag
git log --oneline
cat card.txt

Keep your nametag repository on GitHub, and keep your SSH key. Anything you push to GitHub from this VM from now on uses it. When you are completely done with this VM at the end of the semester, delete its key from your GitHub settings. A key nobody uses is a door nobody watches.
