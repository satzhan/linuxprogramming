Linux Final Project

The Secret Box

It is your first week on a small team that ships its tools as Docker containers. On your first morning, your lead sends you a link to a GitHub repository and a short message:

"This is Jordan's project. Jordan was our junior developer, and he left last week. He built a little 'secret box' that prints a locked message, and he told everyone nobody could ever read it. The build is broken now, and I don't believe the 'nobody can read it' part either. Can you take it over? Fix it, find out how safe it really is, and then build one that actually is safe. When you're done, trade boxes with the rest of the team and see whose lock holds."

That is this project. You will repair someone else's code by reading its history, break his lock, and find three different places where his "deleted" secret is still sitting in plain sight. Then you will build your own box properly, publish it on GitHub so anyone can run it with one command, and trade it with classmates. They try to break your lock and you try to break theirs, and every successful break is proven in public without giving the answer away.

Everything happens on your own Azure Lab VM (Ubuntu 20.04) and on GitHub.

The finish line

You are done when all of these are true:

  • Docker runs on your VM without sudo
  • You fixed Jordan's box and pushed the fixes to your own GitHub repository
  • You broke Jordan's lock and found the three places his secret leaked
  • Your own box, with two locks, is on GitHub, and anyone can build it with one command
  • At least 2 classmates have built and run your box
  • You have built the boxes of at least 2 classmates, broken both locks of each, and posted proof on their repositories
  • You answered every proof posted on your own repository
  • Your log has an entry for every step marked LOG
  • You cleaned up your VM

No teams are needed. Ask the people around you to trade.

How this works

The steps

Each step tells you what you are trying to do and why it matters, but not the exact command. Try it on your own first. When you get stuck, open Hint for a nudge. When you are still stuck, open Show me for the command. Using Show me is completely fine. What counts is that you can say what the command did and why.

Some boxes are labeled Why this way?. They explain why the project does something the way it does, and what else people do in the real world. Boxes labeled Think about it are questions worth a minute of your time. Neither one needs an answer handed in.

The log

Every step marked LOG gets an entry in your log, in the same format you used for the midterm. Each entry has four parts:

  1. Plan. Before you type anything: what are you about to do, and why? One or two sentences in your own words.
  2. Command. The exact command or commands you ran.
  3. What I see. What came back, and what it means. Did it match your plan? If it surprised you, say what surprised you.
  4. Screenshot. The command and its output on your screen.

Steps without the LOG mark are setup. Do them, but they need no entry.

Text like <your-username> means "put your own value here, without the angle brackets".

Part 0: What is a container, really?

You probably have had this experience: a program works perfectly on your machine, you send it to a friend, and it does not run. Their Python is a different version, a file is in a different folder, a permission is different. The program was never really just the .py file. It was the file plus everything around it.

A container packs the program together with everything around it, so whoever runs it gets exactly what you got. Three words carry the whole idea:

  • Dockerfile: a recipe, one instruction per line. "Start from a machine that has Python. Copy this file in. Run this command."
  • Image: what you get by following the recipe. A sealed, ready-to-run package. You build it once.
  • Container: a running copy of an image. You can start as many as you want from the same image, and every one of them starts fresh.

Keep one more idea in your pocket, because Part 5 depends on it: an image is built in layers. Every line of the Dockerfile adds one layer on top of the ones before it.

Why this way? You could ship the whole computer instead: a full virtual machine, like your Azure Lab VM. That works, but a VM carries an entire operating system and takes minutes to start. A container shares the kernel of the machine it runs on and only carries what is different, so it starts in well under a second and is often tens of megabytes. Most modern cloud software runs in containers for exactly this reason.

Part 1: Set up your workbench

Nothing here needs a log entry. It is setup, and it only has to work.

1.1 Install Docker and say hello

Your VM does not have Docker yet. Install the Docker package that Ubuntu provides (its name is docker.io), then run the official test image hello-world. You will need sudo for now. Read the message it prints. It describes, in four short steps, what just happened, including the moment it downloaded something.

Show me
sudo apt update
sudo apt install -y docker.io
docker --version
sudo docker run hello-world

1.2 Make Docker work without sudo

Now try docker run hello-world without sudo. It fails, and the error mentions a file called docker.sock. That file is the doorway between the docker command you type and the Docker service that does the real work. Look at who owns it and what its permissions are, the same way you would look at any file.

You will see that the doorway belongs to the group docker. So join that group. Group changes only count for new logins, so log out and back in (or start a new shell that has the group). Then docker run hello-world should work without sudo.

Hint

usermod changes a user's settings. You want to append one more Group to your own user. Be careful: without the "append" part, you would be removed from every other group, including the one that lets you use sudo.

Show me
docker run hello-world
ls -l /var/run/docker.sock
sudo usermod -aG docker $USER
exit

Reconnect to your VM, then:

groups
docker run hello-world

If you would rather not reconnect, newgrp docker opens a new shell that already has the group.

Do not skip this step. If you keep using sudo docker for the rest of the project, files that Docker creates for you will belong to root, and later steps will fail with Permission denied.

Think about it Anyone in the docker group can start a container that reads or changes any file on the machine. So being in that group is almost the same as being root. That is fine on your own lab VM. Would you add a coworker to it on a shared company server?

1.3 Introduce yourself to git and GitHub

Tell git your name and email, so every commit you make says who made it. If you do not have a GitHub account yet, create one at github.com. Write your GitHub username somewhere handy. You will type it a lot.

Show me
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global --list

Use the same email as your GitHub account.

1.4 Give GitHub a key instead of a password

GitHub will not accept your password from the command line. Instead, your VM proves who it is with a key pair, the same idea as the RSA lab. You keep the private key on the VM and never show it to anyone. You give GitHub the public key. When you connect, GitHub sends a challenge that only the matching private key can answer.

Create an ed25519 key pair, find the two files it made, and paste the public one into GitHub under Settings → SSH and GPG keys → New SSH key. Then test the connection.

Show me
ssh-keygen -t ed25519 -C "you@example.com"
ls -l ~/.ssh
cat ~/.ssh/id_ed25519.pub

Press Enter at every question to accept the defaults. Copy the whole line that cat prints into GitHub. Then:

ssh -T git@github.com

Type yes if it asks about a fingerprint. Success looks like Hi <your-username>! You've successfully authenticated.

It says Permission denied, or it hangs

Permission denied (publickey) means GitHub does not have your public key yet, or you pasted the wrong file. Paste the content of id_ed25519.pub, the one ending in .pub.

If it hangs instead, the normal SSH port may be blocked. GitHub also listens on port 443. Create ~/.ssh/config with this content and try again:

Host github.com
    Hostname ssh.github.com
    Port 443
    User git

Why this way? The other common option is HTTPS with a personal access token, a long random string you paste instead of a password. It works too. Keys win on a machine you use every day, because nothing secret ever travels over the network: the private key only answers a challenge, it never leaves your VM.

Part 2: Inherit Jordan's project

2.1 Clone it and look around LOG

Clone Jordan's repository into your home folder, into a folder called secret-box. Then explore it. List everything, including hidden files, and read README.md, Dockerfile, .dockerignore, hints.txt and box.py. You do not need to understand every line. Try to answer one question for your log: what is this box supposed to do when someone runs it?

Starter repository: https://github.com/satzhan/secret-box-starter.git

Show me
cd ~
git clone https://github.com/satzhan/secret-box-starter.git secret-box
cd secret-box
ls -la
cat README.md Dockerfile .dockerignore hints.txt
cat box.py

2.2 Read the history LOG

A git repository remembers every change anyone ever made to it, with a message from the person who made it. Jordan's history is short, and it tells a story. Show the list of commits, then show which files each commit touched. In your log, tell that story in one sentence per commit. What did Jordan do last, and why?

Show me
git log --oneline
git log --stat

2.3 Make it yours

Right now your copy still points at Jordan's repository. On github.com, create a new, public, completely empty repository named secret-box: no README, no license, no .gitignore. Then point your copy at your new repository, using its SSH address (the one starting with git@github.com:), and push. Refresh the page on GitHub: Jordan's whole history is now in your repository.

Hint

git remote -v shows where your copy points. git remote set-url changes it. git push -u pushes and remembers the destination for next time.

Show me
git remote -v
git remote set-url origin git@github.com:<your-username>/secret-box.git
git push -u origin main

If the push is rejected with "fetch first", your GitHub repository was not empty. Delete it on GitHub, create it again without any files, and push again.

Why this way? GitHub has two shortcuts for copying a repository. A fork keeps the history, but GitHub turns Issues off on forks, and you will need Issues in Part 8. A template gives you a fresh repository, but it throws the history away, and Jordan's history is the first clue in Part 3. Clone plus a new empty repository keeps both.

Part 3: Make it build

First make it work. Then make it right.

3.1 Problem A: a file that is not there LOG

Follow Jordan's README and build the image with the name junior-box. It fails. Read the whole error, not only the last line. There are two different problems hiding here, and Docker may tell you about only one of them at a time. Start with the simplest check: compare the files the Dockerfile wants to COPY with what ls shows in the folder. One of them simply is not there.

When did it disappear, and why? The history knows. Find the commit that deleted it, then bring the file back exactly as it was just before that commit. Do not retype it.

Hint

git log can show only the commits where a file was Deleted. If abc1234 is a commit, abc1234^ means "the commit right before it". git checkout <commit> -- <file> restores one file from any moment in history.

Show me
docker build -t junior-box .
ls
git log --diff-filter=D --oneline --name-only
git checkout <deleting-commit>^ -- message.txt
cat message.txt

Replace <deleting-commit> with the short hash from the second command.

Think about it Jordan deleted message.txt because "it was public on GitHub". You just got it back from GitHub's own copy of the history. Was it ever really gone?

3.2 Problem B: files that are there, but invisible LOG

Build again. Even with message.txt back, Docker says box.py (or caesar.py) is not found, or is excluded. But the files are right there when you run ls. Something is telling Docker to ignore them before the build even starts. Find that file, compare what Jordan meant (read his comment) with what he actually wrote, and fix it so it hides only the file he meant to hide. Then build until it succeeds.

Hint

The file is .dockerignore. The pattern *.py matches every file that ends in .py.

Show me

Open the file with nano .dockerignore and change the line *.py to crack.py. Then:

docker build -t junior-box .
docker images

3.3 Problem C: it builds, then it crashes LOG

Run a container from junior-box, and have Docker remove it when it exits. It crashes with a long Python error. Read the last line first, because that is where Python puts the actual reason.

Then investigate from inside. If you put a command after the image name, the container runs that command instead of its normal program. Use that to find out who the container runs as, and the owner and permissions of the file it is trying to read.

Jordan's comment calls the chmod line "extra security". But this file is already encrypted, and it exists to be printed. Change the chmod so everyone can read the file and only the owner can write it. Keep USER nobody, because Jordan got that part right. Rebuild and run. You should see a block of scrambled text.

Show me
docker run --rm junior-box
docker run --rm junior-box whoami
docker run --rm junior-box ls -l locks

In the Dockerfile, change chmod 600 to chmod 644. Then:

docker build -t junior-box .
docker run --rm junior-box

Why this way? By default a container runs as root. If someone finds a bug in the program, they are root inside the container, and that is a much better starting point for an attack than an unprivileged user. USER nobody costs nothing. Larger projects usually create a dedicated user with useradd in the Dockerfile instead of borrowing nobody.

3.4 Save your fixes

Look at git status before you commit. One of your three changes is already listed under "Changes to be committed", without any git add. Which one, and why? Commit that one first, on its own. Then commit each of the other two fixes separately, with a message that says what you fixed and why. Push.

Show me
git status
git commit -m "Restore message.txt so the build works again"
git add .dockerignore
git commit -m "Fix .dockerignore: hide only crack.py, not every .py file"
git add Dockerfile
git commit -m "Fix permissions: secret1.txt must be readable by user nobody"
git log --oneline
git push

git checkout <commit> -- <file> restores the file and stages it, which is why the first commit needs no git add.

Part 4: Break Jordan's lock

Now switch sides. Pretend you are an outsider who has only Jordan's image, not his folder.

4.1 Take the lock out of the box LOG

You do not have to run a container to get files out of it. Docker can create a container without starting it, copy files out of it, and remove it. Use that to copy the /box/locks folder of junior-box into ~/loot/jordan.

Show me
mkdir -p ~/loot
docker create --name jordan-c junior-box
docker cp jordan-c:/box/locks ~/loot/jordan
docker rm jordan-c
cat ~/loot/jordan/secret1.txt

4.2 Break the Caesar lock LOG

Look at the locked text before you do anything. Some characters did not change at all. And the last line has the shape XXXX{.....-......-.....-......}. What do you think it said before it was locked?

A Caesar lock slides every letter forward by the same amount. With only 26 letters, there are only 26 possible slides, so you can simply try them all. caesar.py has a crack command that does exactly that. The output is long, so filter it down to the line that mentions FLAG. Then use the shift you found to unlock the whole message, and check that it matches message.txt exactly.

Show me
cd ~/secret-box
python3 caesar.py crack ~/loot/jordan/secret1.txt | grep FLAG
python3 caesar.py decrypt <shift> ~/loot/jordan/secret1.txt > ~/loot/jordan/opened.txt
diff -s ~/loot/jordan/opened.txt message.txt

Think about it You knew the answer started with FLAG{. A guess about part of the message is called a crib, and cribs are how real codebreakers attacked much stronger ciphers than this one. What would have been harder if every flag looked different?

Part 5: Where did the secret go?

Jordan's Dockerfile locks the message and then deletes message.txt. Run ls -la /box inside the image and you will see it is not there. So it is gone, right? You are going to find it three times.

5.1 Leak 1: the image remembers its recipe LOG

Every image keeps a record of the commands that built it. Show the full history of junior-box, without cutting long lines short, and find the line that locked the message. What does that line give away? Would you even have needed Part 4?

Show me
docker run --rm junior-box ls -la /box
docker history --no-trunc junior-box

Look for caesar.py encrypt and the number right after it.

5.2 Leak 2: the layers LOG

Think of an image as a stack of transparent sheets, one per line of the Dockerfile. Each sheet only records what changed. When a later line deletes a file, Docker cannot erase it from the sheet below. It lays a small note on the new sheet that says "pretend this file is gone". Looking down through the whole stack, you do not see the file. But the sheet underneath still has it, and anyone who has the image has every sheet.

Prove it. Save junior-box as one .tar file in your home folder, unpack it into a new folder ~/leak, and look inside. Every layer is a tar archive of its own, so tar can list what each one holds. Loop over every file, list its contents, and print the name of any layer that mentions message.txt. You should find two layers. One holds the real file: print it straight out of the layer. The other holds a strangely named file that starts with .wh.. That is the "pretend it's gone" note, called a whiteout.

Show me
docker save junior-box -o ~/junior-box.tar
mkdir -p ~/leak
tar -xf ~/junior-box.tar -C ~/leak
cd ~/leak
for f in $(find . -type f); do
    if tar -tf "$f" 2>/dev/null | grep -q 'box/.*message.txt'; then
        echo "== $f"
        tar -tf "$f" | grep 'box/.*message.txt'
    fi
done

Then print the file from the layer that has box/message.txt (-x extracts, -O sends it to the screen instead of to a file):

tar -xOf <that-layer> box/message.txt
cd ~/secret-box

If tar says Permission denied, you ran docker save with sudo, so the file belongs to root. Finish step 1.2, delete the old file with sudo rm ~/junior-box.tar, and save it again.

5.3 Leak 3, and the one rule behind all three

You already used the third leak in step 3.1: git history. Deleting a file in a new commit does not remove it from the earlier commits, and everyone who clones the repository gets all of them.

Three leaks, one lesson: anything that ever goes into a commit or an image layer stays there. The only safe secret is one that never goes in at all. So the rule for your own box is simple. Lock your messages on your own VM. Keep the plain text in a folder that is never part of the repository or the image. Ship only the locked files.

Why this way? Real teams have more tools for this. Multi-stage builds do messy work in a first image and copy only the finished result into a second, clean one. Newer Docker builders can mount a build secret that is available during one step and never written into a layer (your VM's Docker uses the older builder, which does not have this). And scanners such as GitHub's secret scanning, gitleaks or trufflehog search repositories for passwords and keys that slipped in. All of them exist because Jordan's mistake is extremely common.

Think about it Suppose a real password once got pushed to GitHub. You delete it in a new commit, or even rewrite the history so it is gone. Is that enough? What else has to happen? (Hint: who might have cloned it in the meantime?)

Part 6: Build your own box, the safe way

Your box will have two locks:

  • Level 1 is a Caesar lock. Easy on purpose. Everyone should get through it.
  • Level 2 is AES-256 with a password chosen from wordlist.txt. Harder, but fair: your hint will say the password is in that list.

Each level hides its own flag, like FLAG{maria-orange-tuba}. Whoever breaks a lock uses the flag to prove it.

6.1 Make a vault and write your messages

Create a folder ~/vault, next to ~/secret-box, not inside it. This is where your plain messages and passwords live, and it never goes to GitHub or into an image.

In the vault, write level1.txt and level2.txt. Each one holds a short note to whoever breaks it, and ends with a flag on its own line. Flag rules:

  • FLAG in capitals, then lowercase inside the braces, no spaces: FLAG{...}
  • start with your GitHub username, then two or three words joined with dashes
  • the two flags must be different

Then remove Jordan's message.txt from your project with one command that deletes it from the folder and from git, and commit. Finally, create an empty locks folder inside ~/secret-box. Only locked files will ever go in there.

Show me
mkdir -p ~/vault
nano ~/vault/level1.txt
nano ~/vault/level2.txt
cd ~/secret-box
git rm message.txt
git commit -m "Remove Jordan's message: the new box ships only locked files"
mkdir locks

Example level1.txt:

You got through the first door. The second one is harder.
FLAG{maria-orange-tuba}

6.2 Lock Level 1, then test it LOG

Pick a shift between 1 and 25 and note it in your vault, for example in ~/vault/notes.txt. Use caesar.py to lock ~/vault/level1.txt into locks/secret1.txt. Before you trust it, unlock your own file with your shift and compare it with the original. They must be identical. A lock that even you cannot open is useless.

Show me
python3 caesar.py encrypt <shift> ~/vault/level1.txt > locks/secret1.txt
cat locks/secret1.txt
python3 caesar.py decrypt <shift> locks/secret1.txt | diff -s - ~/vault/level1.txt

The - tells diff to read one side from the pipe.

6.3 Lock Level 2, then attack it yourself LOG

Open wordlist.txt and pick one word as your password. It has to be in the list, because that is the deal with whoever tries to break it. Note it in your vault. Lock ~/vault/level2.txt with openssl, the same way as in the AES lab: AES-256-CBC, with a salt, with PBKDF2, and this time with base64 output (-a) so the result is plain text that can be printed. Save it as locks/secret2.txt.

Then test it twice. First unlock it with the right password and compare with the original. Then attack it the way your classmates will, with crack.py and the wordlist. How many tries did it take?

Show me
openssl enc -aes-256-cbc -salt -pbkdf2 -a -in ~/vault/level2.txt -out locks/secret2.txt -pass pass:<your-word>
cat locks/secret2.txt
openssl enc -d -aes-256-cbc -pbkdf2 -a -in locks/secret2.txt -pass pass:<your-word> | diff -s - ~/vault/level2.txt
python3 crack.py locks/secret2.txt wordlist.txt

Think about it Everyone's secret2.txt starts with U2FsdGVkX1. Decode the start of yours with head -c 12 locks/secret2.txt | base64 -d | head -c 8 and see what word appears. Why is it safe for that part to be the same for everyone? (Look up what -salt adds right after it.)

6.4 Write fair hints and sign your box

Replace the content of hints.txt with hints for whoever opens your box: what kind of lock each level is, and where the password comes from. Never the shift, never the password. Then open box.py and change OWNER from "jordan-junior" to your GitHub username.

Example hints.txt
Level 1 (secret1.txt): Caesar shift.
Level 2 (secret2.txt): AES-256-CBC with PBKDF2, base64. The password is one word from wordlist.txt.
Prove a break by opening an Issue on my repository with the sha256 of the flag. Never post the flag itself.

6.5 Write a Dockerfile that only ships locked files LOG

Jordan's Dockerfile brought the plain message in and locked it during the build. That is how it leaked. Rewrite the Dockerfile so it:

  1. starts from python:3.12-slim
  2. works in the folder /box
  3. copies in only box.py, hints.txt and the locks/ folder
  4. runs as user nobody
  5. runs python3 box.py when a container starts

No message.txt, no caesar.py, no RUN line that touches a secret. Also update .dockerignore so the image never receives the tools, the wordlist, the git folder or the markdown files.

Show me

Dockerfile:

FROM python:3.12-slim

WORKDIR /box

# only the program, the hints and files that are already locked
COPY box.py hints.txt ./
COPY locks/ ./locks/

# do not run as root
USER nobody

CMD ["python3", "box.py"]

.dockerignore:

.git
*.md
crack.py
caesar.py
wordlist.txt

Think about it Jordan needed a chmod line and you do not. Run ls -l locks on your VM and look at the permissions your files already have. Why can nobody read them?

6.6 Build it, then attack your own image LOG

Build your image with the name mybox and run it. You should see your name, your hints and both locked blocks.

Now do Part 5 to yourself before anyone else does. Check the full build history: no shift, no password, no plain text. Then save mybox to ~/mybox.tar, unpack it into ~/leak-mine, and search the contents of every layer for FLAG{. A clean image produces no hits. Run the same search in ~/leak and watch it find Jordan's flag, so you know the search works.

Hint

In 5.2 you listed the file names inside each layer with tar -tf. To search the file contents, use tar -xOf, which prints the contents of every file in a layer, and pipe that into grep -a (search binary data as if it were text).

Show me
docker build -t mybox .
docker run --rm mybox
docker history --no-trunc mybox

docker save mybox -o ~/mybox.tar
mkdir -p ~/leak-mine
tar -xf ~/mybox.tar -C ~/leak-mine
cd ~/leak-mine
for f in $(find . -type f); do
    if tar -xOf "$f" 2>/dev/null | grep -a -q "FLAG{"; then
        echo "LEAK in $f"
    fi
done
echo "search finished"
cd ~/secret-box

If you see only search finished, your image is clean.

6.7 Add a safety net, then look before you commit

Create a .gitignore that keeps plain text and keys out of git forever, even if one ends up in this folder by accident: ignore level*.txt, *.key and private_key.pem. Then run git status. You should see your changed Dockerfile, .dockerignore, box.py and hints.txt, plus the new .gitignore and locks/. Nothing from the vault. If anything unexpected shows up, stop and find out why before going on.

Show me
printf 'level*.txt\n*.key\nprivate_key.pem\n' > .gitignore
git status

Part 7: Ship it

7.1 Write your README and push

Replace Jordan's README.md with your own: what your box is, how to build and run it straight from GitHub (the command from 7.2), and how to prove a break (an Issue with the sha256 of the flag). Then add everything, commit with a clear message, and push.

Show me
git add Dockerfile .dockerignore box.py hints.txt .gitignore README.md locks/
git status
git commit -m "My own secret box: two locks, only locked files in the image"
git push

7.2 Test it like a stranger LOG

Docker can build straight from a GitHub address: it downloads the repository and follows its Dockerfile. Build your box from your own GitHub URL with the name test-mine and run it. If that works, anyone in the class can do the same.

One catch: the Docker on your VM uses an older builder that assumes the main branch is called master. GitHub calls it main. Add #main to the end of the URL.

Show me
docker build -t test-mine https://github.com/<your-username>/secret-box.git#main
docker run --rm test-mine

Image names must be all lowercase. couldn't find remote ref master means the #main is missing. If Docker cannot find your repository at all, check that it is public and that your push went through.

Why this way? The usual way to share an image is a registry such as Docker Hub or the GitHub Container Registry: you build once, push the finished image, and everyone else pulls it ready-made. That needs accounts, tokens and an extra push step. Building from the Git URL needs none of that, and everyone builds from the same recipe you can read. The cost is that every person builds it themselves.

7.3 Check GitHub with your own eyes, then post your box

Open your repository on github.com and click through every file. Make sure no plain message, shift or password appears anywhere. Check that Issues are turned on (Settings → General → Features). Then post your repository link in the Brightspace discussion Box Exchange, with one line about your box and no hints beyond hints.txt.

Part 8: Trade boxes, break locks, prove it

Now the class becomes a market of boxes. Your box goes out, other boxes come in, and every break gets proven in public without spoiling the answer for anyone else.

8.1 Bring in at least two boxes LOG

Find at least two classmates to trade with, in class or from the Box Exchange thread. Trade fairly: everyone whose box you take gets your link. Build each of their boxes straight from their GitHub URL, as box-<their-username> in lowercase. Run each one and save what it prints into ~/loot/<their-username>.out.

Show me
docker build -t box-<their-username> https://github.com/<their-username>/secret-box.git#main
docker run --rm box-<their-username> > ~/loot/<their-username>.out
cat ~/loot/<their-username>.out

Think about it Your second classmate's box probably built much faster than Jordan's first build did. What did your VM not have to download again? Think in layers.

8.3 Break both locks LOG

Break Level 1 with caesar.py, as you did for Jordan. Break Level 2 with crack.py and wordlist.txt.

Before you run crack.py, read it. It tries every word in the list, but it checks two things before it believes a word is the password. The first check is "did openssl succeed?". Why is that not enough on its own? The comment at the top of the file explains it.

Show me
cd ~/secret-box
python3 caesar.py crack ~/loot/<their-username>/secret1.txt | grep FLAG
python3 crack.py ~/loot/<their-username>/secret2.txt wordlist.txt

How big is the pile of guesses for each kind of lock? Here is a way to see it: write down how many possible keys there are, and count the digits in that number.

A Caesar lock and a 256-word list both fall in a few seconds at most. An 8-letter password made of random lowercase letters is already out of reach for crack.py, but a dedicated cracking machine could still get through it. A truly random key has a number of possibilities with 78 digits. Trying a billion keys per second, from the start of the universe until now, would not get through a meaningful fraction of it. That is the difference between a lock that is hidden and a lock that is hard.

8.4 Prove it without giving it away LOG

You want to show the owner you have their flag without posting it, because then anyone could copy it. A hash is a fingerprint of a piece of text: the same text always gives the same fingerprint, but you cannot rebuild the text from the fingerprint.

Compute the SHA-256 hash of the flag with no newline at the end, using echo -n. Then do it once without the -n, and compare the two results. One invisible character changes everything, so everyone uses echo -n.

On the owner's GitHub repository, open one new Issue per level you broke:

  • Title: Level 1 broken by <your-username> (or Level 2)
  • Body: only the hash

Never post the flag, the shift or the password. Issues are public.

Show me
echo -n 'FLAG{their-flag-here}' | sha256sum
echo 'FLAG{their-flag-here}' | sha256sum

9.2 Clear out your files, and keep what matters
