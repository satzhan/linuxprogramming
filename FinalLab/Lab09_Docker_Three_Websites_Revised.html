Three websites with Docker

Run a web server on your own Linux VM. Open its page in a browser. Change the page and visit the other two websites. Then stop the server, bring it back, and find out which changes survive.

Student AVM A · own Nginx server
Student BVM B · own Nginx server
Student CVM C · own Nginx server

Everyone needs an assigned Ubuntu Linux VM on the same Azure lab network, a laptop with a browser and an SSH client, and permission to use sudo on their own VM. Keep an ordinary SSH terminal open on the VM. Later, open a second terminal on your laptop for the browser connection. All three students run the same commands on their own VMs unless a step says otherwise.

What is Docker? A Linux program normally needs supporting files and libraries to run. Docker distributes those pieces in an image. Docker uses the image to create a container—an isolated environment in which the program runs. An image is a starting template; a container is one instance made from it. You can stop a container and start the same one again, or remove it and create a fresh one from the image.

Unlike your Azure VM, a Linux container does not boot an independent operating-system kernel. It shares the Linux kernel of the VM hosting it. In this lab the packaged program is Nginx (pronounced “engine-x”), a web server that receives HTTP requests and returns webpages. No Nginx installation on the VM is needed.

01

Start a web server on each VM

All three students work at the same time. Run the commands on your Azure VM terminal, not on your laptop, unless a step says otherwise.

Every Azure VM

Check the Docker installation

Docker has a command-line client and a background service called the daemon. The client receives the command you type; the daemon creates and runs containers.

sudo docker --version
sudo systemctl is-active docker

sudo runs the Docker command with administrator privileges. --version only checks whether the Docker client exists; it does not prove the service can run containers. systemctl is-active docker asks Linux whether the Docker background service is running.

Check: You should see a Docker version and active. A missing Docker command or an inactive service needs fixing before the next step.
docker: command not found

These installation commands are for the assigned Ubuntu VMs. They install Docker from Ubuntu’s repositories, then start the Docker service.

sudo apt update
sudo apt install -y docker.io
sudo systemctl enable --now docker

Run the two checks again. If apt reports permission, repository, or network errors, keep the error and tell the instructor; do not run an unknown installation script.

Docker is installed, but its service is inactive or failed

Try starting the service, then read its status. A failed status screen usually contains the reason the service stopped.

sudo systemctl start docker
sudo systemctl status docker --no-pager

If it still fails, report the error instead of repeatedly reinstalling Docker.

Every Azure VM

Run a small test container

Docker provides a tiny test image named hello-world. The program starts, prints a message, and exits.

sudo docker run --rm hello-world

run creates a container from an image and starts its program. If the image is not already on the VM, Docker downloads it first. --rm removes the test container after it finishes; it does not delete the downloaded image.

The message is produced by a program running in a container, not by a shell command named hello-world installed on your VM.

Check: Look for Hello from Docker!. It is normal for this container to exit immediately.
permission denied ... /var/run/docker.sock

The Docker client could not contact the daemon through its Unix socket. Use sudo docker, not just docker. Changing the docker group is unnecessary for this lab and gives broad privileges.

sudo docker run --rm hello-world
Cannot connect to the Docker daemon

This is different from a missing image: Docker is installed, but the service may not be running.

sudo systemctl status docker --no-pager
sudo systemctl start docker
Unable to find image locally / download fails

Unable to find image locally by itself is not an error; Docker normally prints it before the first download. If you get timeout, network unreachable, TLS or DNS errors, check connectivity and retry once. An image download requires access to a registry the first time.

sudo docker pull hello-world

If the registry is blocked on your lab VM, ask the instructor to make the image available.

Every Azure VM

Check that port 8000 is available

Two different programs on the same VM generally cannot both listen on the same IP address and TCP port. A previous web server may still be using port 8000.

sudo docker ps -a
sudo ss -ltnp | grep ":8000" || true

docker ps -a lists running and stopped containers. ss -ltnp lists listening TCP sockets and, when permitted, the processes using them. grep searches for :8000; || true prevents “no match” from being treated as a command failure.

Check: If nothing is listening on port 8000, the ss command may print nothing. If you see a listener, find out which program owns it before proceeding.
An old container named lab09-web is listed

If this is a leftover container you created for this exercise, remove it. Otherwise, do not delete other students’ or unrelated containers.

sudo docker rm -f lab09-web
sudo docker ps -a
Port 8000 is used, but docker ps does not show the program

The listener may be a regular Python, Flask, or another host service. Read the ss output to identify it. Stop only a process you recognize and own. Ask the instructor before changing anything else.

Every Azure VM

Start Nginx in a container

Nginx is a web server. Instead of installing it on the VM, you will run the copy packaged in the nginx:alpine image.

sudo docker run -d --name lab09-web -p 8000:80 nginx:alpine
sudo docker ps
  • nginx:alpine identifies an Nginx image built on the small Alpine Linux distribution.
  • -d means detached: Nginx stays running while the terminal returns to a prompt.
  • --name lab09-web gives this container a name for later commands.
  • -p 8000:80 publishes port 8000 on the Azure VM and forwards it to port 80 inside the container.

All three students use the name lab09-web and port 8000. This is fine because they are on different VMs. A long container ID after docker run means Docker started the container, but does not yet prove Nginx answers requests.

Check: docker ps shows lab09-web with a status beginning Up and a port mapping like 0.0.0.0:8000->80/tcp.
The container name is already in use

docker ps shows only running containers; docker ps -a also shows stopped containers, which still reserve their names. Remove only your old lab09-web container, then run the Nginx command again.

sudo docker ps -a
sudo docker rm -f lab09-web
bind: address already in use / port is already allocated

Something is already using the VM’s port 8000. Diagnose it rather than running the same command again.

sudo docker ps
sudo ss -ltnp | grep ":8000"

Stop the identified old lab service if you own it. Keep the lab port at 8000 so later commands match.

The image does not download

Docker pulls nginx:alpine on the first use. If the pull finishes, the printed list of downloaded layers is normal. If it times out, test the VM’s connectivity and retry this command.

sudo docker pull nginx:alpine

Do not confuse a registry download failure with an Nginx web-server failure; Nginx has not started yet.

docker run printed an ID, but docker ps does not show lab09-web

The container probably exited after starting. Check the stopped entry and the program’s logs.

sudo docker ps -a
sudo docker logs --tail 30 lab09-web
Every Azure VM

Check the web server without leaving the VM

These two requests travel through different paths. The first runs a downloader inside the container. The second runs curl on the Azure VM and uses Docker’s published port.

sudo docker exec lab09-web wget -qO- http://127.0.0.1/
curl -4 --noproxy "*" --max-time 5 http://127.0.0.1:8000/
sudo docker logs --tail 12 lab09-web

docker exec starts an extra command inside an already-running container. wget -qO- fetches the page quietly and writes its bytes to the terminal rather than a file. In that first command, 127.0.0.1 is the container itself.

In the second command, 127.0.0.1 is the Azure VM. The request goes to VM port 8000 and should be forwarded to container port 80. -4 selects IPv4, --noproxy "*" avoids a configured web proxy, and --max-time 5 sets a maximum wait. docker logs displays what the container wrote to standard output or standard error, including Nginx request records.

Check: Both requests should print HTML with Welcome to nginx!. This checks the application and the host-to-container connection separately.
Connection reset by peer / curl: (56)

Retry once; a reset can be temporary. Do not infer the exact cause from one reset. Then compare the internal request with the VM request.

sudo docker ps -a
sudo docker exec lab09-web wget -qO- http://127.0.0.1/
curl -4 --noproxy "*" -v http://127.0.0.1:8000/
sudo docker logs --tail 30 lab09-web

If the internal request works and VM curl fails, check port publishing with sudo docker port lab09-web. If both fail, check whether Nginx is running. docker ps showing Up does not prove that an HTTP request succeeds.

curl says Connection refused or times out

Check whether Nginx’s container is up and whether Docker published the intended port.

sudo docker ps -a
sudo docker port lab09-web
sudo ss -ltnp | grep ":8000" || true

A refused connection is not the same as a successful HTTP response containing an error page.

docker exec reports container is not running or No such container

Read the all-containers list. If it exists but is stopped, use sudo docker start lab09-web and inspect logs. If it is absent, return to the Nginx start step.

HTML prints in the terminal instead of a webpage

That is correct. curl and wget retrieve page contents; they do not draw the webpage. The browser will render the same HTML in the next part.

Every Azure VM

Find your VM address and share it with your group

Each VM needs an address that the other two VMs can use. This is not the public SSH endpoint that you connect to from your laptop.

hostname -I

The output may contain more than one address. Use the private IPv4 address assigned to the VM’s lab network interface—often an address beginning with 10. in Azure. Confirm it with your group or the instructor if several addresses appear. 127.0.0.1 is always local to the machine running the command; it cannot identify your VM to a classmate.

Write down VM A IP, VM B IP, and VM C IP. Share only those IP addresses. Do not share passwords, private SSH keys, or login sessions.

Check: All three VM private IPv4 addresses are known before setting up the browser tunnel.
hostname -I prints multiple addresses

Check the interfaces and choose the IPv4 address of your Azure lab NIC. The address must be reachable from the other lab VMs; do not use a Docker bridge address such as 172.17.x.x unless the instructor specifically directs it.

ip -4 addr show
The IPs look correct but classmates cannot connect

Keep the address for now. The peer-VM test later will distinguish a working web server from a network rule that blocks VM-to-VM requests.

02

See the site in your laptop browser

You have already proved that Nginx answers curl on its VM. Now connect your laptop browser to it. You will use SSH local port forwarding, which carries a local browser connection through the SSH session to the Azure VM. Keep all three web servers running.

The SSH terminal for your normal VM shell and the SSH tunnel terminal are different: use one terminal to type commands on the VM, and another terminal on your laptop to keep the tunnel alive.
Student A's page127.0.0.1:8765
Student B's page127.0.0.1:8766
Student C's page127.0.0.1:8767

The port numbers above belong to your laptop. Each VM still uses port 8000. Assigning fixed laptop ports makes it possible to open all three websites in separate browser tabs.

Prepare your SSH tunnel command

Copy your ordinary Azure SSH command from the VM connection page, for example ssh -p 50000 student@YOUR_AZURE_HOST. It may include an -i key-file option. Enter the three private VM IP addresses separately. Each student chooses their own role and pastes their own SSH command. The form changes the command displayed below; it does not connect to the VMs or save credentials.

Enter the IP addresses and your original SSH command.

Complete the fields to build a command.

-L 127.0.0.1:8765:TARGET:8000 tells SSH to listen on port 8765 on your laptop and forward browser requests to the target address on port 8000 as seen from your own VM. There are three -L entries—one per student. Your own VM uses 127.0.0.1:8000; your friends use their private VM IP addresses.

Your own laptop terminal

Open the tunnel and keep it running

Run the generated SSH command in a local laptop terminal, not inside your already-connected Azure VM shell. If SSH asks for your ordinary authentication, complete it as usual.

-N tells SSH not to open a remote shell. A quiet terminal that stays open is normal. -o ExitOnForwardFailure=yes catches local forwarding setup errors such as an occupied laptop port; it does not prove every other VM is reachable. Keep the tunnel open while you use your browser. To close it later, press Ctrl+C in this local terminal.

Check: No new shell prompt appears while the SSH tunnel is active. Your other SSH terminal remains available for work on the VM.
ssh: connect ... Connection refused / Operation timed out

Check the Azure SSH endpoint and SSH port in the command you pasted. Those are different from the private VM IP and Docker port 8000. First confirm your normal SSH command still logs in without forwarding.

bind [127.0.0.1]:8765: Address already in use / Could not request local forwarding

Another tunnel or program already uses one of the laptop ports 8765–8767. Close your old SSH tunnel using Ctrl+C. On macOS/Linux, inspect the listener with:

lsof -nP -iTCP:8765 -sTCP:LISTEN

Check ports 8766 and 8767 similarly. Do not kill an unknown process just to free a port.

The SSH command works, but I get a terminal prompt

Your command may be missing -N. A normal SSH shell can still forward ports, but for this exercise a dedicated -N tunnel is easier to keep separate from your working VM terminal.

Your own laptop browser

Open your own Nginx webpage first

Student A opens http://127.0.0.1:8765/. Student B opens http://127.0.0.1:8766/. Student C opens http://127.0.0.1:8767/. These addresses refer to three different local ports, not three public websites.

A browser asks Nginx for the document. Unlike curl, it interprets the HTML and displays the page. You should see “Welcome to nginx!”. Leave this browser tab open; it will change when you replace the page.

Here 127.0.0.1 means your laptop because the browser runs there. SSH carries the connection to the VM, and Docker forwards it into the container.

Check: Your own webpage is visible in an ordinary laptop browser before you edit anything.
The browser cannot reach the site

Check the layers in order: is the laptop SSH tunnel open; does curl http://127.0.0.1:8000/ work on the Azure VM; is the browser using the correct role’s port? If the local curl works but the browser fails, focus on the SSH tunnel and laptop port, not Nginx.

The browser displays HTML text rather than a rendered page

Confirm the browser address is the http://127.0.0.1:876X/ URL and not a local file:// view of a text file. A normal Nginx response sends Content-Type: text/html.

The SSH terminal is quiet—does that mean it failed?

No. An ssh -N tunnel normally has no prompt or success message. The browser request is the test. If the site fails, return to the VM’s curl test to isolate the problem.

03

Make a page that belongs to your VM

The three Nginx servers currently show the same welcome page because all three containers came from the same image. Each student will replace only their own page. Nothing about this requires rebuilding the image.

Every Azure VM

Create an HTML file on the VM

A webpage is a text file. Here you will create one in your VM’s home directory, which is outside the container. Later you will copy it into Nginx’s web directory.

mkdir -p ~/lab09
cat > ~/lab09/index.html <<'HTML'
<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <title>My first Docker site</title>
  <style>
    body { font: 22px Arial, sans-serif;
           background: #e8f2ff;
           padding: 55px; text-align: center; }
    h1 { color: #174a71; }
  </style>
</head>
<body>
  <h1>Website from STUDENT on VM A</h1>
  <p>Served by Nginx inside a Docker container.</p>
  <p>Linux command I use: ls</p>
</body>
</html>
HTML

mkdir -p ~/lab09 makes a folder for your own work. The cat > ... <<'HTML' syntax is a here-document: the shell writes all following lines into index.html until it sees a line containing only HTML. The file begins with <!doctype html>, contains a title and CSS styling, and places visible text inside <body>.

<h1> means a main heading; <p> is a paragraph; background: #e8f2ff; chooses the page color. The web browser interprets these tags; Nginx simply returns the file.

Check: cat ~/lab09/index.html should print the complete HTML file. The page is saved on your VM before anything is copied into Docker.
The shell displays a > prompt and waits

You probably did not finish the here-document. Enter HTML alone on a new line and press Enter. The last HTML must not be indented. If the file is malformed, run the complete command again.

I pasted the prompt and got command not found

Only paste commands and file contents from the dark boxes. Text such as student@vm:~$ is the terminal prompt, not a command.

The file is empty or has wrong contents

Inspect it using cat ~/lab09/index.html. You can rerun the complete creation command: > replaces the existing file; it does not append to it.

Every Azure VM

Change the name, command and page color

Open the page in a text editor and make it visibly different from the other two students’ pages.

nano ~/lab09/index.html

Replace STUDENT with your own chosen label or initials and VM A with the correct letter. Replace ls with a Linux command you have used and add one sentence about what it does. Each group member should choose a different color: for example A #e8f2ff (blue), B #fff1df (orange), and C #e7f6e9 (green). You can choose other colors, but each page should be recognizable without reading the URL.

In nano, save with Ctrl+O, Enter, and exit with Ctrl+X. Saving changes the VM file; it does not yet change the page inside Docker.

Check: Use cat ~/lab09/index.html to confirm your changes really reached the file.

On an Ubuntu VM you can install it with sudo apt install -y nano if permitted, or use an editor already available. The goal is to change the contents of the VM file, not to use one particular editor.

My changes disappeared when I closed nano

Open the file with cat. If the old text is still there, you may have exited without saving or edited a different file path. Reopen ~/lab09/index.html and save with Ctrl+O before leaving.

Every Azure VM

Copy your file into Nginx and inspect the copy

Nginx serves /usr/share/nginx/html/index.html inside its container. Copy your VM file there, replacing the sample welcome page.

sudo docker cp ~/lab09/index.html lab09-web:/usr/share/nginx/html/index.html
sudo docker exec lab09-web cat /usr/share/nginx/html/index.html
curl -4 --noproxy "*" http://127.0.0.1:8000/

docker cp copies from the host VM into the container filesystem. The colon in lab09-web:/path means “inside this container.” The second command reads that file inside the container to confirm the copy, and curl checks what Nginx is actually serving through the VM port.

Copying a file into the container does not change the saved nginx:alpine image. You now have three versions to think about: the original image, your edited file on the VM, and the copied file in this container.

Check: The HTML printed from inside the container and the HTML returned by curl both contain your name and chosen text.
docker cp says No such container or path

Check the exact container name and whether it exists with sudo docker ps -a. Confirm your source file with ls -l ~/lab09/index.html. If the container is missing, start it again using the Nginx command in Part 01.

docker cp succeeded, but curl shows the original Nginx welcome page

First check the file inside the container:

sudo docker exec lab09-web cat /usr/share/nginx/html/index.html
sudo docker ps -a
sudo docker port lab09-web

If the copied file is right but curl returns an old page, check that you are contacting the same VM and port, and no old web server is answering on a different port. Re-run docker cp after saving your edited VM file.

docker cp worked, but my latest edit is not visible

Editing the VM file does not automatically update the container’s copy. Run docker cp again each time you save a new version. Later labs can use a bind mount for automatic sharing.

Your laptop browser

Refresh your own website

Return to your own tab in the laptop browser. Use the same URL you used for the Nginx welcome page.

The heading, paragraph and background should now show your choices. The SSH tunnel and the Docker port map have not changed; only the HTML file being returned has changed.

Check: A, B and C now each have a separate, personalized website visible on their own laptops.
The browser still shows the old welcome page

If VM curl still returns the old page, go back to the copy step; it is not a browser-cache problem.

Stop a container, then bring it back

Keep three browser tabs open. Do this in order: A first, then B, then C. Only the current student types the Docker commands on their own VM; the other two refresh that student’s browser tab. Watch how the browser behavior changes when the process and container change state.

Current student’s Azure VM

Stop the web server

Stop your own container. Do not delete it yet.

sudo docker stop lab09-web
sudo docker ps
sudo docker ps -a

docker stop asks the container’s main process to stop. docker ps lists only running containers, so your stopped container disappears from that list. docker ps -a includes stopped ones and should show Exited.

Ask the other students to refresh your tab. The browser should fail to load the page because Nginx is no longer running. The other two students’ websites should still work.

Check: Your website is unavailable while the container is stopped; the other two websites stay available.
My browser still shows the page after docker stop

An already-open browser tab retains pixels from its previous response. Refresh the page. Also check whether another service is listening on port 8000; a saved screenshot is not proof that the server remains available.

sudo docker ps -a
sudo ss -ltnp | grep ":8000" || true

Use sudo docker ps -a. You may have used a different name or already removed this container. Do not stop a classmate’s container to make the test work.
